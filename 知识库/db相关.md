# Mysql

## 一、索引相关

### 1.1 InnoDB B+树索引结构

思路：先分析B+树这种数据结构的特性--->采用这种特性的优势在哪？（结合db的性能瓶颈&查询）



基于多路平衡查找树（B+树）实现，所有的数据存储在叶子节点，所有叶子节点通过双向链表连接

非叶子节点（根节点、中间节点）仅存储索引键和子节点指针，用于导航查询路径

B+树索引分为聚簇索引和二级索引，

聚簇索引：默认以表的主键作为索引键（若未定义主键，Innodb会隐式生成一个），叶子节点存储整行数据

二级索引：以非主键字段作为索引键，可手动创建，叶子节点存储索引键+主键值，查询时需通过主键值到聚簇索引中查找完整数据（回表）



优势：

1、查询性能稳定（根节点->叶子节点）

2、范围查询高效（找到起始叶子节点后，走双向链表遍历即可）

3、存储空间利用率高（非叶子节点仅存储索引键+指针，使得单个节点可容纳更多索引项，树高更低减少磁盘IO）

4、排序友好 可直接利用叶子节点的链表顺序，避免额外开销



#### **发散1：树高**与磁盘IO

InnoDB的B+树索引是按磁盘页分层存储的，B+树每个节点在物理存储上对应一个或多个磁盘页，默认页大小为16KB，（如果某个节点数据量较大超过了一个磁盘页的容量时，InnoDB会将该节点的数据分布到多个连续磁盘页中，例如叶子节点存储大量数据/非叶子节点存储大量键值和指针）

然后磁盘的读写有一个很重要的特点：无法像内存一样随机访问单个字节，而是按页读取---即每次IO操作会读取一整个磁盘页的数据（即使只需要其中一个值）

那么每访问B+树的一个节点，就需要触发一次磁盘IO，树高越高每次查询需要访问的B+树节点越多，磁盘IO次数也越多



#### 发散2：磁盘IO与瓶颈

为什么磁盘IO成为了Mysql的性能主要瓶颈？

思路---：磁盘与内存的速度鸿沟&数据库的核心操作（读写数据、索引查询）对磁盘的强依赖



**计算机存储体系差异**

数据库的数据最终存储在磁盘，但所有运算都必须在内存中完成，数据从磁盘-->内存的加载 内存--->磁盘的持久化 也就是读写IO本质是“慢设备”与“快设备”之间的数据搬运，两者速度差异很大

| 存储介质    | 读写延迟    |
| ----------- | ----------- |
| 内存        | 10-100 ns   |
| SSD固态硬盘 | 100-1000 us |
| HDD机械硬盘 | 5-10ms      |

**数据库对磁盘的依赖**

1、数据库核心工作时频繁读写数据（查询一条记录需要索引页+数据页&&写一条记录需要写数据页+日志页），每次操作都绕不开磁盘IO（除非数据已在内存缓存中）

2、此外数据库的IO很多是随机IO，而磁盘对随机访问的效率很低

- 顺序IO：数据在磁盘上连续存储，读取时磁头或闪存控制器无需频繁移动
- 随机IO：数据在磁盘上分散存储，每次读写需要定位到不同的物理位置，单次IO定位成本远高于传输成本

此外数据库的场景中随机IO占比很高：

- 用索引查询数据时，索引的中间节点可能分散在不同的磁盘页（中间节点指向的页通常不连续）
- 比如更新多条非连续存储的记录都需要定位到分散的磁盘页触发随机IO

3、InnoDB缓冲池优化：缓存常用的磁盘页（索引页、数据页）减少重复的磁盘读，但缓存容量有限（一般为服务器内存的50-70%）但数据库总量往往远大于缓存总量，所有访问冷数据（未被缓存的数据）必须从磁盘读，或是当缓存满了加载新数据时需要淘汰旧数据如果旧数据时脏页还要写回磁盘，因此缓冲池是缓解磁盘IO

4、数据库写操作对磁盘IO更敏感，因为需要保证数据持久性ACID中的D，在InnoDB写操作流程：

- 先写redo log（确保崩溃后能恢复数据），redo log最终要刷到磁盘（即使有log buffer缓存，事务提交时也需至少刷一次盘）
- 再更新缓存池中的数据页（内存操作）
- 后台定期将脏页刷回磁盘

redo log的刷盘是同步操作（事务提交时必须完成），如果磁盘写redo log很慢（比如HDD随机写）会卡住事务提交--此时磁盘IO的速度就是事务处理速度的上线，哪怕批量写最终也需要数据持久化到磁盘，因此磁盘写入的带宽&IOPS会直接限制数据库的写入吞吐量

所以数据库优化中减少磁盘IO是核心方向（用SSD替代HDD、建索引减少全表扫描、调优缓冲池提升缓存命中率、优化redo log刷盘策略等）--本质都是为了绕过或缓解这个瓶颈







# Redis

## 一、性能瓶颈

我们知道对于Mysql数据库来说，磁盘IO成为了其主要的性能瓶颈，但Redis作为内存数据库，主要受限于内存、网络、CPU以及自身架构特性



1、内存，Redis的物理边界

Redis核心优势是所有数据（键值对、数据结构、缓存元信息等）都存储在内存，若数据量超过内存总量，会触发两种问题：

- swap机制被触发：操作系统会将Redis部分内存数据“交换”到磁盘的swap分区（相当于磁盘模拟内存）但磁盘速度远慢于内存，一旦发生swap，Redis性能将暴跌
- 数据淘汰压力：若开启内存淘汰策略，内存满时，Redis需频繁执行“淘汰旧数据”的逻辑（扫描键、计算热度、删除数据），这会占用CPU资源，导致正常命令处理延迟增加
- 内存碎片：Redis频繁更新（删除大key、修改字符串）会产生内存碎片，进而触发淘汰或swap



2、网络：高并发下的数据传输瓶颈

Redis是C-S架构，所有命令需要网络传输，当并发量极高时，网络带宽和延迟成为主要瓶颈：

- 带宽限制：大key（存储10MB的字符串、包含10w元素的哈希表），单次读写大key会占用大量网络带宽，例如一个10MB的大Key，每秒被读取100次消耗1GB/S带宽，若服务器网卡带宽仅1GBPS，会直接导致网络拥堵，或是一些小key，命令+响应1kb，每秒百万次请求，也到了1GBPS
- 网络延迟：Redis命令处理本身很快，但网络延迟可能放大响应时间。例如：同机房部署（网络延迟通常0.1-1毫秒）跨机房/云厂商部署：网络延迟10-50ms，此外TCP连接的三次握手、拥塞控制的机制在高并发下也可能因网络波动导致连接超时、重传



3、CPU：单线程模型的性能天花板

Redis核心命令处理逻辑是单线程（仅用一个CPU核心处理客户端命令），这一架构简化了并发控制（无需加锁），但也让CPU成为高并发下的关键瓶颈：

- 复杂命令阻塞：单线程致命弱点
- 高频命令的CPU消耗
- 多核利用率低



4、持久化机制 “数据安全”与“性能”的平衡难题

Redis虽为内存数据库，但需通过RDB快照或AOF日志 来实现数据持久化

- RDB性能开销 通过fork子进程生产全量数据快照 fork()会复制主线程的内存页表（写时复制），但大内存下fork耗时很高，期间主线程会被阻塞
- AOF性能开销，通过记录所有写命令实现持久化，性能瓶颈主要来自日志刷盘



因此Redis优化方向通常为：控制内存碎片与数据量、避免大key与耗时命令、优化网络架构（就近部署、客户端连接池）、合理配置持久化策略、集群分担单实例压力
