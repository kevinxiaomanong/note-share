# Mysql

## 一、索引相关

### 1.1索引介绍

**索引是一种用于快速查询和检索数据的数据结构，其本质可以看成是一种排序好的数据结构。**

优点：

1、通过索引可以大幅减少需要扫描的数据量，直接定位到符合条件的记录

2、加快排序和分组，如果order by&group by的列有索引，可以直接利用索引已经排好序的特性避免额外操作

缺点：

1、维护开销



大多数情况下索引比全表扫描要快，但也有例外：

- 数据量太小
- 查询结果集占比过大（如果要查询的数据占了整张表的大部分，优化器可能认为全表扫描更划算，因为通过索引多次回表（随机IO）的成本可能高于一次顺序的全表扫描）





### 1.2 InnoDB B+树索引结构

思路：先分析B+树这种数据结构的特性--->采用这种特性的优势在哪？（结合db的性能瓶颈&查询）



基于多路平衡查找树（B+树）实现，所有的数据存储在叶子节点，所有叶子节点通过双向链表连接

非叶子节点（根节点、中间节点）仅存储索引键和子节点指针，用于导航查询路径

B+树索引分为聚簇索引和二级索引，

聚簇索引：默认以表的主键作为索引键（若未定义主键，Innodb会隐式生成一个），叶子节点存储整行数据

二级索引：以非主键字段作为索引键，可手动创建，叶子节点存储索引键+主键值，查询时需通过主键值到聚簇索引中查找完整数据（回表）



优势：

1、查询性能稳定（根节点->叶子节点）

2、范围查询高效（找到起始叶子节点后，走双向链表遍历即可）

3、存储空间利用率高（非叶子节点仅存储索引键+指针，使得单个节点可容纳更多索引项，树高更低减少磁盘IO）

4、排序友好 可直接利用叶子节点的链表顺序，避免额外开销



#### **发散1：树高**与磁盘IO

InnoDB的B+树索引是按磁盘页分层存储的，B+树每个节点在物理存储上对应一个或多个磁盘页，默认页大小为16KB，（如果某个节点数据量较大超过了一个磁盘页的容量时，InnoDB会将该节点的数据分布到多个连续磁盘页中，例如叶子节点存储大量数据/非叶子节点存储大量键值和指针）

然后磁盘的读写有一个很重要的特点：无法像内存一样随机访问单个字节，而是按页读取---即每次IO操作会读取一整个磁盘页的数据（即使只需要其中一个值）

那么每访问B+树的一个节点，就需要触发一次磁盘IO，树高越高每次查询需要访问的B+树节点越多，磁盘IO次数也越多



#### 发散2：磁盘IO与瓶颈

为什么磁盘IO成为了Mysql的性能主要瓶颈？

思路---：磁盘与内存的速度鸿沟&数据库的核心操作（读写数据、索引查询）对磁盘的强依赖



**计算机存储体系差异**

数据库的数据最终存储在磁盘，但所有运算都必须在内存中完成，数据从磁盘-->内存的加载 内存--->磁盘的持久化 也就是读写IO本质是“慢设备”与“快设备”之间的数据搬运，两者速度差异很大

| 存储介质    | 读写延迟    |
| ----------- | ----------- |
| 内存        | 10-100 ns   |
| SSD固态硬盘 | 100-1000 us |
| HDD机械硬盘 | 5-10ms      |

**数据库对磁盘的依赖**

1、数据库核心工作时频繁读写数据（查询一条记录需要索引页+数据页&&写一条记录需要写数据页+日志页），每次操作都绕不开磁盘IO（除非数据已在内存缓存中）

2、此外数据库的IO很多是随机IO，而磁盘对随机访问的效率很低

- 顺序IO：数据在磁盘上连续存储，读取时磁头或闪存控制器无需频繁移动
- 随机IO：数据在磁盘上分散存储，每次读写需要定位到不同的物理位置，单次IO定位成本远高于传输成本

此外数据库的场景中随机IO占比很高：

- 用索引查询数据时，索引的中间节点可能分散在不同的磁盘页（中间节点指向的页通常不连续）
- 比如更新多条非连续存储的记录都需要定位到分散的磁盘页触发随机IO

3、InnoDB缓冲池优化：缓存常用的磁盘页（索引页、数据页）减少重复的磁盘读，但缓存容量有限（一般为服务器内存的50-70%）但数据库总量往往远大于缓存总量，所有访问冷数据（未被缓存的数据）必须从磁盘读，或是当缓存满了加载新数据时需要淘汰旧数据如果旧数据时脏页还要写回磁盘，因此缓冲池是缓解磁盘IO

4、数据库写操作对磁盘IO更敏感，因为需要保证数据持久性ACID中的D，在InnoDB写操作流程：

- 先写redo log（确保崩溃后能恢复数据），redo log最终要刷到磁盘（即使有log buffer缓存，事务提交时也需至少刷一次盘）
- 再更新缓存池中的数据页（内存操作）
- 后台定期将脏页刷回磁盘

redo log的刷盘是同步操作（事务提交时必须完成），如果磁盘写redo log很慢（比如HDD随机写）会卡住事务提交--此时磁盘IO的速度就是事务处理速度的上线，哪怕批量写最终也需要数据持久化到磁盘，因此磁盘写入的带宽&IOPS会直接限制数据库的写入吞吐量

所以数据库优化中减少磁盘IO是核心方向（用SSD替代HDD、建索引减少全表扫描、调优缓冲池提升缓存命中率、优化redo log刷盘策略等）--本质都是为了绕过或缓解这个瓶颈



#### 发散3：对比其他结构

**B树**

B树也是一种多路平衡查找树，但其每个节点既存储索引键也存储数据记录，可能B树节点存储10条索引键和对应的数据，B+树节点存储100条索引键，使得B树需要更多次磁盘IO去定位，此外B树叶子节点之间没有指针关联，在进行范围查询时需要从根节点重新遍历，而mysql的范围查询比较频繁，会降低效率



**红黑树**

红黑树是平衡二叉树，层高与数据量呈现**O(log₂N)** 增长，对于千万级数据树高可能达到30以上，IO次数过多，此外也不太适合范围查询

## 三、引擎相关

### 3.1 Innodb与MyISAM

MySQL 5.5.5 之前，MyISAM 是 MySQL 的默认存储引擎。5.5.5 版本之后，InnoDB 是 MySQL 的默认存储引擎

MySQL 存储引擎采用的是 **插件式架构**

**存储引擎是基于表的，而不是数据库**，负责数据的存储和读取



| 比较维度     | InnoDB                                             | MyISAM                 |
| ------------ | -------------------------------------------------- | ---------------------- |
| 锁级别支持   | 支持行级锁/表级锁                                  | 仅有表级锁             |
| 事务支持     | 提供事务支持&实现了SQL标准的四个隔离级别           | 不提供事务支持         |
| 外键支持     | 支持（不建议使用，在业务代码中进行约束）           | 不支持                 |
| 数据崩溃恢复 | 异常崩溃重新启动可恢复，依赖redo log               | 不支持                 |
| 索引实现     | 数据文件本身就是索引文件，存储在主键索引的叶子节点 | 索引文件和数据文件分开 |
| 性能差异     | 随着CPU核数增加，读写能力线性增长                  | 无法并发读写           |



### 3.2 InnoDb怎么存储数据的

InnoDB是以页为单位管理数据，页对应磁盘上连续16KB字节块，每次IO操作都以页为单位进行的

物理存储上：InnoDB有两种文件组织方式

- table_name.frm 表结构定义文件
- table_name.idb 数据和索引都在该文件



重要的.idb文件组织：

```
.ibd文件
├── 文件头（File Header）
├── 段（Segment）- 逻辑分配单位
│   ├── 区（Extent）- 1MB连续空间 = 64个页
│   │   ├── 页0（Page 0）- FSP Header
│   │   ├── 页1（Page 1）- IBUF Bitmap
│   │   ├── 页2（Page 2）- INODE
│   │   └── 页3-63 - 数据页/索引页
│   └── 更多区...
├── 页（Page）- 16KB基本单位
│   ├── 索引页（B+树的内部节点）
│   ├── 数据页（B+树的叶子节点，包含实际行数据）
│   └── 其他特殊页（Undo页、系统页等）
└── 文件尾（File Trailer）
```



所有B+树都存储在同一个.idb文件中，通过段隔离：

- 段时Innodb的逻辑分配单位
- 每个独立的B+树都有自己的段
- 段负责管理B+树所需的所有页



```
.ibd文件
├── 聚簇索引段（Clustered Index Segment）
│   ├── 根节点页
│   ├── 内部节点页（索引页）
│   └── 叶子节点页（数据页）
│
├── 二级索引段1（Secondary Index Segment - idx_name）
│   ├── 根节点页  
│   ├── 内部节点页
│   └── 叶子节点页
│
├── 二级索引段2（Secondary Index Segment - idx_email）
│   ├── 根节点页
│   ├── 内部节点页
│   └── 叶子节点页
│
└── 其他段（Undo段、临时段等）
```

索引的非叶子节点=索引页 叶子节点=数据页

所有索引的B+树都存储在同一个.ibd文件中











## 四、事务相关

事务本质是保证对数据库的操作构成一个逻辑上的整体，即要么全部执行成功要么全部执行失败

关系型事务有四大特性ACID：

- A 原子性 事务是最小的执行单位不可分割
- C 一致性 执行事务前后数据保持一致
- I 隔离性 事务之间互不影响相互隔离
- D 持久性 事务执行成功后对数据的修改是持久的



### 4.1 并发事务导致哪些问题

多个事务并发运行，经常对同一数据进行读写操作，会导致可能的问题：

1、脏读

A读取到B事务修改后但未提交的数据

2、丢失修改

事务A修改--事务B修改--事务A提交--事务B提交

最终A的修改丢失了

3、不可重复读

事务A两次读取中间事务B修改 导致一次事务里前后读取结果不一致

4、幻读

事务A两次读取中间事务B在该范围插入一条数据 导致事务A相同范围查询多了新的数据 好像出现幻觉一样



针对隔离性，SQL标准定义了四大隔离级别：

- 读未提交
- 读已提交
- 可重复读 
- 串行化 不存在任何并发问题 事务依次执行





### 4.2 并发事务控制

锁（悲观锁）和MVCC（乐观锁）

锁控制通过读写锁实现并发控制：

- 共享锁S
- 排他锁X

S和S可以并行，但SX&XX会冲突

读写锁又根据锁粒度分为表级锁和行级锁

行级锁又分为：

- 记录锁
- 间隙锁
- 临键锁 左开右闭区间，锁定一个范围包含记录本身，主要目的是为了解决幻读问题，因为记录锁只能锁住存在的记录，为了避免插入新数据需要依赖间隙锁

如果操作的索引是唯一索引&主键，InnoDb会对临建锁进行优化，降级为记录锁



**行锁与索引绑定**

InnoDb引擎的行锁是针对索引字段加锁，而非直接物理行，这是因为InnoDB天然需要索引来定位行

索引是定位行的唯一高效方式，因此如果更新语句的Where条件不使用任何索引，InnoDB无法通过索引定位到具体行，那么只能全表扫描符合条件的行，对整个表加锁



**快照读与当前读**

- 快照读 普通的select语句通过mvcc机制实现，事务启动时创建一个数据快照，后续的快照读都读取这个版本的数据
- 当前读 类似select... for update/lock in share mode、insert、update、delete会使用next-key lock来锁定扫描的索引记录和间隙，防止其他事务在这个范围内插入新的记录



**MVCC实现细节**

InnoDB为每行数据添加了三个隐藏字段：

- DB_TRX_ID 最后一次插入或更新该行的事务id
- DB_ROLL_PTR 回滚指针，指向该行的undo log
- DB ROW ID 如果没有设置主键且该表没有唯一非空索引时 InnoDB会使用该id生成聚簇索引（隐式主键）



**ReadView**

- 目前最大事务ID+1 即下一个要被分配的事务ID 大于等于该ID的数据版本均不可见
- 活跃事务列表中最小ID 小于这个ID的数据版本均可见
- 当前活跃事务ID列表
- 创建该ReadView的事务ID 即自身事务ID

如何判断可见性：![image-20250905160441437](D:\编程文档\note-share\知识库\assets\image-20250905160441437.png)

特别注意在读已提交RC和可重复读RR不同事务隔离级别下生成ReadView时机是不同的：

前者在每次当前读之前都会生成 而后者在事务开始之前生成后续查询复用



**undo log**

作用：

- 事务回滚时用于将数据恢复修改前
- MVCC 读取记录时如果该记录对当前事务不可见，通过undo log读取之前的版本数据

不同事务或相同事务对同一记录行的修改，会使该记录行的undo log成为一条链表，首部为最新的记录



**MVCC+Next-key lock解决幻读**

我们知道在SQL标准定义的隔离级别里其实RR可重复读是不能解决幻读问题的，但InnoDB引擎通过MVCC+Next-key lock来解决幻读问题

1、对于普通select，此时以MVCC快照读来读取数据，前后都是读取同一个ReadView，新插入的数据版本不可见

2、当前读通过加next-key lock来锁定读取到的记录同时还锁住了间隙，防止其他事务在查询范围内插入数据



**当前读与锁定读**

在RC和RR两个隔离级别下，如果执行普通的select语句则会使用MVCC，并在RR隔离级别下通过next-lock key防止了幻读

如果是select lock in share mode/for update会读取最新版本的数据，并加锁 







## 五、日志相关

### 5.1 redo log重做日志

重做日志，让mysql具备崩溃恢复的能力

每条redo log日志由表空间号+数据页号+偏移量+修改数据组成

刷盘策略：

1、事务提交不进行刷盘操作，如果mysql挂了或宕机，损失最近1s内事务

2、事务提交每次都刷盘，事务提交成功redo log记录一定在磁盘

3、事务提交只把log buffer里redo log内容写入page cache文件系统缓存，Mysql挂了也不丢除非宕机，page cache缓存区丢失



重点理解：Mysql中数据以页为单位，查询一条记录会从硬盘中把一页的数据都加载出来放入buffer pool中

后续查询优先从Buffer Pool里面找，更新时也是直接更新缓冲池里的数据，然后把在某个数据页做的修改记录到

redo log buffer里再刷盘到redo log文件



为什么不直接刷脏页？而是写redo log buffer再刷盘？

--首先页大小默认16kb 但可能就只修改了几字节的数据，直接页同步没必要，其次数据页刷盘是随机写性能很差

redo log一行记录可能就几十字节，而且还是顺序写，速度很快





### **5.2 undo log回滚日志**

每一个事务对数据的修改都会被记录到 undo log ，当执行事务过程中出现错误或者需要执行回滚操作的话，MySQL 可以利用 undo log 将数据恢复到事务开始之前的状态。

undo log还有个重要功能是支持MVCC

当数据被修改时，InnoDB会将旧版本数据写入undo log，在新数据行通过DB_ROLL_PTR回滚指针指向这条undo log，然后更新DB_TRX_ID为当前事务ID，多次修改后这些undo记录通过回滚指针串联成版本链

InnoDB将undo log分为两类：

1、插入undo log

记录insert操作，仅用于事务回滚（因为插入的新数据在事务提交前对其他事务不可见，提交后即可删除）

2、更新undo log

记录Update&Delete操作，既可用于回滚也可用于MVCC

事务提交后不会立即删除，等待所有依赖该版本的事务结束后由purge线程异步清理

undo log版本链形成：

事务修改数据时先将旧版本数据写入undo log，新数据行的Roll ptr回滚指针指向旧版本记录，DB_TRX_ID更改为当前事务ID，MVCC实现依赖undo log版本链



### **5.3 binlog归档日志**

binlog是逻辑日志，属于Mysql Server层日志，记录语句原始逻辑，binlog为二进制日志

Mysql的数据备份，主从架构依赖binlog同步数据，误操作恢复，结合全量备份+binlog可以恢复到任意时间点

要注意binlog记录的是逻辑操作（SQL语句/行变化）不是物理页的变化（redo log记载）



Mysql提供三种binlog格式：

1、STATEMENT 基于语句

记录SQL语句，但部分SQL语句（如包含NOW() UUID()等非确定性函数 回放时可能导致主从数据不一致）日志体积小，写入效率高，

2、ROW 基于行

不记录SQL语句而是记录每行数据的具体修改，日志体积大、写入性能略低，但主从绝对一致可精确恢复

3、MIXED混合模式，默认使用statement格式，当检测到非确定性语句时自动切换为ROW格式

强烈建议生产使用ROW格式，避免主从数据不一致的幽灵问题



文件结构：

1. 默认在datadir目录下
2. mysql-bin.000001 mysql-bin.000002
3. 索引文件 mysql-bin.index

日志轮转（当前文件大小达到max_binlog_size 1GB默认||服务器重启||手动执行flush logs）

每个binlog文件由多个Event组成



写入时机：事务执行过程中先把日志写到binlog cache，提交时再写到binlog 文件

涉及到write和fsync时机：

默认为1：即事务每次提交都刷盘

还可设置为0，只写到page cache由OS去控制刷盘时机



**最佳实践**

- 生产环境必须开启binlog 格式设为ROW

ROW格式可以有效避免幽灵问题：主库执行的SQL语句在从库重放时产生不同的结果导致主从数据不一致，例如NOW() 函数，自增主键顺序问题

而ROW格式不记录SQL语句而是记录实际的数据变更，但ROW格式日志体积更大&主从复制传输更多数据，但现代存储和网络成本已经很低，数据一致性的重要性更强

- 设置合理的过期时间 避免磁盘爆满



**两阶段提交**

为什么需要2PC？

--在mysql中一个事务需要同时写入两个日志：

- redo log（Innodb引擎层）保证崩溃恢复
- binlog (server层) 保证主从复制和数据恢复

```
先写redo log成功 后写binlog失败（服务器宕机）重启后Innodb通过redo log恢复事务，数据存在，但从库没有这个事务的binlog 主从不一致

先写binlog成功 后写redolog失败，事务回滚数据不存在，但从库已经通过binlog执行了这个事务，主从不一致
```



提交流程：

1、事务执行完后，InnoDB引擎先写入redo log buffer，然后调用fsync刷盘到redo log文件，此时redo log被标记为prepare状态

2、Mysql服务器写入binlog buffer，并调用fsync刷入bin log文件，binlog写入成功后InnoDb将redo log的状态修改为commit，并输入磁盘，然后完成事务提交



恢复原理：

1、崩溃在prepare阶段之后，binlog写入之前

由于此时redo log还是prepare状态，binlog无事务记录，InnoDB将事务回滚

2、崩溃在binlog写入之后，redo log commit前

此时redo log虽然还是prepare 但binlog已经完整记录该事务，InnoDb会将redolog改为commit状态提交事务

3、redo log commit之后

均完整，事务正常提交



重启流程：

Mysql重启时检查所有处于prepare状态的事务，如果该事务对应的binlog存在，说明从库已经同步，则需要提交该事务，如果该事务对应的binlog不存在，要把该事务回滚

而数据回滚其实依赖undo log





**binlog 和 redolog的恢复**

| 维度 | binlog                                                       | redolog                                                  |
| ---- | ------------------------------------------------------------ | -------------------------------------------------------- |
|      | 修复误操作/数据删除                                          | 修复崩溃导致的未刷盘数据丢失（确保持久性）               |
|      | 手动执行binlog解析日志重放                                   | 重启时自动触发                                           |
|      | 可恢复指定时间范围/指定事务ID操作                            | 仅恢复已提交但未刷盘到磁盘的数据页修改，不涉及未提交事务 |
|      | 依赖全量备份（单独binlog无法恢复全量数据，需先恢复全量备份再用binlog补增量） |                                                          |

binlog：需要主动修复数据错误的场景，如修复误操作、恢复指定时间点数据

redolog: 崩溃后的数据修复，例如Mysql进程被意外kill，但数据文件未损坏，或是服务器断电，重启后InnoDB通过redo log恢复未刷盘的已提交事务



生产环境的典型恢复流程：

1、db崩溃后重启时通过redo log自动恢复已提交的未刷盘数据

2、若存在误操作，先恢复最近的全量备份再通过binlog回放“全量备份完成时间~误操作前的增量日志”最终恢复到误操作前状态



### 5.4日志的写入&刷盘

redo log的刷盘策略受**innodb_flush_log_at_trx_commit**参数影响：

- 0 事务提交时 redo log值留在InnoDB的内存buffer中 后台线程每秒将redo log buffer写入OS缓存并调用fsync刷盘 redo log **留在 MySQL 内存**，MySQL 崩溃会丢数据 性能最好但安全性最差
- 1 事务提交时立即将redo log buffer写入OS缓存并调用fsync刷盘 redo log **立即刷盘**，任何崩溃都不会丢已提交事务，性能最差但最安全
- 2 事务提交时将redo log buffer写入OS缓存 但不调用fsync刷盘 redo log **写入 OS 缓存**，MySQL 崩溃不会丢数据，但 OS 崩溃会丢 



| 日志类型 | 写入时机          | 持久化时机          |
| -------- | ----------------- | ------------------- |
| undo log | 每条DML语句执行时 | 跟随redo log刷盘    |
| redo log | 每条DML语句执行时 | 根据策略刷盘        |
| binlog   | 事务COMMIT阶段    | 根据sync_binlog刷盘 |

关键理解：undo log本身也是数据，对undo log的修改会产生redo log，所以undo log的持久化依赖于redo log的刷盘

Mysql进程内存（redo log buffer 通过write系统调用 写操作系统内核缓存（page cache/buffer cache）--通过fsync() 或 OS后台刷盘 到物理磁盘（SSD/HDD）

OS缓存是指操作系统的页缓存，当Mysql调用write系统调用写入redo log文件时，数据先被复制到OS的page cache，此时数据还在内存中尚未写入物理磁盘

### 6.1主从复制

```
主库 (Master)                    从库 (Slave)
┌─────────────┐              ┌─────────────────┐
│  Binlog     │              │  Relay Log      │
│  (二进制日志)│              │  (中继日志)     │
└──────┬──────┘              └────────┬────────┘
       │                              │
       │ 1. Binlog Dump Thread        │ 3. SQL Thread
       │◄─────────────────────────────┤ (执行SQL)
       │                              │
       │ 2. I/O Thread                │
       └─────────────────────────────►│
                                    └─────────────────┘
```



主从复制步骤：

1. 主库记录binlog（只有已提交的事务才会写入binlog）
2. 从库IO thread连接主库 请求从指定的binlog文件和位置开始发生日志
3. 主库为每个从库创建一个binlog dump thread，来读取位置开始的binlog事件然后实时发送给从库IO线程
4. 从库IO Thread写入Relay log，写入本地中继日志文件
5. 从库执行Relay log 读取后重放事件，即在从库上重新执行相同操作



不同格式binlog的复制细节

Statement：从库执行SQL 可能主从不一致 NOW() RAND()函数

Row：直接将users表中数据更新 

mixed：Mysql来判断SQL是否安全，安全用statement不安全用row

































## 七、Mysql实践

### 7.1 主键选择

1、不使用UUID/MD5/HASH这种无序值作为Mysql主键

InnoDB引擎使用聚簇索引来组织数据，主键即聚簇索引，数据行在物理上按照主键顺序存储，表数据本身其实是主键索引的叶子节点

页分裂：InnoDB以页为单位存储数据默认页大小16KB，新插入的数据需要按主键顺序存放，但目标页已满时就需要分裂页面，系统会分配一个新页，将原页的部分数据移到新页中

页分裂后，页面填充率较低（通常只有50%）浪费存储空间，空间碎片化

使用无序值作为主键，每次随机插入都可能触发页分裂，读取&写入时需写入多个页面（且变为随机IO）

建议使用自增主键，且和业务不挂钩



### 7.2 字段选择

不建议使用TEXT类型字段，容易把IO、网络带宽打爆

不要把Mysql当文档型数据库用

字符集用utf8mb4 也是默认字符集

在字段声明时Not null，null比较坑，例如name字段值为null，在count(name) 时查不到这条记录

还有比如有个价格字段，假设其为null，在sum操作时，null+数值也是null会导致返回的也是null，可能代码也会报错，且必须显式指定默认值

主键列如果为整型，统一使用bigint，如果数据库用bigint，代码用int，当数据比较大的时候传过来是负值

设计货币金额精度敏感使用decimal类型，



### 7.3建表规范

- 必须包含时间戳字段datachange_lasttime
- 较长的字符类型，建议用前缀索引
- 单张表索引数量控制五个以内，组合索引字段控制三个以内（Mysql更新时还要写索引）
- 组合索引字段的顺序，去重之后数据越多代表区分度越高（高基数），放在前面
- 出海数据库 加UDL字段 userdata_location



### 7.4索引规范

背景：idx_a_b_c

- 前缀%模糊查询
- 类型转换
- 运算/函数 

避免排序

避免回表

- 禁止使用子查询（Mysql支持不好）

- update/delete 必须基于主键操作，删全表用truncate

不出现多于一次的join，多表关联时保证被关联的字段有索引，join类型要一致（避免因隐式转换导致索引失效）

# Redis

## 一、性能瓶颈

我们知道对于Mysql数据库来说，磁盘IO成为了其主要的性能瓶颈，但Redis作为内存数据库，主要受限于内存、网络、CPU以及自身架构特性



1、内存，Redis的物理边界

Redis核心优势是所有数据（键值对、数据结构、缓存元信息等）都存储在内存，若数据量超过内存总量，会触发两种问题：

- swap机制被触发：操作系统会将Redis部分内存数据“交换”到磁盘的swap分区（相当于磁盘模拟内存）但磁盘速度远慢于内存，一旦发生swap，Redis性能将暴跌
- 数据淘汰压力：若开启内存淘汰策略，内存满时，Redis需频繁执行“淘汰旧数据”的逻辑（扫描键、计算热度、删除数据），这会占用CPU资源，导致正常命令处理延迟增加
- 内存碎片：Redis频繁更新（删除大key、修改字符串）会产生内存碎片，进而触发淘汰或swap



2、网络：高并发下的数据传输瓶颈

Redis是C-S架构，所有命令需要网络传输，当并发量极高时，网络带宽和延迟成为主要瓶颈：

- 带宽限制：大key（存储10MB的字符串、包含10w元素的哈希表），单次读写大key会占用大量网络带宽，例如一个10MB的大Key，每秒被读取100次消耗1GB/S带宽，若服务器网卡带宽仅1GBPS，会直接导致网络拥堵，或是一些小key，命令+响应1kb，每秒百万次请求，也到了1GBPS
- 网络延迟：Redis命令处理本身很快，但网络延迟可能放大响应时间。例如：同机房部署（网络延迟通常0.1-1毫秒）跨机房/云厂商部署：网络延迟10-50ms，此外TCP连接的三次握手、拥塞控制的机制在高并发下也可能因网络波动导致连接超时、重传



3、CPU：单线程模型的性能天花板

Redis核心命令处理逻辑是单线程（仅用一个CPU核心处理客户端命令），这一架构简化了并发控制（无需加锁），但也让CPU成为高并发下的关键瓶颈：

- 复杂命令阻塞：单线程致命弱点
- 高频命令的CPU消耗
- 多核利用率低



4、持久化机制 “数据安全”与“性能”的平衡难题

Redis虽为内存数据库，但需通过RDB快照或AOF日志 来实现数据持久化

- RDB性能开销 通过fork子进程生产全量数据快照 fork()会复制主线程的内存页表（写时复制），但大内存下fork耗时很高，期间主线程会被阻塞
- AOF性能开销，通过记录所有写命令实现持久化，性能瓶颈主要来自日志刷盘



因此Redis优化方向通常为：控制内存碎片与数据量、避免大key与耗时命令、优化网络架构（就近部署、客户端连接池）、合理配置持久化策略、集群分担单实例压力





二、数据结构

在redis中 -1这个下标表示倒数第一个数据，这样可以简化对末尾元素的访问，避免额外查询长度的操作，如无需先执行LLEN获取列表长度再len-1





## 二、内存管理

### 2.1 过期删除

**为什么需要设置过期时间**

内存不比磁盘，是有限且宝贵的，如果不对缓存数据设置过期时间内存占用会一直增长最终可能导致OOM，通过设置合理的过期时间Redis可以自动删除暂时不需要的数据，为新的缓存数据腾出空间

且过期时间这个和一些业务很贴合，例如短信验证码可能只在一分钟有效，可以直接通过Redis来判断是否有效



**如何判断数据过期**

Redis有个过期字典可以看做hash表来保存过期时间，key为Redis数据库的某个key，value为一个long long类型的整数，保存其过期时间（毫秒级别的Unix时间戳）

查询一个key时先检查该key是否存在于过期字典中，如果不存在直接返回，如果存在则判断一下该key是否过期，如果过期直接删除key然后返回null





针对过期的key，Redis采用定期删除+惰性/懒汉式删除结合的策略，两者结合起来兼顾内存和CPU

定期删除对内存友好对CPU不友好

**定期删除实现**

Redis周期性地随机从设置了过期时间的key抽查一批，不保证所有过期的key都会被立即删除，此外通过执行时长和频率来减少对CPU的影响

- 如果执行时间超过阈值（默认25ms），中断这一次定期删除循环，避免使用过多CPU时间
- 如果这一批过期的key超过一个比例（默认10%）会重复执行删除流程，否则也中断此次定期删除循环，避免做过多的工作而获取很少的内存回收

默认每次抽查20个key，每秒执行10次，不建议把频率调过大&遍历所有key，会提高CPU的使用率

此外立即删除的成本太高了，

**惰性删除**

即每次查询key的时候才对数据进行过期检查，这种对CPU最友好但对内存不友好，可能内存存在很多过期的key占用空间



**大量key集中过期**

Redis在处理过期key时需要消耗CPU资源，如果过期key数量庞大导致Redis实例CPU占有率升高

在设置key的过期时间时尽量随机一点，或者开启lazy free机制，Redis在后台异步删除过期的key不阻塞主线程运行



### 2.2 内存淘汰

相关问题：Mysql里有2000w数据，Redis里只有20w数据，怎么保证Redis中数据都是热点数据？其实就是内存淘汰，随着用户的访问Redis通过淘汰算法来动态保留住热点数据



内存淘汰算法：当 Redis 使用的内存达到`maxmemory`（配置文件中设置的最大内存阈值）后，新写入 / 修改数据时，会触发淘汰策略，删除部分旧数据以释放内存

LRU和LFU是其中两类基于数据访问热度的淘汰算法（区别与随机淘汰、过期时间优先）



**LRU：最近最少使用**

核心思想：基于时间局部性原理，即最近访问的数据短期内可能再次被访问

标准的LRU算法会维护一个访问时间链表，每次数据被访问移到链表头部，每次从链表尾部淘汰，但这种实现会产生大量链表节点移动开销，不符合Redis追求高性能

Redis对LRU的实现：在key的元数据中记录一个24位的最后访问时间戳lru字段，当触发淘汰时Redis不扫描所有key而是随机挑选N个key，淘汰其中时间戳最小的key，N默认为5，其实N越大结果越接近标准LRU



**LFU：最不经常使用**

核心思想：一段时间内被访问次数最少得数据未来被访问的概率也越低

标准的LFU实现有冷数据误判问题：比如一个旧key过去访问频繁（但近半年未访问）却会因历史访问次数高而被保留占用内存，因此Redis实现了带衰减的LFU：

- 访问计数器：每个key的元数据中用8位存储访问次数，每个key被访问时计数器并非直接+1而是按概率递增（避免计数器过快溢出）若当前计数器值较小<10 大概率+1 若当前值>100小概率+1
- 计算器衰减：Redis定期对所有key的计数器进行衰减，例如默认每1分钟无访问计数器衰减一半，让过去频繁访问但近期无访问的冷数据计数器下降
- 淘汰逻辑：同样随机挑选N个key，比较LFU计数器淘汰其中计数器最小的key，若计数器相同再比较最后访问时间



在Redis4及之前默认策略是noeviction不淘汰任何数据，若此时内存达到maxmemory新写入/修改请求会直接报错，之后默认策略是volatile-lru（仅对设置了过期时间的key进行近似LRU淘汰）



在实际生产环境下，maxmemory不推荐设置为0，建议为服务器内存的50-70%，因为当其为0时，内存的淘汰策略会失效，含义是不设置任何内存上限，这会导致随着数据不断写入Redis，Redis持续向OS申请内存，服务器可用物理内存逐渐被占满若开启了swap分区会继续使用swap（但swap是磁盘模拟内存，性能会暴跌）一旦物理内存+swap也被耗尽，OS会触发OOM Kkiller机制：系统会根据进程的内存占用优先级筛选并终止高内存消耗进程（Redis作为内存密集型进程大概率会被优先jill）很多云服务默认会设置为volatile-lru





## 三、线程模型

Redis核心思想是--单线程处理核心请求+多线程处理非核心/阻塞操作，这样既避免了多线程上下文切换的开销，又通过辅助线程解决了潜在的性能瓶颈

Redis启动后会创建一个主线程负责绝大多数核心操作：

- 接收客户端TCP连接
- 执行Redis命令，维护数据结构
- 管理内存
- 响应客户端结果（封装返回值，写TCP响应）

Redis性能瓶颈主要在IO层面而非CPU计算，内存读写速度远快于IO，若引入多线程来处理命令反而因线程上下文切换+并发问题带来的锁开销增加额外成本，降低整体性能



辅助线程类型：

| 类型       |                                                              |
| ---------- | ------------------------------------------------------------ |
| IO线程     | 将主线程的网络IO操作：TCP 连接建立、请求读取、响应发送拆分多个辅助线程处理 |
| 持久化线程 | RDB持久化、AOF重写，                                         |
| 删除线程   | 大key异步删除UNLINK命令，避免耗时操作阻塞主线程              |



**单线程如何处理并发请求**

Redis主线程通过IO多路复用器同时监听多个客户端的TCP链接，例如Linux的epoll

1. 主线程将所有客户端连接的文件描述符注册到epoll
2. epoll监听这些FD的可读写事件（客户端发送请求、连接可写入响应）
3. 当有事件触发时，epoll将触发事件的FD告知主线程
4. 主线程依次处理请求

使得单线程无需阻塞在某个连接的IO上，可高效处理多个并发连接

且核心命令由主线程串行处理，无需像mysql一样为数据加锁





**单线程模型：**

![image-20250915152046402](D:\编程文档\note-share\知识库\assets\image-20250915152046402.png)

Redis基于Reactor模式设计了一套高效的事件处理模型，该事件处理模型以单线程方式运行

文件事件处理器使用IO多路复用程序同时监听多个socket套接字，并根据socket目前执行的任务来为socket关联不同的事件处理器，这使得Redis不需要额外创建多余的线程来监听客户端的大量连接，类似NIO的Selector组件



本质是借助了OS内核提供的多路复用系统调用如epoll，可以让单线程通过一个内核级监听队列同时监听多个TCP连接的IO状态，只有当连接的IO就绪时才会通知应用线程处理

1、注册监听，Redis启动时将所有客户端TCP连接注册到内核的多路复用器epoll中

2、阻塞等待就绪：Redis的单线程调用epoll_wait，此时线程会阻塞但不占用CPU，直到内核检测到至少有一个连接的IO就绪

3、批量处理就绪的IO事件，处理完后再次回到阻塞等待步骤，循环往复



新链接的建立：

启动时创建监听socket并注册到epoll，监听新链接请求，主线程epoll_wait发现有新连接时调用accept()接受新连接生成客户端socket，将该socket注册到epoll监听其数据读写事件，回到等待状态循环处理后续事件



## 四、持久化机制

在使用缓存时我们经常需要对内存中的数据做持久化即写入硬盘中，主要是为了重启机器&故障后恢复数据，以及用作集群之间主从节点的数据同步，Redis有三种持久化方式：AOF/RDB/混合



**RDB**

基于快照的全量备份，即创建某一时刻存储在内存全量数据的副本，可以复制到其他从节点以及留在本地重启恢复数据，RDB的触发有两种方式：

- 自动触发 （redis.conf里 有自动触发规则 save 900 1 300 10 60 10000即某时间范围内有多少次数据修改就触发）
- 手动触发：执行save（Redis主线程执行会阻塞所有客户端请求）&bgsave命令（fork一个子进程执行|推荐）

fork阶段会短暂阻塞主线程，与内存大小有关



**AOF**

基于日志的增量记录，客户端执行完写命令后，Redis将命令追加到内存的AOF缓冲区，根据配置的刷盘策略将缓冲区内存写入磁盘的AOF文件，刷盘策略有三种：

- appendfsync always: 每个命令都立即刷盘
- appendfsync everysec : 每秒刷盘一次
- appendfsync no 让OS决定何时刷盘 一般30s刷一次

但AOF文件会随着命令增多而膨胀，例如多次修改同一key的命令被重复记录，因此Redis提供bgrewiteaof命令或自动触发进行重写：

1、主线程fork子进程，去遍历内存数据生成重建当前数据最小命令集

2、重写期间的新命令会写入重写缓冲区，重新完后合并到新AOF文件



| 对比维度   | RDB                                  | AOF                        |
| ---------- | ------------------------------------ | -------------------------- |
| 数据完整性 | 低（快照间隔内数据可能丢失）         | 高（最多丢失1s数据）       |
| 文件体积   | 小（二进制压缩）                     | 大（文本命令）             |
| 加载速度   | 快（直接加载二进制数据）             | 慢（需要重新执行所有命令） |
| 写性能     | 高（bgsave不阻塞主线程）             | 中（需要频繁追加，且刷盘） |
| 适用场景   | 全量备份、数据迁移、容忍部分数据丢失 | 对数据安全性要求较高       |



**业务层补偿机制**

Redis宕机了，使用了AOF持久化，且刷盘策略为默认的appendfsync everysec，那么丢失的这1s数据怎么处理呢？首先明确丢失原因：若宕机发生在缓冲区已写入但未完成刷盘的窗口期这部分命令就会丢失



首先明确：这1s内未刷盘的数据没有落地到磁盘，Redis重启后无法通过AOF日志恢复



## 五、事务

Redis的事务是一组命令的集合允许多个命令打包执行，即事务中的命令要么全部执行要么全部不执行，且执行过程中不被其他客户端命令打断

事务通过以下四个命令实现：

1. MULTI 开启事务 后续命令会被加入事务队列但不执行
2. EXEC 执行事务队列中所有命令 返回各命令的执行结果
3. DISCARD 放弃事务清空队列命令
4. WATCH 监视一个或多个key若事务执行前这些key被修改，事务会取消执行



需要理解Redis的事务特性和传统Mysql数据库有显著差异：Redis的原子性很有限，且无隔离级别

1、有限的原子性：命令入队时如果发现语法错误，那么整个事务全部不执行&如果执行时某个命令报错不回滚而是继续执行剩余命令，不会有类似mysql undo log回滚机制

2、隔离性：串行执行，Redis是单线程模型即执行事务期间其他客户端命令会被阻塞，可以理解为串行化最高的隔离级别

3、事务持久性：Redis持久性依赖持久化机制AOF&RDB



因此Redis的事务还是有挺多局限性的，建议可以引入Lua脚本去执行，Redis能保证Lua脚本内命令原子性执行，且支持更复杂的逻辑（如条件判断）

且Lua脚本去批量执行多条Redis命令可以减少网络开销





























## 六、实践优化

### **6.1 bigkey**

bigkey大健是指占用内存空间过大或包含过多元素的健，其影响贯穿Redis整体

**风险点：**

1、性能阻塞 

对大key的操作会占用较长CPU时间片，导致后续所有命令排队等待引发Redis卡顿

2、内存与网络资源浪费

单个实例可能因为某几个Big Key快速达到内存上限，触发内存淘汰策略，误淘汰正常小key

客户端读取时也会占用大量网络带宽

尤其在Cluster集群下，key通过hash slot被分配到不同节点，若某个大key分配到单个节点会导致节点负载不均，即该节点的内存、cpu、网络压力远高于其他节点，称为集群瓶颈，且迁移相对困难

3、持久化与异常恢复

AOF重写和RDB持久化压力增大，且恢复时大key消耗大量时间



**如何发现大key**

1、redis-cli --bigkeys 官方推荐工具 遍历所有键统计

2、memory usage 直接返回键占用的内存大小

扫描命令scan渐进式遍历，避免全量遍历阻塞，适合生产环境日常检测



**解决方案**

1、业务设计上避免大key的产生，例如：

- String拆分，比如将200mb的日志文件拆分成：log:20240917:001/002每个key存10MB
- 集合类键分片：对包含大量元素的集合类key按一定规则拆分到多个小集合，例如存储用户100w订单数据的Hash键：user:10086:orders,按订单月拆分为user:10086:orders:202401 每个hash存储当月订单



2、对于已存在的大key，尽量避免全量操作减少阻塞

例如使用unlink命令异步删除大key

读写操作时禁用全量读取，改用hmget/srandmember

批量操作代替循环单条





### 6.2 内存碎片

内存碎片是指Redis实际占用的物理内存远大于其存储数据所需的逻辑内存，导致内存资源被无效占用

Redis依赖操作系统的内存分配器管理内存，当Redis频繁执行写入-删除-更新操作时，内存分配器可能无法将释放的内存完全复用从而产生碎片-零散、未被使用的内存空间



如何检测：通过INFO memory命令查看

```
127.0.0.1:6379> INFO memory
# Memory
used_memory:1073741824  # Redis 存储数据实际使用的逻辑内存（字节）
used_memory_rss:1342177280  # Redis 进程实际占用的物理内存（字节，即 RSS 内存）
mem_fragmentation_ratio:1.25  # 内存碎片率 = used_memory_rss / used_memory
```

关键指标为mem_fragmentation_ratio碎片率，通常：

1.5以下都是正常的 1.5以上就需要介入治理了 但如果<1 说明Redis内存可能被swap到磁盘了，这是更严重的性能问题



Reids会在碎片率到一定比例或是空闲内存不够时自动触发内存块整理，将零散的内存块移动、合并为连续的大内存块，释放可复用的空间。

若碎片率极高可以重启Redis实例，重启后新数据会按照无碎片方式分配内存





### 6.3 hotkey

**Hotkey（热点 key）** 指的是在某一时间段内，被客户端高频次访问的特定 key。这类 key 的访问量往往远超其他普通 key，可能瞬间集中产生数十万甚至数百万次请求，极易成为系统性能瓶颈，甚至引发服务不可用的风险。

hotkey和业务场景强相关，例如秒杀商品、热门话题



风险：

- Redis实例压力过载，热点key高频请求长期占用主线程导致其他命令被阻塞
- 如果热点key没命中，大量请求瞬间打到后端数据库（Redis可支撑10w+qps 但Mysql一般几千）存在db雪崩风险
- 网络带宽耗尽，导致正常请求无法传输
- 集群节点负载失衡，单节点承担所有热点请求，形成单点过热



解决：

1、本地缓存+Redis

2、Redis集群热点分散，例如对hotkey进行分片

3、hotkey设置超长时间过期，并主动更新

4、业务预热缓存，例如提前将商品价格&库存加载Redis
