### 并发相关

Q1：我现在有一个Java后端接口，接口内要访问其他四个服务，每个服务都是100ms，如果只有一个线程，不能使用多线程，怎么把接口返回时间降到100多ms



这里日常我们编写代码时会使用CompletableFuture+ThreadPool去做，但是这种其实是多线程处理了

这里可以考虑使用单线程异步非阻塞调用，核心是用单线程管理所有异步IO操作的状态和回调，避免线程切换



单线程实现方案：基于单线程反应器模式React模式，在单线程事件循环中完成所有服务调用

即基于非阻塞IO和事件驱动模型，通过高效的IO多路复用，在单线程内处理大量并发请求，同时避免多线程切换的开销，但不适用于CPU密集型场景，因为单线程无法利用多核CPU会导致计算瓶颈此时应使用多线程或分布式计算，若存在无法异步化的阻塞操作（sleep或锁等待）会阻塞整个单线程导致所有IO操作停滞



例如每个服务调用后还需要100ms的本地计算，那么多线程就更合适





**发散：**

其实这种单线程异步模型在Redis中也有应用：

即使用多路复用IO解决单线程的IO阻塞问题：底层依赖操作系统的select/poll/epoll等系统调用，这是解决该问题的核心技术，本质是让单线程可以同时监听多个IO事件（比如多个客户端的网络连接、磁盘文件的读写），当某个IO事件就绪时再去处理对应的事件避免在等待IO上浪费时间



Redis核心事件循环就是单线程+多路复用的落地实现，流程如下：

1. **初始化多路复用器**：启动时，Redis 会初始化一个 I/O 多路复用器，注册需要监听的 I/O 事件（比如监听客户端连接的 `listen` 端口）。

2. **阻塞等待 I/O 就绪**：单线程调用多路复用器的 `wait` 方法（如 `epoll_wait`），**阻塞等待**所有注册的 I/O 事件中 “有就绪的”（比如有新客户端连接、已连接客户端发送了命令数据、磁盘 I/O 完成）。
   ✅ 注意：这里的 “阻塞” 是 “多路复用器的阻塞”，而非 “线程处理逻辑的阻塞”—— 线程只在 “等待 I/O 就绪” 时阻塞，一旦有事件就绪，会立即唤醒并处理。

3. 处理就绪事件

   ：多路复用器返回所有 “就绪的 I/O 事件” 列表，单线程逐个处理：

   - 若为 “新客户端连接事件”：建立 TCP 连接，将新连接的 I/O 事件注册到多路复用器，后续监听该连接的命令请求。
   - 若为 “客户端命令请求事件”：读取客户端发送的命令数据，在内存中执行命令（如 `GET key`），生成响应结果。
   - 若为 “响应写入事件”：将命令执行结果写入 TCP 连接，返回给客户端（若写入时 TCP 缓冲区已满，会将 “写入事件” 重新注册到多路复用器，等待缓冲区空闲后再重试，避免阻塞）。

4. **循环往复**：处理完所有就绪事件后，单线程再次回到 “阻塞等待 I/O 就绪” 的步骤，形成无限循环。



```
package org.elon.thread;

import java.util.concurrent.CompletableFuture;
import static java.lang.Thread.sleep;

public class SingleThreadMutilService {

    private int service1(){
        try {
            sleep(1000);
            return 10;
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
    private int service2(){
        try {
            sleep(1000);
            return 10;
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
    private int service3(){
        try {
            sleep(1000);
            return 10;
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
    private int service4(){
        try {
            sleep(1000);
            return 10;
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }

    public static void main(String[] args) {
        //记录一下执行总耗时
        long start = System.currentTimeMillis();
        SingleThreadMutilService singleThreadMutilService = new SingleThreadMutilService();
        CompletableFuture<Integer> completableFuture1 = CompletableFuture.supplyAsync(() -> singleThreadMutilService.service1());
        CompletableFuture<Integer> completableFuture2 = CompletableFuture.supplyAsync(() -> singleThreadMutilService.service2());
        CompletableFuture<Integer> completableFuture3 = CompletableFuture.supplyAsync(() -> singleThreadMutilService.service3());
        CompletableFuture<Integer> completableFuture4 = CompletableFuture.supplyAsync(() -> singleThreadMutilService.service4());
        CompletableFuture.allOf(completableFuture1,completableFuture2,completableFuture3,completableFuture4).join();
        CompletableFuture<Integer> result = completableFuture1.thenCombine(completableFuture2, Integer::sum)
                .thenCombine(completableFuture3, Integer::sum)
                .thenCombine(completableFuture4, Integer::sum);
        long end = System.currentTimeMillis();
        System.out.println(result.join());
        System.out.println("总耗时:" + (end - start) + "ms");
    }
}

```

这种方式看似是单线程，但其实CompletableFuture.supplyAsync()默认使用了Java自带的公共ForkJoin线程池，所以实际是多线程并行执行的

ForkJoinPool.commonPool线程数量默认与CPU核心数相关

所以核心还是要抛弃多线程并行的思路，改用单线程事件循环处理所有异步任务



Q2：BS架构系统前后端怎么设计不那么阻塞

首先前端在调用的时候并行调用后端服务接口，而不是一个个请求过去，例如前端一个页面加载可能需要调用5个后端接口，如果接口之间没有相互依赖，可以并行调用五个接口，而不是串行等待



前端做数据预加载与缓存策略：

- 如进入列表页时，预加载下一页数据
- 缓存一些临时高频数据，如字典表，配置项



后端核心：快速响应请求

1、异步拆分：将同步处理+返回结果拆分成触发任务+查询结果

2、线程池隔离：为不同业务（订单、商品、日志）配置独立线程池，避免一个业务的耗时操作耗尽线程阻塞其他业务



前后端协同：减少不必要的交互

- 多个关联请求合并，减少http往返次数
- 后端返回前端直接可用的格式，避免前端二次处理
- 实时性要求高的场景（聊天/监控面板）用websocket实时通信

Q2：深度分页优化

指的是查询结果集的 “尾部数据”（例如从第 10000 行开始，取 10 行数据），对应的 SQL 通常是 `LIMIT offset, size`（如 `LIMIT 10000, 10`）。这类查询在数据量较大时（如百万 / 千万级表），容易出现性能瓶颈，核心原因是 MySQL 对 `LIMIT offset` 的处理机制 —— 它会**先扫描并跳过前 `offset` 行数据**，再取 `size` 行，跳过的行数越多，性能越差。

优化思路是避免Mysql扫描和跳过大量无效数据，通过定位到目标数据的起点直接取数:

思路1：基于主键/唯一索引的范围查询

```
-- 优化前：LIMIT 10000, 10（需跳过 10000 行）
SELECT * FROM user WHERE status=1 ORDER BY id LIMIT 10000, 10;

-- 优化后：用 id > 10010 定位起点（直接从 10011 行开始取）
SELECT * FROM user WHERE status=1 AND id > 10010 ORDER BY id LIMIT 10;
```

这种其实需要记录上一页末尾的主键ID，不支持跳页查询（如直接从第1页跳到第1000页）



思路2：覆盖索引优化：

```
-- 优化前：SELECT * 需回表，且 LIMIT 10000 效率低
SELECT * FROM user WHERE status=1 ORDER BY id LIMIT 10000, 10;

-- 优化 1：仅查 id 和 name，构建联合索引 (status, id, name)（覆盖索引）
CREATE INDEX idx_status_id_name ON user (status, id, name);
-- 直接从索引取数，无需回表
SELECT id, name FROM user WHERE status=1 ORDER BY id LIMIT 10000, 10;

-- 优化 2：若需查 *，可先通过覆盖索引取 id，再关联查完整数据（减少回表行数）
SELECT u.* FROM user u
JOIN (
  -- 子查询用覆盖索引取 id，仅 10 个 id，回表次数从 10010 降到 10
  SELECT id FROM user WHERE status=1 ORDER BY id LIMIT 10000, 10
) AS t ON u.id = t.id;
```

避免大量回表操作，如果在扫描跳过的时候需要回表会很慢





思路3：书签查询（基于非唯一索引的范围定位）：

示例：需求：按 `create_time` 降序分页，上一页最后一条记录的 `create_time='2024-05-01 10:00:00'`、`id=10010`，当前取下 10 行：

```
-- 优化前：LIMIT 10000, 10 需跳过大量数据
SELECT * FROM user WHERE status=1 ORDER BY create_time DESC LIMIT 10000, 10;

-- 优化后：用 (create_time, id) 定位起点（避免 create_time 重复导致漏行）
SELECT * FROM user 
WHERE status=1 
  AND (create_time < '2024-05-01 10:00:00'  -- 先按时间过滤
       OR (create_time = '2024-05-01 10:00:00' AND id < 10010))  -- 时间相同则按 id 过滤
ORDER BY create_time DESC, id DESC 
LIMIT 10;
```



### 限流相关

为什么要限流？？

爬虫、突发流量-->超过了系统能承受的范围，保护系统正常运转，对请求流量进行限制，防止服务雪崩

限流可能导致用户请求无法被正常处理或是无法立即被处理

控制系统的负载，削峰填谷，保证服务的质量



触发限流后的常见处理方式：

- 拒绝服务
- 排队或等待
- 服务降级



限流方式：

单机限流：计数器、滑动窗口、漏桶、令牌桶

分布式限流：Redis令牌桶、发票服务器sentinel



**限流算法**

1、固定窗口计数器算法

描述：将时间划分为固定大小的窗口，每个窗口内限制请求数量

2、滑动窗口计数器算法

限流颗粒度更小

3、漏桶算法

4、令牌桶算法



**限流维度**

- IP限流
- 业务ID：
- 个性化：根据业务的属性。比如机票聚合查询，依赖一些供应商的接口，不同供应商API直连能力不同，限流大小也不同，或是根据系统的运行指标（如QPS、系统负载）动态调整限流策略



**实现落地**

1、单机限流

基于Guava的RateLimiter工具类做，基于令牌桶算法，可以应对突发流量，此外Guava还支持平滑预热限流，即预热时间内速率逐渐提升到配置的速率



2、分布式限流

这种架构下存在多种服务，且一种服务可能被部署多份，经典比如建议使用Redis+lua

- 减少网络开销，利用Lua脚本批量执行多条Redis命令
- 通过Lua脚本来保证原子性

或是直接用Redisson封装好的做限流



常见实现：

Redis令牌桶--每次请求Redis（如果请求量较大的话 对Redis的调用量也是蛮大的）

发票服务器--sentinel 



结合机票聚合查询业务：

请求量大且调用方多：1000+渠道 平均qps2500+

为什么需要限流？

1. 请求流量不稳定：存在突发流量 （爬虫、活动这个其实可以预测到）
2. 资源有限 （部分底层资源不耐突发流量，比如一些航司供应商的接口，如果有突发流量可能会把它们打挂，部分资源收费）
3. 业务要求：业务合同原因，需要对一些外部分销的渠道进行限流

作为核心主流程：需要保证响应速度和稳定性

限流配置动态调整



单机限流其实运行性能好且稳定，但如果在分布式系统使用单纯的单机限流，开启HPA后流量会处于半失控状态

分布式限流其实每次请求都需要请求阈值管理者单点，这存在网络开销和不稳定因素
