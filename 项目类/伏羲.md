### 1、元数据管理

埋点介绍：埋点无非是who、when、where、how、what去定义

对于who：携程这边分两种，uid对应一个账户、cid对应一台设备、sid对应一次会话id即sessionid、vid访问标识符

when：事件发生时间、上报时间、类似Flink的两种时间语义、然后还有个时区的问题（上报时区）、unix时间戳

where：位置：IP/GPS

How：用什么设备 设备型号、OS等等 运营商

这些属于公参，框架自带的，每个埋点都应该有的

What：自定义参数，例如我搜一张北京-上海机票点搜索框，那么搜索框点击应该把票的时间、出发地这些信息给带上一起上报，所以这个是跟业务场景相关的





**时区的两大解决方案**

要么就是上报时区

或者使用unix时间戳，原理是时间戳生成的时候就会去掉时区的影响，传到另一个地方时再根据当地的区域加上时区的影响，时间戳是基于GMT的 不考虑时区的影响



**使用埋点数据的痛点**

需要某个数据的时候不知道有没有埋点，埋点查找难，如果你作为BI，其实想知道前端的一个埋点情况的，如果去问不一定能问得到，或者去找json，但根本不知道field的含义

埋点参数版本混乱，不同版本不一样，需要绑定起来

客户端和服务端是不一样的，客户端发布收不回来，比如客户端发完发现少了两个参数，要么等下一个版本补上，要么加hotfix（但你要指望用户都更新不一定），会导致埋点十几个公参，但每个公参版本都不一样，如果sql不管版本，会导致有些记录能拿到有些记录拿不到，如何做好兼容，即在参数元信息里加版本

## 伏羲平台产品-查总

**埋点介绍**

埋点是一种常见的数据采集方法，主要是记录用户使用产品的关键行为，例如页面的访问、按钮的点击等等

客户端采集实时发送到服务端，由公共数仓统一加工、存储

埋点数据是重要的数据资产，是实现数据驱动的基础，通过分析用户行为数据了解用户喜好与需求，做一些个性化功能与服务，埋点数据的分析可以支持产品决策，且埋点可实时检测业务指标，实时监控核心指标，比如某个重要按钮点击量的下跌

且目前各大互联网公司的新人红利已经基本消失，运营的重点也从挖掘新用户转变为了留存（即挖掘存量用户价值）那么挖掘重点在于用户行为分析，这依赖于高质量的埋点数据



**埋点的问题与挑战**

埋点数据质量是可用的基础，分析师常反馈埋点采集数据不全或关键参数空值率较高，基于这种质量分析出来的数据真实性和可信度不高，容易误导业务判断

使用起来不友好：产品团队想看数据得先找分析师提需求，再等分析师清洗加工再配置报表，如果中途需求变更分析师得重来，而且分析师找埋点也很头疼，很耗时，开发成本高，效率低，



**埋点的规范与流程**

埋点的开发是一个比较复杂的流程，需要规范化管理

1. 产品&运营同学提出数据需求  全局视角 指标定义
2. 数仓做方案设计 事件定义、参数定义、时机定义
3. 研发同学评估、开发 可行性评估、开发规范
4. 测试同学测试验收发布 数据、时机、事件准确
5. 平台可视化、取数分析、AB实验、人群圈选 

过去通过conf、飞书等文档进行需求管理 流程缺乏统一 难以闭环

建立贯穿埋点生命周期的管理规范，将散落在各地的信息、角色权责串联起来，保证每个环节都可被验证



**埋点设计**

埋点方案的设计直接决定了埋点数据产出的质量

埋点五要素：谁在什么时间什么地点干了什么事情 怎么干的

其中时间和地点是系统自动采集，业务埋点的设计主要关注埋点部署的位置、采集的数据信息、触发时机





**系统模块**

位置管理：如何定位，且建立了埋点地图



参数管理模块：治理埋点采集的内容，围绕业务目标采集真正解释用户行为，支撑深度分析的关键信息，例如用户点击了酒店卡片，需要采集酒店id，酒店名称、星级等，这些参数的命名、数据类型都需要标准化和管理，否则会陷入数据混乱，导致数据无法聚合或对比分析



埋点验收模块：

以上可以高效完成埋点方案设计，但实际开发还是可能存在问题，在埋点发布之前即投入应用之前，需要对埋点进行验收。系统会根据埋点的注册信息自动生成埋点校验规则，当埋点采集到的数据校验不通过时系统会自动提示，例如错埋、漏埋、取值不符合预期，当埋点验收通过才可以发布上线



埋点开发：

代码埋点（主流）：每个埋点都需要开发排期、测试，埋点代码和业务代码耦合，埋点下线费力度高

 服务端埋点：记录不容有失的业务结果，例如下单、支付等，服务端不受网络波动、用户关闭客户端浏览器等影响，数据上报成功率比前端高，适用于对数据准确性 实时性更高的业务场景

前后端埋点拼接：前端埋点擅长捕捉用户行为，后端埋点擅长记录业务最终结果或状态，拼接能更完整记录用户结果



**埋点应用**

# 数仓相关

看下怎么写数据的

什么是UDF函数：用户自定义函数，是大数据处理中一个重要概念

在Hive中内置了很多函数：例如JSON解析、字符串处理

但这些内置函数无法满足所有业务需求，例如我想把JSON字符串解析成一个Map，就需要自己写一个函数

Hive 中主要有三种 UDF：

| 类型     | 全称                              | 用途                                | 示例                                |
| -------- | --------------------------------- | ----------------------------------- | ----------------------------------- |
| **UDF**  | User-Defined Function             | **一行输入 → 一行输出**（标量函数） | `MapJson('{"a":1}') → map('a','1')` |
| **UDAF** | User-Defined Aggregation Function | **多行输入 → 一行输出**（聚合函数） | 自定义`MY_AVG()`                    |
| **UDTF** | User-Defined Table Function       | **一行输入 → 多行输出**（表函数）   | `LATERAL VIEW explode()`的底层实现  |

### 架构升级

老架构:

Hive--->Clickhouse-->查询

UBT采集-->KAFKA--->Flink/Spark--->Hive表（HDFS存储）

数仓每天调度（T+1，凌晨跑Hive-->Clickhouse集群 同步ETL）多分片（CK分布式表）



新架构：Data Lakehouse 核心思路是存算分离

数据存储层：HDFS 

元数据层：Iceberg

计算引擎：StarRocks查Iceberg Trino查Iceberg+Hive

StarRocks通过External Catalog功能接入Iceberg

注意StarRocks自己不存数据，只是借用了自己的计算能力（向量化引擎、MPP并行）去读外部的Iceberg文件



**Q1:为什么不直接用sr的内表**

UBT数量很大，全量用户行为直接存Starrocks内表成本很高，而且Trino/Spark等工具也需要同一份数据



**Q2：为什么需要两个引擎Starrocks+trino**

sr查单张iceberg表很快，由于向量化引擎，但跨格式JOIN不擅长

trino的优势在跨数据源JOIN 例如 Iceberg JOIN Hive

这也是湖仓一体的精髓：一份数据多引擎 按场景各取所长 省存储又兼具灵活性和性能



**Q3 Iceberg VS Hive**

底层都是HDFS 不同的是谁来管理表结构、分区、文件列表这层元数据



**Q4: 新架构优势在哪**

1、减少额外元数据查询开销

Hive-->Clickhouse同步时 可能按时间分表 真实表名不等于埋点名



2、T+1延迟 

Hive 分区昨天写完 → 凌晨调度同步 → 今天才能查
   用户看到的永远是昨天的数据

且ETL任务脆弱 增加维护成本 上线周期以天计算 链路长



3、双存储成本

同一份埋点数据，HDFS 存一份，ClickHouse 再存一份
   ClickHouse 是列式存储且有副本，成本很高





为什么CK在当时时合理原则 因为那时候数据湖概念刚兴起 生产落地案例少 Hive查询又很慢 分钟级 不能给用户用

用CK做列存+向量化 基本上亿级数据秒级响应 有点类似Redis查询加速层的意思



老架构本质是用 ClickHouse 当 Hive 的"查询缓存"，用数据冗余换查询性能，代价是 T+1 延迟、双份存储、ETL 维护成本。新架构 Iceberg + StarRocks 直接消灭了这个中间层——存储层进化了，查询引擎

### 埋点管理

从业务类型上，UBT埋点可以分为开发埋点与业务埋点

- 开发埋点用于排障与开发统计，比如根据内存埋点中size字段判断当前用户设备是否处于不健康状态，或是对内存占用做统计可以知道当前页面占用的用户平均内存，用于定位线上问题或衡量性能指标
- 业务埋点侧重于业务统计，如统计页面PV、UV，或者统计按钮点击次数，关键元素的曝光次数

各类型埋点说明：

- pageview 衡量页面访问 新打开页面或从上一个页面返回，PV埋点都会被记录
- trace 业务普通埋点 业绩统计类埋点
- action 点击埋点 点击页面元素出发
- exposure 页面元素曝光触发，一般自动触发
- devtrace 开发类普通埋点 
- metric 数值统计埋点
- server服务端埋点

一般场景下，只需要主动埋入 PV/Trace/DevTrace 埋点，其他类型大多由框架自动埋入。

不要滥用埋点，每次埋点都有网络、存储、MQ等资源占用，可以通过多个过程合并至一次埋点上报、埋点字段使用概要数据等手段有效降低埋点量级

按场景正确使用不同类型埋点：UBT通道和下游系统会针对特定场景对埋点加工处理做针对性优化

另外还有剔除异常用户的功能，即剔除一些网络爬虫crawler

我们有张爬虫明细表，按天分区，有uid、vid、cid三种类型，包含IBU和HTL，且酒店bu还有APP/ONLINE/H5/小程序



这里有个技术点Anti-Join反连接模式，目的和INNER JOIN正好相反，如果inner join其实是保留爬虫的用户行

而我们left join+is null 是只保留不是爬虫的用户行

这里为什么不用更直观的NOT IN呢？语义是等价的，这在OLAP引擎里有两个问题：

1. NULL陷阱 如果子查询里division_id有一条NULL值，NOT IN的结果是整个WHERE返回空，因为 x not in (..., null)在sql标准里恒为UNKNOWN,而left join+is null不受此影响
2. 性能 爬虫名单表有77,140,236 大概七千多万，OLAP引擎对LEFT JOIN有专门的hash join优化，通常比NOT IN子查询更快



SQL三值逻辑：不是简单的布尔true/false，而是true/false/unknown

而where子句只保留结果为true的行，其他都会被过滤，所以用not in其实很容易埋雷，只要有脏数据产生，就没有数据返回了

sr处理join的核心是hash join，阶段1 Build，读小表在内存建hash table，然后读大表逐batch用uid_value去hashtable探测

# 知识补充

### 1、存储类型

OSS和S3是同一类产品-云对象存储（object storage）只是厂商不同

传统的文件系统用目录树组织文件，例如/data/2024/log.txt 而对象存储的模型更简单：

bucket+key

桶+字符串路径 得到value（二进制文件）+metadata



S3是AWS推出的 Amazon Simple Storage Service，业界事实标准，几乎所有大数据生态都原生支持S3

衍生出了S3协议，现在说兼容S3是指实现了S3的API接口

OSS是阿里云的对象存储产品，国内用得多



文件存储用目录树组织数据，即我们每天用的文件系统

- 有真实的目录层级，ls、cd都是真实操作
- 支持随机读写，可以只修改文件中间某几行
- 访问需要挂载到操作系统



对象存储是用扁平的key-value组织数据，没有真正的目录

- 不支持随机写，只能整体上传覆盖，对象写入后是不可变的
- 通过HTTP REST API访问 无需挂载
- 单个bucket可存数十亿对象，近乎无限扩展
- 存在大量元数据，高度可扩展，海量数据支持

适合大量非结构化数据，图片、视频、日志、数据湖文件



块存储是最底层的，文件存储通常建立在块存储之上，被分成多个block存储到磁盘

对象存储是独立的设计

### 5、分区策略



- 全量分区 每个分区存当天的全部数据快照 每天全量覆盖写入 存储开销大 查询简单 不需要合并多个分区 适合DIM维表、数据量不太大
- 增量分区 每个分区只存当天新增或变更的记录 不存没变化的 存储小 但想知道当前状态需要合并所有历史分区 适合ODS 贴近binlog/kafka原始数据 适合数据量大 变化率低
- 快照分区 本质和全量分区一样 也是每个分区存完整数据 但强调不可变性 写入后不再修改 记录某个时间点的业务状态留存 按业务节点做存档 审计  历史定格的场景
- 拉链分区 给每条记录加上start_date和end_date 记录在哪段时间内有效 用一张表存所有历史变化，存储效率最高，实现复杂适合变化不频繁的数据

# 沼泽地

1、项目里存在很多关联查询，将数据读取到内存再进行过滤或筛选呢？和join比哪个好

看场景，但通常Join好，使用Join的优势：

- 减少网络传输：只传输最终结果集，而不是把两张大表都拉到内存
- 利用索引：JOIN条件命中索引时，数据库可以避免全表扫描
- 内存压力小，不占用JVM堆内存，不触发GC

一些内存关联适合的场景：

- 一侧数据量极小，如字典表、配置表，可以缓存到内存，避免重复查询
- JOIN逻辑复杂度很高
- 跨异构数据源







2、技术选型

在做技术选型时 应当从真实业务负载出发 

| 查询类型     | 代表场景                                  | 关键指标       |
| ------------ | ----------------------------------------- | -------------- |
| 单埋点聚合   | count(uid),count(DISTINCT uid)按天        | 延迟p95        |
| 多维Group by | 例如按city、platform、私餐分组            | 延迟+内存      |
| 跨源JOIN     | 埋点JOIN AB实验表、人群表（iceberg+hive） | 是否支持、延迟 |
| 多埋点组合   | inner join/union 多张Iceberg表            | 并发吞吐       |

用生产规模的数据结构，在测试环境搭建同结构集群，写入相同量级的模拟数据

重点在于保留数据分布特征：uid基数大小、热门city的数据倾斜程度，这些直接影响JOIN和Group by性能

然后设计测试用例，针对第一步分出的每类查询，各写3-5条代表性SQL

```
-- 用例 A：基础聚合（主路径）
SELECT d, COUNT(*) AS pv, COUNT(DISTINCT uid_value) AS uv
FROM iceberg.ctripdi_prodb.some_key
WHERE d BETWEEN '2025-01-01' AND '2025-01-30'
GROUP BY d;

-- 用例 B：多维 GroupBy + 私参过滤
SELECT city, platform, COUNT(DISTINCT uid_value) AS uv
FROM iceberg.ctripdi_prodb.some_key
WHERE d = '2025-01-15' AND some_param = 'xxx'

-- 用例 C：跨源 JOIN（Iceberg + Hive AB表）
SELECT ab.exp_version_array[1], COUNT(DISTINCT t.uid_value)

  ON lower(t.uid_value) = ab.division_id
WHERE t.d = '2025-01-15' AND ab.d = '2025-01-15'
  AND ab.exp_code = 'xxx' AND ab.is_cur_trigger = 1
GROUP BY 1;
```

**压测 SR vs Trino**

SR集群5台 128G 32C

对比trino



结论：在同等环境下，20个并发。SR（no cache）比Trino快1-3倍不等，SR（block cache）快1-10倍不等，平均快7倍，选用SR做OLAP引擎





在SR-Hive这个场景实测下来，如果并发量过多，基本跑不出来，相比下来trino稳定

这就是为什么涉及到Hive-Iceberg join的时候用trino 因为用户其实可能会选多个日期



SR在查询hive外表的时候，同一SQL在不同情况下，查询耗时差异较大，具体表现为：

- 高并发下耗时远高于低并发，高并发下HDFS出现瓶颈
- 高资源消耗SQL会导致集群整体查询耗时上升，劣质SQL拖慢集群
- 同一SQL在数据冷加载和热加载情况在耗时不同，数据未预热查询耗时波动



我们把占用大量IO、MEM、cpu的sql统称为劣质SQL，SR资源隔离是软隔离，在同一进程进行隔离，尤其对IO方面无法做到有效隔离，当多个劣质SQL查询时，会导致其他SQL无充足资源使用，被迫进入等待队列



数据未预热：初次查询时需要从hdfs侧拉数据到BE节点，会产生网络IO开销，且SR BE侧开启了DataCache，同时也对BE节点产生写入IO，第二次查询会从SR BE的Data Cache读取数据，避免上述开销





**从架构定位来看SR-hive这个场景**

SR是一个原生OLAP引擎，核心设计是管理自己的列式存储（类似CK），External Catalog是后来加入的能力，本质是一个适配器，让BE节点去读HDFS上的外部文件

Trino则相反，从Presto时代开始就是为读外部存储而生，Hive/HDFS是它的第一场景



SR-Hive的流程：

1. FE查询Hive metastore获取tablename、partition个数等表元信息
2. FE查询hdfs获取文件信息，block块分布等文件元信息
3. FE基于1和2生产最优执行计划，并把执行计划下发各个BE节点
4. 各个BE根据执行计划开始计算，第一步往往是scan算子，从HDFS拉原始数据

Hive Metastore Server、以及NameNode被打爆，且BE节点资源竞争没有隔离，高并发这样拉取会相互抢占集体拖慢，而Trino对HMS元数据的缓存更成熟、加上Resource Group资源隔离，以及split调度



而Iceberg的元数据是文件，存在HDFS上，本身就是分布式文件读取，HMS不再是必经的单点瓶颈

Hive的问题根源：HMS Thrift RPC拿分区列表，且HDFS NameNode拿每个分区下的文件列表，两次集中式服务调用

存算分离：

- 计算层 无状态节点 弹性调度
- 存储层 对象存储S3/OSS + 本地缓存



存算一体挑战：

- 资源僵化 存储与计算紧密绑定，导致二者无法独立扩展，难以同时高效利用
- 成本高：数据三副本冗余，存储成本增加
- 弹性受限：扩缩容时数据需要balance，引发大量IO，影响应用

存算分离优势：

- 资源灵活 存储与计算解耦 可独立扩展
- 节省存储 本地存储一副本
- 极致弹性 计算节点秒级扩缩容





Hive+Clickhouse vs iceberg+sr+trino

- 从存储上看 数据在Hive和CK是双份存储 而SR做存算分离 减少存储 
- 从计算上看 之前我们凌晨有一批Spark Job做埋点数据的T+1同步到CK，运维和计算成本，新架构无需额外做同步
- 从系统角度 CK是share disk架构 SR走存算分离是share nothing结构，计算节点是无状态的，可扩展性好，在k8s体系下单节点扩容5s，CK的扩容很麻烦需要人工搬迁数据，且计算和存储分离后会使得资源利用率变高
- 从吞吐和性能上看 CK是单表的极致性能，非常适合单张宽表做聚合分析的场景，但多查询并发和复杂JOIN是短板，而SR的并发调度和JOIN优化是其核心能力，结合我们经常多埋点分析，包括结合AB实验、人群JOIN来看SR更合适

**CK的劣势**







宽表模式是一种写时计算materialization的思路，在写入时把所有关联做完，查询时只扫一张表，这个思路在一下条件下是合理的：

- 查询模式固定，预先知道要关联哪些维度
- Schema稳定
- 有数据工程团队维护ETL，构建宽表的Spark任务通常是一个复杂的多源JOIN作业，很脆弱

但实际业务场景往往是：维度经常变、需求经常临时出现，维护成本堆积

Lakehouse架构（Iceberg+MPP引擎）：把Join的代价还给查询时，用计算换灵活性，数据层保持干净的范式设计
