









## LLM基础

区分：哪些是工程做的，哪些是模型做的

大模型只负责三件事：

1. 理解用户语义
2. 按照约束输出结构化内容/tool_call
3. 整合工具结果生成自然语言问答

剩下的都是AI应用工程层实现：上下文组装、限流、重试、路由、风控、记忆、工具调用、MCP转发、配额管理

大模型只是算力推理底座，核心是围绕大模型调用搭建一套工程治理架构





























### 大模型API调用

其实AI应用跑通很简单，难点在于如何把大模型API当成一个不稳定、昂贵、受配额约束的外部依赖做治理



拆开看，一次请求通常包含8个阶段:

1. 业务请求进入：鉴权
2. 上下文组装：拼system prompt，user input，history，rag，工具schema，输出格式约束
3. token预算评估：估算输入token，预留输出token，决定是否裁剪历史，压缩上下文或换小模型
4. 模型网关路由：选择模型、供应商、区域、超时参数、重试策略、限流桶
5. 供应商API调用：同步返回或流式返回
6. 响应解析：处理delta，tool call，
7. 状态回写：
8. 观测与告警：记录traceid，ttft

模型网关不能只当代理层看，它更接近AI应用的稳定性控制面，如果没有网关每个业务系统都会自己处理API KEY、超时、重试、限流、日志、供应商切换，哪怕第一版很轻，也要把模型调用收口到一个统一的LLM gateway



**同步返回 vs 流式返回**

同步返回：等待LLM生成完全部内容后，一次性返回完整结果

流式输出：边生成边返回，模型每产生一段文本或一个事件，供应商就通过长连接把增量推给调用方



TTFT：time to first token 从请求发出到收到第一个可展示token的时间

流式输出不是性能魔法，它没有让模型少算token，只是把等待过程拆成了可感知的进度



tips：面向用户展示的长文本默认用流式，后台批处理和强结构化任务默认









### JSON结构保证

不能把自然语言承诺当成工程契约



structured outputs是在模型侧服务器校验，是openai、anthropic推出的高级功能

模型在生成每一个token时严格按照schema约束生成 模型内部做实时约束和校验

而json mode+json schema 模型尽力生成符合schema的结构 但必须应用层校验





fuction calling的价值 是把模型擅长的语义理解和程序擅长的确定性执行连接起来



sop：standard operating procedure



关键原则：可以降级，但不能让模型编造业务事实





### 工具调用

























后端工具执行程基本流程：

1. 先按工具名分发
2. 做JSON Schema校验 再反序列化为业务参数
3. 权限校验 
4. 工具返回结构化结构，让模型基于事实生成回答
5. 全链路审计 把模型意图、参数和执行结果记录

设想一下，如果我们把模型生成的参数直接丢给订单服务，等于把业务系统的入口暴露给一个概率模型



**限流**

传统API限流通常按QPS，大模型API只按qps不够，应同时看：

- RPM 每分钟请求数
- TPM 每分钟Token数
- 并发数 正在生成的请求数量
- 上下文大小  单请求输入token



一个典型的降级链路：

优先模型可用 -> 正常调用
优先模型 429 -> 切备用同级模型
备用模型也限流 -> 切轻量模型并缩短输出
仍不可用 -> 排队或返回"当前请求繁忙"

注意：降级不是偷偷变差，如果轻量模型会影响答案质量，要在业务层明确标记，例如“当前为快速模式，复杂问题建议稍后重试”















## AI Agent

agent=llm+planning+memory+tools

agent loop：推理--行动--观察--推理  至任务完成||达到最大轮次

1. 初始化时加载System Prompt、可用工具列表、用户初始请求
2. 循环迭代--读取上下文，LLM推理决定下一步（调用工具还是直接回复）触发并执行工具，捕获返回结果追加到上下文
3. LLM判断任务完成，不再调用工具时退出循环
4. 安全兜底--防死循环，设置迭代次数&token消耗 阈值

但任务跑越久，上下文会越来越长。关键信息被稀释后，模型容易跑偏



记忆：短期记忆通常是上下文历史，用来保持对话连续性，长期记忆一般是外部知识库，比如向量数据库或知识图谱，短期记忆解决刚才说了什么，长期记录解决过去积累了什么

tool：让LLM真正操作外部世界，比如查数据、调API、读文件、执行代码

observation：观测，工具执行后返回结果，放入上下文再进行下一次推理，反馈闭环很重要



对于一个Agent系统，通常绕不开三层：

1. LLM Call 模型调用，不同供应商模型的接口差异 重试 限流
2. Tools call 让LLM和外部系统交互
3. Context Engineering 管理传给大模型的prompt和上下文，还包括动态记忆注入等

能调模型，能用工具，能管上下文，Agent的能力栈就基本成型了





### 如何保障agent在Tool的调用与发现

agent想准确调用外部工具 绕不开Open AI Schema和MCP，前者解决数据格式问题，后者解决通信接入问题

数据格式：Function Call Schema

外部工具可以很复杂，但 LLM 推理时只认结构化描述。它用 JSON Schema 描述工具名称、用途、参数类型、必填字段。模型根据这段描述判断要不要调用工具，以及参数该怎么填。

一个典型的查询慢SQL日志的工具描述

```
{
  "type": "function",
  "function": {
    "name": "query_slow_sql",
    "description": "查指定微服务在特定时间段的慢 SQL 日志。服务响应慢、数据库超时、CPU 飙升的时候用这个。如果用户问的是网络或内存问题，别调这个。",
    "parameters": {
      "type": "object",
      "properties": {
        "service_name": {
          "type": "string",
          "description": "服务名，比如 user-service、order-service"
        },
        "time_range": {
          "type": "string",
          "description": "时间范围，格式 HH:MM-HH:MM，比如 09:00-09:30"
        },
        "threshold_ms": {
          "type": "integer",
          "description": "慢 SQL 判定阈值（毫秒），默认 1000"
        }
      },
      "required": ["service_name", "time_range"]
    }
  }
}
```

进阶封装Skills，有些任务不是调用一个原子工具就能完成的，比如“排查数据库慢查询”，得先读日志、跑分析脚本、对照团队规范给出建议。如果每次都从零开始，Agent 的输出既不稳定，也没法复用。

**Skill 的本质不只是工具的高阶封装，更像一份可调用的经验包**：把一类任务的执行顺序、约束条件和踩坑记录写下来，让 Agent 在判断当前任务命中时才把它读进来，而不是启动就全部塞进上下文。



1. 传统Toolkits黑盒：把多个原子工具在代码层封装一个高阶工具，对外只暴露JSON Schema，适合推理步骤少逻辑固定的场景
2. Agent Skills白盒，以SKILL.md为核心的自然语言指令集，每个Skill是一个独立文件夹



Skill.md分两部分，前面是轻量元数据（我是谁、什么时候使用），后面是正文（具体流程、约束和示例），启动时只读元数据做发现，等LLM判断需要某个skill，再把完整正文加载进上下文，延迟加载

Claude Code、Cursor这类工具已经原生支持这套模式，会自动扫描项目里的.claude/skills目录，由模型自己判断哪个Skill该激活



工具怎么接入宿主程序？

我们需要让模型知道工具长什么样，MCP提供了一套基于JSON-RPC 2.0的统一通信协议，被称为AI领域的USB-C接口

外部系统通过MCP Server暴露能力，宿主程序连接Server后就能自动发现并注册工具

![image-20260517154625614](D:\编程文档\note-share\AI\理论\assets\image-20260517154625614.png)

MCP 定义了三类标准原语：

| 原语类型  | 作用                     | 例子                           |
| --------- | ------------------------ | ------------------------------ |
| Tools     | LLM 主动调用的函数       | 查询数据库、发送邮件、执行代码 |
| Resources | Agent 按需读取的只读数据 | 本地文件、数据库记录、日志流   |
| Prompts   | 可复用的提示词模板       | 代码审查模板、故障报告模板     |







### Agent构建范式

**ReAct**

Reasoning+Acting，思路是让模型一边推理，一边和外部环境交互，LLM自己容易缺少实时信息，也容易幻觉

ReAct就让它走一步看一步，每一步根据工具返回结果继续判断



**Plan-and-Execute**

先让LLM制定全局分布计划，再由执行器按步骤完成，适合步骤多、依赖关系明确的长期任务，但其实它计划一旦定下来，动态调整和容错会弱一点，有点接近workflow了，

先用 CoT 生成全局步骤，再在每个步骤内部嵌入 ReAct 子循环。这样既有全局结构，也保留局部灵活性

**Reflection**



**Multi-Agent**

多个独立Agent协作完成复杂任务，每个Agent专注一个角色或职能

1、Orchestrator-Subagent模式：编排agent负责全局规划和任务分发，子agent并行或串行执行具体任务，最后汇总输出

2、Peer-to-Peer模式：agent之间平等对话，互相审查，适合需要辩论、评审、验证的任务



**A2A协议**

单个Agent升级到Multi-Agent后，agent之间怎么沟通变成一个工程问题

如果还靠自然语言互相聊天，Token 消耗很高，也容易出现格式解析错误。

它让 Agent 之间用结构化数据交互，比如带 Schema 的 JSON、XML，或者状态流转指令，而不是一堆自然语言废话。



**Agentic Workflows**

吴恩达倡导：没必要一直干等底层模型突破，用工程方法，把推理、工具、记忆、反思、多实体协作编排成流水线，已经能做出很多可用的AI应用

常见设计模式有四个：

1. **Reflection**——让模型检查自己的工作
2. **Tool Use**——给 LLM 配网络搜索、代码执行等工具
3. **Planning**——让模型提出多步计划并执行
4. **Multi-agent Collaboration**——多个 Agent 协作完成任务

真实项目里，这几个模式很少单独出现。更常见的是混着用。

比如先 Planning 拆任务，再用 ReAct 执行子任务，中间调用 Tools，最后用 Reflection 做检查。这样看，Agentic Workflows 更像是一套工程组合拳，而不是某个单独框架。





## RAG

**Retrieval-Augmented Generation**

检索-增强-生成，把信息检索和大语言模型绑在一起用，系统先从知识库里检索出和当前问题相关的片段，然后把这些片段和原始问题一起喂给LLM，让模型基于检索内容回答，而不只靠训练时记住的知识



LLM的缺陷：

1. 知识时效性，预训练模型的知识会停在训练数据截止时间点，训练后发生的新事件、新政策、新产品文档，模型默认是不知道的，除非通过联网、工具调用或外部知识注入来补，RAG是动态检索外部知识源
2. 私有数据访问，企业内部的产品文档、知识库、客户数据，不可能让公开 LLM 随便访问。RAG 在用户提问时只提取和问题相关的片段给 LLM，不需要暴露全部数据，模型也能基于企业自己的知识回答。
3. 幻觉，LLM 编造事实这件事大家都遇到过。RAG 通过提供明确参考文本，让模型尽量基于证据回答，确实能降低幻觉概率。生产级 RAG 通常还要配引用校验、答案评估、拒答机制和人工反馈闭环。
