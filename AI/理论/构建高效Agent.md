## 构建高效 Agent

> 原文：[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)  
> 作者：Anthropic 工程团队，2024-12-19

---

### 核心观点

在与众多团队合作构建 LLM Agent 的过程中，Anthropic 发现：**最成功的实现往往使用简单、可组合的模式，而非复杂框架**。

核心建议：先用简单 prompt，配合完善的 eval 进行优化，只有当更简单的方案确实不够用时，再引入多步骤 agentic 系统。

---

### 基本概念：Workflow vs Agent

| 类型 | 定义 |
|---|---|
| **Workflow（工作流）** | LLM 和工具通过预定义代码路径进行编排，控制流由代码决定 |
| **Agent（智能体）** | LLM 动态指挥自身流程和工具使用，自主决定如何完成任务 |

两者不是非此即彼，而是一个复杂度谱系。根据任务特点选择合适的位置。

### 何时使用agent
先找最简单的解决方案，只有需要的时候再增加复杂度
智能体系统通常用延迟和成本换取更好的任务表现
工作流对于那些可以提前定义好步骤的任务更适合，而智能体更适合那些难以提前枚举所有步骤的复杂任务。
workflow能提供可预测性和一致性 但对于需要大规模灵活性和模型驱动决策时 智能体是更好的选择。
但其实对大多数应用，通过retrieve+in-context examples来优化单次LLM足够了

### 何时使用frameworks
有很多开源框架（如 LangChain、LangGraph 等）可以帮助快速搭建 agentic 系统，但它们并非必要条件。Anthropic 的经验是：
- **优先直接使用 LLM API**：大多数模式只需几行代码
- **框架的价值**：提供了更高层次的抽象和工具
- **框架的风险**：增加调试难度，诱导过度设计
- **建议**：先用简单 prompt + eval，只有在确实需要时再引入框架。

---

### 基础构建块：增强型 LLM

所有 agentic 系统的基础单元是**增强型 LLM**，在原始 LLM 之上叠加三种能力：

- **检索（Retrieval）**：从外部知识库获取相关信息
- **工具（Tools）**：调用外部 API、执行代码、操作文件等
- **记忆（Memory）**：短期上下文 + 长期持久化存储

这个增强型 LLM 就是后续所有架构模式的基本组件。

### 六种工作流架构模式

#### 1. Prompt Chaining（提示链）

将任务分解为一系列步骤，每次 LLM 调用处理上一步的输出，中间可插入程序化校验点。

**适用场景**：任务能清晰拆分为固定子任务，愿意用延迟换取更高准确率。

**示例**：
- 先生成营销文案 → 再翻译成多种语言
- 先输出文档大纲 → 校验大纲 → 再根据大纲撰写正文

---

#### 2. Routing（路由）

对输入进行分类，将其分发给专门的后续处理流程。

**适用场景**：不同类型的输入需要差异化处理，且分类本身可以准确完成。

**示例**：客服场景中，将用户问题分类为"账单问题"、"技术支持"、"投诉"，分别路由给不同的专化 prompt 或工具链。

---

#### 3. Parallelization（并行化）

LLM 同时处理一个任务的多个部分，最后聚合输出。有两种模式：

- **分区（Sectioning）**：将任务拆分为独立子任务并行执行
- **投票（Voting）**：对同一任务运行多次，通过多数表决提升可靠性

**适用场景**：任务可分解为独立并行子任务，或需要多个独立视角来提升置信度。

---

#### 4. Orchestrator-Workers（编排者-工作者）

一个中央 LLM（编排者）动态地将任务拆解，分配给工作者 LLM 执行，最后汇总结果。

**适用场景**：复杂任务，且所需子任务无法提前预测。

**示例**：
- 需要跨多个文件做修改的代码任务
- 需要从多个来源收集信息并综合分析的搜索任务

---

#### 5. Evaluator-Optimizer（评估者-优化者）

一个 LLM 生成响应，另一个 LLM 评估结果并给出反馈，形成迭代精炼循环。

**适用场景**：有明确的评估标准，且迭代精炼能带来可验证的提升。

**示例**：文学翻译——先翻译，再由评估者从流畅度、文化适配性等维度打分并指出问题，再重新翻译。

---

#### 6. Autonomous Agents（自主 Agent）

LLM 完全自主地运行，通过工具调用和环境反馈的循环来执行长周期任务。适合处理那些难以甚至不可能提前枚举所有步骤的复杂任务。

**工作循环**：
1. 感知当前环境状态
2. 制定行动计划
3. 使用工具执行动作
4. 观察结果，调整策略
5. 重复直到目标完成

**风险点**：错误会在循环中累积放大，需要设计人工介入检查点和沙箱环境来控制风险。

---

### ACI：Agent-Computer Interface

Anthropic 提出了一个重要概念：**ACI（Agent-Computer Interface，智能体-计算机接口）**，类比 HCI（人机交互界面）。

工具文档的质量对 Agent 性能影响极大，应像设计用户界面一样认真对待工具接口设计：

- 每个工具的文档要清晰描述其功能、参数和边界条件
- 工具命名应语义明确，避免歧义
- 通过大量测试和迭代来验证工具设计是否符合 LLM 的"认知习惯"

---

### 实施建议

**三个核心原则：**

1. **保持简单（Simplicity）**：能用简单 prompt 解决的问题不要引入 agentic 架构
2. **透明可见（Transparency）**：让 Agent 的规划步骤对用户/调试者可见
3. **精心设计 ACI**：把工具文档和接口设计视为一等公民

**关于框架的建议：**

优先直接使用 LLM API，大多数模式只需几行代码即可实现。框架（如 LangChain、LangGraph 等）有其价值，但也会引入：
- 额外的抽象层，遮蔽底层 prompt 和响应，增加调试难度
- 诱导开发者过度设计，引入不必要的复杂度

---

### 高价值应用场景

两类最适合 Agent 落地的场景：

**1. 客服（Customer Support）**
- 有明确的成功指标（解决率、满意度）
- 可以接入公司知识库和操作系统
- 错误可控，有人工兜底
- 典型案例：Coinbase、Tines 使用 Claude 构建 agentic 客服，大幅提升解决率和效率

**2. 代码生成（Coding Agents）**
- 代码执行结果可客观验证（测试通过与否）
- 有清晰的反馈循环（编译错误、测试失败）
- 适合多步骤、跨文件的复杂编程任务

---

### 总结

| 维度 | 建议 |
|---|---|
| 起点 | 从最简单的 prompt 开始 |
| 升级时机 | 简单方案达到性能上限时 |
| 架构选择 | 按任务特点选择合适的模式，不追求复杂 |
| 工具设计 | 像做产品一样打磨 ACI |
| 风险控制 | 长周期 Agent 需要沙箱 + 检查点 |
