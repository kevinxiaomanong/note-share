### 1、AI infra&大模型算法&大模型应用

**AI infra**

AI infra（AI infrastructure）指的是人工智能基础设施，可以理解为支撑大模型训练+推理+应用全生命周期的底层工程系统，核心关注以下领域：

| 子领域         | 核心问题                         |
| -------------- | -------------------------------- |
| 分布式训练框架 | 如何用千卡GPU联合训练一个模型？  |
| 模型推理服务   | 如何高并发、低延迟               |
| 模型部署与编排 | 如何在k8s上弹性调度GPU服务       |
| 向量数据库     | 如何高效存储/检索十亿级embedding |

AI infra工程师的典型职责：

1. 部署开源大模型到生产环境，用vLLM+Docker+k8s提供HTTP API
2. 优化推理性能，启用PagedAttention（vLLM特性）提升吞吐
3. 设计高可用架构、集成可观测性（日志、指标、trace链路）、网络隔离（API不出内网）、限流



技术栈：

- python、GO
- 系统：k8s、Docker、cuda、vllm
- 数据库：Milvus、qdrant、redis
- 监控：Prometheus、grafana



适合人群：系统工程师、SRE、后端工程师转型、强工程能力，懂GPU基础





**大模型算法岗**

核心目标：设计、训练、优化大模型本身--让模型更聪明、高效、专业

| 方向                 | 具体工作                                            |
| -------------------- | --------------------------------------------------- |
| 基础模型研发         | 设计新架构（如改进Transformer）、预训练千亿参数模型 |
| 模型微调（SFT/RLHF） | 在垂直领域（如金融、医疗）微调模型，提升专业性      |
| 模型压缩与加速       | 量化、剪枝、蒸馏，让大模型能在手机/边缘运行         |
| 多模态/Agent算法     | 研究图文理解、语言生产、智能体决策等前沿能力        |
| 评估与对齐           | 设计评测集、减少幻觉                                |

技术栈：

- python、C++（高性能算子）
- 框架：Pytorch、DeepSpeed

输出：产出模型权重.bin文件和训练/推理脚本，部署的Qwen、Llama来自这类团队

适合强数学+编程能力，热爱前沿研究，硕士以上



**大模型应用开发岗**

用大模型解决具体业务问题--把AI能力转化为用户价值

| 场景             | 具体工作                                      |
| ---------------- | --------------------------------------------- |
| RAG应用开发      | 构建企业知识库问答（埋点助手）、文档摘要      |
| Agent系统开发    | 开发能调用工具的智能体（自动查数据+生成报告） |
| 前端集成         | 在web/app/im 中嵌入聊天界面（如copilot）      |
| Prompt工程与评估 | 设计高质量prompt，构建评估pipeline            |

技术栈：

- 语言：python、java、typescript
- 框架：Langchain
- 后端：springboot
- 数据库：PostgreSQL
- 部署：docker、k8s、serverless



我们依赖算法岗训练的模型，也依赖AI infra，需要调用它们部署的推理服务、直接面向用户

适合：全栈/后端工程师、懂业务、重交付、强工程落地能力



**三者协作关系**

算法岗关注模型好不好，产出模型给infra，infra部署vLLM服务，提供API为大模型应用开发岗调用，关注服务稳不稳、快不快，而我们去开发具体应用落地

#### AI大模型概览

LLM是一个“基于海量数据训练出的、超大规模参数化的、概率性文本生成函数”

但这个函数并不是总能给出正确输出，真相是LLM的输出是看似合理而非绝对正确，它没有真实理解只是模仿训练数据中的语言模式，会自信地编造错误信息（幻觉/hallucination），它的正确依赖于：输入是否清晰、问题是否在训练数据覆盖范围内，是否使用RAG/工具增强

而我们的检索增强，实际上是在改造这个函数的输入，不是改造LLM函数本身，而是在喂给它更高质量的输入



大模型的训练数据来源：

1. 大规模网页文本（占比最大）
2. 开源代码库
3. 书籍与百科
4. 对话与问答数据

训练阶段：

1. 预训练，学习语言基本规律、世界知识、代码语法，在万亿级token的语料上通过下一个词预测任务训练，获得基础语言能力
2. 监督微调，使用高质量人工标注的指令-回答对，使得其能理解指令、生成结构化回答
3. 对齐优化，RLHF（基于人类反馈的强化学习，人类对多个回答打分，模型学习偏好



python基础 目前AI大模型生态来看 python无疑是和生态结合更紧密的语言 我们花时间简单过一下基础即可



怎么看待大模型微调这个事情？

适合长期稳定、领域高度垂直的任务，比如医疗诊断助手、法律文书自动生成，投入大，周期长，维护难



真正快速见效、低成本落地、且被广泛采用的技术路径是RAG检索增强生成+指令工程prompt engineering+Agent智能代理，这是当前企业级AI应用的主流范式

灵活、可解释性强、更新迭代快、成本低，适用于：客服系统、知识库问答、数据分析助手



本质是如何让现有大模型更好地为业务服务





### 大模型应用 vs agent

1. **大模型应用开发**

   泛指**所有基于 LLM/Embedding 等大模型能力做的业务系统**，范围极广，是一个**领域统称**。

   只要调用了大模型接口、基于模型能力对外提供服务，都属于这类。

   

2. **Agent（智能体）**

   是**具备自主规划、多轮决策、工具调用、循环执行能力**的一类特殊大模型应用，强调**自主行动、闭环流转**，属于大模型应用里的**复杂形态**。

   

> 一句话：**所有 Agent 都是大模型应用，但不是所有大模型应用都是 Agent**。



Agent 是该领域下**带自主决策 + 多轮循环 + 工具调用**的复杂子类；

普通应用是**代码主导流程**，Agent 是**LLM 主导流程**；
