### **三、服务配置**

我们可以在SOA Portal里对我们的服务进行配置

配置分应用配置和服务配置，服务配置适用单个服务，而应用配置则是对该应用下所有SOA服务都生效

服务可配置的点有很多，我们一个个学习

1、服务预热

Java应用在刚开始启动的时候处理响应速度会很慢，只有当热点代码被执行了一定次数以后，响应速度才会到达一个稳定状态，由于Java慢启动现象的存在，多数情况下我们有必要对Java应用进行预热，防止出现大量的慢请求

过程：

在机器启动后，将先进入预热阶段，时间由预热时长决定

预热阶段时流量会根据预热算法逐步增加（无特殊需要推荐默认的线性算法）

预热结束后，机器将进入稳定阶段，流量将保持均匀



2、黑白名单

黑名单：启用后对在黑名单里的客户端访问直接拒绝，返回403Frobidden

白名单：启用后对不在白名单里的客户端访问直接拒绝，返回403



3、限流

防止调用方请求量突然增加而导致服务端压力增大

触发条件：连续10s的请求数超过了单机预定设置的限流值，则框架直连返回429，不反序列化请求，不进入服务业务实现处理，知道连续10s内请求小于限流值，类似滑动窗口的实现



- 服务限流 到达当前服务 所有操作的请求
- 操作限流 到达当前服务下 某个特定操作的请求



- 单机限流 作用于服务端单机
- 集群限流 仅支持服务级别限流



4、流量分配

- 由多条配置的路由策略组成
- 每条路由策略应指明 路由规则 以及命中后如何分配流量

### 四、原理剖析

携程内部服务多，目前内部采用SOA这种框架将业务进行解耦，我们分成以下角色

- SOA  面向服务的架构
- Server 服务提供方
- client 服务调用者
- 契约 规范数据交换方式和接口定义，独立于语言和操作系统平台，是一种通用的协议，根据契约文件可以生成相同服务接口的不同语言实现，内部推荐BJSC契约
- 序列化与反序列化 
- 服务注册与寻址 因为实际环境下，服务端可能部署在集群上，而客户端也在不同机器，我们通过Artemis注册中心来维护，实时更新服务信息和路由信息，并提供了运维API



**Artemis与服务端、客户端的交互**

服务端启动时，会与注册中心建立WebSocket的长连接，并将自身的服务信息注册到注册中心，服务实例启动完成后每5s调用自身健康接口进行自检，自检成功向注册中心发送心跳包，如果注册中心没有接收到心跳包会认为这个实例不健康，会踢出集群

客户端初始化时也会与Artemis建立webSocket的长连接，通过服务标识获取到对应的服务调用信息，注册中心会自动实时把路由和实例的变化信息推送给客户端



**熔断**

服务端熔断： 服务端接口在处理请求大量出错/变慢 会出发服务端熔断 这时接口会直接返回熔断错误 来保护服务提供者其他接口不受影响

客户端熔断：客户端调用某个接口大量出错/变慢，发送客户端熔断，这时不会再发出请求而是直接抛出熔断异常，来保护客户端本身和依赖该客户端的其他程序，避免发生雪崩效应

SOA熔断的实现参考了netflix hystrix

服务端熔断是操作维度 客户端是服务+操作+ip维度



**隔离**

避免部分请求占据过多系统资源，以信号量&线程池实现 上限300 同熔断粒度

但其实300也比较大，假设服务端有10台机器，那其实需要客户端3000个并发才打挂 



**限流**

服务端通过滑动窗口算法来控制最近10s的访问量，对于超出访问量的请求，服务端会直接返回429，目前SOA Portal支撑多种限流方式

IP直连：通过域名访问时其实内网请求会跟外网一样，先经过硬件LB，再走SLB最终到达服务端，但其实内网没必要这样，直接根据IP地址直接访问服务端机器即可

分组路由：一个Service可以部署在不同的实例，可以对实例进行分组，并通过路由策略控制client访问的分组

#### **7.1异步服务编排**

首先要明确：为什么要上异步？或者说异步解决了什么问题？

第二是异步是怎么解决这些问题的



异步的核心价值是解放**请求线程**，例如服务调用方，或是http请求调用方，提升系统的并发处理能力，降低资源消耗

**异步价值1-解决因线程资源耗尽导致系统并发能力低下**

Tomcat的工作线程池容量是有限的，如果每个请求线程都阻塞在IO等待上，那么同时能处理的请求数就被线程数限制死了：

- 同步/伪异步 200线程-->最多同时处理200请求
- 异步：线程发起IO请求后立即释放，去处理其他任务，IO返回后再回调处理结果，200线程可以支持数千个并发请求，因为线程不再被等待占用

**异步价值2-解决资源浪费，响应延迟升高**

阻塞线程在IO等待期间，CPU完全空闲，但线程的栈内存、线程调度资源仍被占用，大量阻塞线程会导致内存占用飙升，线程切换开销大CPU频繁切换阻塞唤醒的线程，表现为CPU/内存没跑满，但请求响应越来越慢



异步实现的核心原理：

**通过IO多路复用+回调/事件驱动** 让线程从全程占用变为只处理有效工作

- IO多路复用，如NIO selector、linux epoll，一个线程可以管理多个IO连接，监听哪些连接有结果返回
- 回调/CompletableFuture，结果返回后，由指定的线程处理结果，而非原请求线程阻塞等待



核心流程拆解为：

1. 发起异步请求，工作线程调用queryDaasNio，仅做封装请求、发起网络调用的工作，然后立马释放返回线程池
2. 网络请求由NIO框架的IO线程管理
3. 请求返回结果后，IO框架通知回调线程池，由回调线程处理结果，组装响应最终返回给用户



核心线程分工：

| 线程类型           | 核心职责                                       |
| ------------------ | ---------------------------------------------- |
| Tomcat工作线程     | 接收用户HTTP请求、发起异步IO调用、释放回线程池 |
| IO线程（selector） | 专门管理多个IO连接，检测哪些连接有结果返回     |
| 回调线程池线程     | IO线程检测到结果后，执行回调逻辑               |

一般异步http客户端会启动专门的IO线程，这个线程通过epoll监听所有已发起的IO连接，会把所有待返回的连接注册到selector上然后进入等待状态（不阻塞，是内核级的监听，CPU几乎无消耗），当连接就绪内核会通知selector有数据，IO线程去读取数据然后把结果交给回调线程池



**不要用tomcat线程去做IO管理**

如果让tomcat工作线程去监听IO，线程被占用无法处理新请求



另外建议无论哪种异步框架（JDK的CompletableFuture、OkHttp）都不要依赖默认的回调线程池，必须显式指定自定义的回调线程池，根据自身业务场景选择合适的线程池参数



daas伪异步，其实是同步http请求+线程池异步执行，本质上http请求还是同步阻塞的只是把阻塞的同步请求丢到了线程池里执行，改用apache asynchttpclient异步回调，这样我们的线程池也不阻塞了，该客户端基于IO多路复用技术，底层直接依赖Java NIO实现IO操作，而java nio在linux下的底层实现就是epoll系统调用，windows下是IOCP



**多路复用技术逐层解析**

1. 应用层 CloseableHttpAsyncClient

Apache封装的异步http客户端，对外提供简介的异步API，内部封装了所有底层IO逻辑

- 启动少量IO线程，默认CPU核心数*2，专门负责管理所有http连接的IO事件
- 这些IO线程不处理业务逻辑，只监听连接，读取写入数据，和业务解耦

2、JVM层Java NIO

CloseableHttpAsyncClient底层依赖Java NIO实现，核心用到：

| NIO核心组件   | 作用                                                         |
| ------------- | ------------------------------------------------------------ |
| selector      | 一个selector监听多个socketchannel的IO事件，对应管理多个http连接 |
| socketchannel | 非阻塞的socket通道，发起http请求时不阻塞线程等待响应，注册到selector后返回 |
| selectionkey  | 标记socketchannel注册到selector的时间类型，IO线程通过key判断连接有就绪事件 |

IO线程循环执行selector.select方法，该方法不阻塞线程，而是让内核监听所有注册的连接，只有当至少一个连接就绪，内核才唤醒线程，线程再处理就绪的连接

相比同步代码里的httpclient.execute让线程阻塞在socket.read，异步模式下IO线程仅在selector.select清理等待

3、内核层 操作系统系统调用

Java NIO 的`Selector`在不同操作系统下，会调用对应的内核级 IO 多路复用接口：

- **Linux 系统**：`Selector`底层调用`epoll`系统调用（携程服务器几乎都是 Linux，这是核心场景）；
- **Windows 系统**：调用`IOCP`（IO Completion Port）；
- **macOS/BSD 系统**：调用`kqueue`。

epoll的优势：

- 相比传统的select/poll，epoll没有连接数上线，适合高并发场景
- epoll是事件驱动，无需遍历所有连接

java nio与epoll

- selector.open 内核创建epoll实例
- socketChannel.register 调用epoll_ctl将socket FD 注册到epoll实例
- selectot.select 调用epoll_wait内核监听就绪事件

#### 7.3 fallback机制

在远程服务调用（如SOA、微服务RPC、HTTP调用）领域中，Fallback（降级/兜底）机制是一种核心的容错策略，即当远程服务调用出现异常（超时、熔断、服务不可用、网络故障）时，不直接抛出异常或返回错误给上层业务而是执行预设的兜底逻辑，返回一个可预期的备用结果以此来保证整个系统的稳定性和可用性



RPC中不可避免会遇到各种异常：

- 服务端宕机、网络分区
- 调用超时
- 服务被熔断，sentinel/hystrix检测到服务错误率过高，暂时切断调用
- 服务限流，接口qps达到阈值



如果没有fallback：

- 前端页面报错、用户体验差
- 异常层层传递引发雪崩
- 核心流程中断，比如订单支付依赖的积分服务故障导致支付失败

而fallback机制能接住这些异常，比如：

- 积分服务故障时，fallback返回0积分，不影响支付核心流程
- 酒店价格服务超时返回缓存中历史价格，保证页面能正常展示
- 机票库存服务不可用，fallback返回暂无库存，而非页面500错误



**fallback机制**

1、静态兜底

调用失败返回固定的静态值

2、缓存兜底

调用失败时返回本地缓存/redis中的历史数据，比静态值更贴近真实业务，携程的主流方案

3、降级调用

调用失败时降级调用“简化版”服务或备用服务，适合核心流程不能返回静态值的场景



**fallback与熔断、限流的关系**

fallback常和熔断、限流配合使用，构成完整的容错体系：

熔断触发fallback：避免持续请求故障服务



保障核心流程（下单、支付）可用
