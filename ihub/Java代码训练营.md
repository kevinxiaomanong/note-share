### 2024-10考试复盘

1、线程池规范定义 自定义 而不是ThreadPoolExector 里面默认的最大线程数是Integer.max



2、一套代码不应该区分测试环境还是生产环境，如业务上真有所差异，也应该以不同环境的配置来驱动功能而不是在代码上写死环境





3、异步使用规范：

- 警惕假异步 即异步调用之后立即get
- future.get必须加超时时间 有线程卡死的风险 
- 异步必须使用自定义线程池 禁用ForkJoinPool 公用线程池会导致雪崩效应 这也是为什么不建议用parallelStream
- 异步必须处理异常
- 禁止在异步里套用异步 高并发会死锁



异步的最佳实践应该是：当前线程不需要立刻拿到结果，或者你想让当前线程解放回去干更重要的事（例如Tomcat线程、Netty线程）

实践：并行执行多个任务、后台异步执行（日志、埋点、通知）、响应式编程全链路异步





4、重构的major

方法圈复杂度过大，try-catch过大，魔数判断，常量维护，方法内部逻辑职责不单一（例如在get方法内部去做update/insert这种）

特别是一个大的try-catch里面还把exception给吞了，如果真的线上有问题排查起来是很痛苦的



5、循环体里面去做RPC

如果传值不对 例如不小心传了一个1000元素大小的list，可能就要调用1000次，请求放大风险



6、不建议用pair 可读性很差 很模糊 用对象定义



7、查询参数/sql 都不要用字符串拼接，可以创建对象序列化或使用client模块 url应该配置化，不同环境下域名不同



8、明文token 挂kms



9、一些不必要的开销：

例如json转换的new ObjectMapper 例如RestTemplate这种



10、ForkJoinPool的使用场景

专门用于分治计算、CPU密集型、任务能拆解的线程池，思想是分治，先把大任务fork成小任务，然后等小任务执行完合并结果，工作窃取（自己任务结束后可以去做线程队列尾部的任务）



11、SimpleDateFormat

是线程不安全的，如果每次方法内去new又很性能浪费，建议用DateTimeFormatter去定义静态变量

如果是老项目，不能用JDK8的，那就建议用ThreadLocal，避免线程安全问题



12、服务端代码和展示层分离，不应该在后端去出现类似html的标签



13、e.printStacktrace生产禁用

这个会越写越大 直接到标准输出流 会把disk打爆 并且这个是同步阻塞IO 写到日志框架

9、策略模式重构

把不同的算法/处理逻辑封装成独立的策略，干掉大量if/else 或是switch，并且这些逻辑未来会不断增加

可以用策略模式消除冗长的条件判断

策略模式+工厂模式







10、为什么不建议用sleep做限流 RateLimiter

sleep只是单线程减速，且阻塞当前业务线程，无法管控，只是拖延时间不是流量控制

可以通过RateLimiter去本地单机限流 通过令牌桶/漏桶算法

如果单机限流不够，可以用分布式限流

或者对于DB、第三方调用 可以单独自定义小线程池



11、不要外部契约与内部逻辑强耦合

扩展性很受限，且一旦外部契约升级或接口切换改动困难

建议外部数据封装一层代理类统一访问



12、递归的写法是不建议的 风险很大 即使要写也应该明确终止条件且尽量前置

递归很容易死循环





13、函数方法重构-深层嵌套 大量if-else 大try-catch

卫语句 逐层提前return 策略模式消除大量if-else

深层嵌套：一个方法干了参数校验、业务计算、入库、发消息等所有事情，应进行单一职责拆分，一个方法只做一件事，去拆成多个独立的小方法

超大catch：一顿不同异常混在一个catch （exception e）会吞异常，无法对不同异常做不同处理，做细粒度try-catch，或是自定义业务异常+全局异常处理器，业务直接抛异常给@restcontrolleradvice全局捕获，尽量精准捕获



14、金额相关用bigdecimal



15、bit位操作问题



16、线程池规范

对业务应建立统一线程池，不应在方法里重复创建，此外queue.size动态会导致不可控

无拒绝策略，核心线程数为0，无界队列

队列长度很讲究，如果太大会导致线程不够请求积压，线程数没法扩容，如果太小可能导致频繁触发拒绝策略





17、过期/无用代码清理



18、资源流保证关闭，尽量避免手搓，用成熟框架/组件



19、文件流处理

用byte-buffer去读写，而不是直接把文件赛进去

即直接用文件的大小去创建一个buffer 这是很想当然的写法 实际上文件大小不可控

存在OOM风险，应该设定一个固定大小的缓冲区 去批次读写

























### 2025-08复盘

1、@transactional

Spring提供的声明式事务，底层基于AOP动态代理

- 拦截加了注解的方法
- 方法前开启事务
- 正常执行提交
- 抛出异常回滚



生效条件：

1. 注解必须加在public方法上
2. 必须通过SpringBean调用，不能this.xxx()内部自调用
3. 底层用Spring事务管理器
4. 异常必须是RuntimeException/Error才默认回滚 （生产配）



核心配置：

事务隔离级别，对应数据库SQL标准，默认可重复读

事务传播机制：默认用required，有事务就加入，没有就新建



不要吞异常try-catch 不往外抛



AOP代理实现

- JDK动态代理 要求目标类必须实现接口
- cglib动态代理 目标类不用实现接口，底层通过继承目标类，生成子类实现

springboot强制用cglib



aop不改原类代码，而是生成一个代理包装对象，所有的事务、切面都在代理对象上生效



cglib失效：

1. private方法不能被重写
2. a() 被外部调用 走代理对象，但自调用是原生普通对象，绕过了代理，可以通过自注入或是aopcontext.currentProxy
3. static/final
4. 异常被吞





2、用动态线程池

不应仅仅在初始化线程池去读配置，而应去监听qconfig配置修改，去实时set



3、bigdecimal

在除法时需要指定进位规则，否则在除不尽的时候会抛异常

使用规范：

业务统一封装金额工具类，金额使用BigDecimal+string初始化，所有运算指定小数+舍入模式

加减乘 不会出现无限小数 但除法可能 因此必须显式指定 舍入模式 否则一旦除不尽会抛异常

舍入模式：

**HALF_UP** 四舍五入（最常用，日常金额、账单）

**FLOOR** 向下取整（直接截断，抹掉后面小数）

**CEILING** 向上取整（多收不少收，计费、阶梯收费）

**HALF_EVEN** 银行家舍入（金融对账、利息，避免统计偏差）



bigdecimal比较要用compare

前端传金额用字符串，避免前端浮点精度丢失
