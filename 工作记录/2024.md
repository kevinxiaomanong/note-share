**对于mr时the source branch must be rebased onto the target branch的理解**

其实本质是两个分支存在不同步或是代码冲突的原因，推荐做法如下：

首先从源分支切换到目标分支，然后从远程拉取目标分支的最新代码，接着切换回源分支对目标分支进行rebase变基，主要是使得我们在源分支上做的修改能够作用到目标分支上，期间可能存在冲突我们需要解决，解决完后可以将源分支上的修改进行push，然后就能顺利创建merge 。

**思考点：**

- 我们在做UT的时候 对于被测类是不mock或是spy的 这些是为了模拟外部依赖对象才需要的
- 如果你想mock静态方法的依赖，需要使用powermockito框架，因为mockito是通过继承的子类去覆盖父类的方法来实现，但是静态方法是不能被覆盖的，powermockito是基于字节码技术来进行修改的
- powermock静态方法时 特别注意 模拟抛出异常时 静态方法返回值为空和方法没有定义异常的特殊情况，需要用doThrow和抛出运行时异常来解决

**GPT：**

这是一种常见的前后端集成方式，前端代码进行修改后通过构建工具的处理生成静态文件，这些静态文件

放在resource/static目录 这样后端服务器就可以直接提供这些静态资源



而在前后端分离项目里 前端和后端项目独立开发和部署 

前端代码构建后会部署到一个静态资源服务器上 例如Nginx

后端项目部署到应用服务器如Tomcat、Jetty，直接运行在jvm上

前端服务器配置反向代理到后端服务器，这种方式可以实现跨域请求，还可通过Nginx的负载均衡提升性能

通常nginx会将所有静态资源请求从前端构建目录提供，而将`/api`开头的请求代理到后端服务器



特别注意的是，前端项目运行的时候有mock数据的概念，你需要看哪些是mock的，通常状态码会为304not modify



其实在我们这个场景下 是不需要的 因为resource/static和web项目是同步的 关心好接口实现即可

工作原理：

通过字节码操作，在编译时对代码进行修改，具体来说会在方法内部捕获所有的受检异常并重新抛出这些异常

典型应用场景：

简化测试代码、lambda表达式（如果lambda表达式中的代码抛出受检异常会导致编译错误！！可以使用这个来解决问题）、简化反射调用（反射的api会抛出多种受检异常）、异步任务处理异常

今天先看下context path:http://docs.fx.ctripcorp.com/docs/soa/how-to/gov-service/service-config/context-path

得到的信息是Context Path主要用于服务端启用Service Mesh，用于实例注册，如果配置错误会导致服务端实例拉出，客户端访问失败

升级framework bom至最新版本，升级后service mesh会根据SDK上报的Context Path值自动获取，服务端不需要配置Context Path

Context Path是由三部分组成：/{Captain Group Context Path}/{Servlet Path}/{Service Path}

1、Captain Group Context Path 集群管理 基本信息下有Context Path
