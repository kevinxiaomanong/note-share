## **海外目的地营销看板**

**项目介绍**： 针对沙特、迪拜等海外旅行目的地方在我司各站点的营销活动投放，为了更好地反馈其营销活动的数据表现，开发了一套涵盖多维度旅行指标的营销数据看板，包含搜索下单趋势、长短线竞对目的地、酒店竞争系数、跟团游产品均价等指标。

**主要工作**

•***\*本地缓存引入\****：针对公共 StarRocks 集群高峰期查询超时问题，设计 Caffeine 本地缓存降级方案，接口失败时自动回退最近成功结果，并监听 ApplicationReadyEvent 实现启动时异步预热本地缓存，保障看板高可用。

•**翻译接口对接**：设计 LLM 产品名离线翻译的异步容错方案：翻译任务提交时即落库（requestId + PENDING），消费端按 requestId 更新翻译结果，并新增 QSchedule 定时补偿任务扫描超时未完成的 PENDING 记录并重新提交，避免消息丢失导致翻译结果缺失。

•***\*生产 OOM 排查与解决\****：生产多次出现 "k8s docker events oom occured!" 告警，发现分代 ZGC 垃圾回收算法对堆外内存的占用相对较多， 在容器内存配置较低的情况下容易出现 Docker OOM，改用 G1 GC 算法后大大降低了 OOM 频率。

•***\*Excel 导出优化\****：将 七路 DaaS 接口调用由串行改为 CompletableFuture 并行编排，补充 orTimeout 超时兜底防止线程泄漏；结合 Java 21 虚拟线程替换自定义线程池，I/O 等待时虚拟线程自动从载体线程卸载，有效并发上限从固定线程数提升至内存容量级别。

### **### 1、审批流状态机**

审批流状态机重构：将数据外发合规审批从强耦合代码重构为显式有限状态机（ApprovalEvent 事件枚举 + Guard/Action 转换规则 + 嵌套 Map 转换表），6 类角色流转路径单表可览，新增审批节点只需增行配置。

***\*核心设计-三个概念\****

1、ApprovalEvent，事件枚举，代表发生了什么，有需求提交、审批节点通过/拒绝、需求撤销、需要补充信息等

2、StateTransition，转换规则，有三个要素：目标状态、Guard进入条件、Action副作用，这里用工厂方法封装了几种常见形式：StateTransition.to 和self 分别表示有条件地跳到新状态和自转换

3、DemandStateMachine，转换表本身，是个Spring Bean，@PostConstruct的时候把所有规则注册进去

即某个状态下，遇到某事件，会如何转换，注意这里某状态遇到某事件可能根据条件有多条转换规则，比如当需求处于审批中状态下，遇到审批节点通过这个事件，那要看首先当前环节下有没有其他角色没审批完，然后看还有没有下一环节，如果这个审批节点通过后所有环节都过了，那才转换到审批通过状态

机器对外只暴露一个方法：fire(当前状态、遇到什么事件、当前上下文)

然后状态机内部执行时，就是按顺序遍历规则，第一个符合条件的规则胜出，执行它的action，如果当前状态下没有注册这个事件，那就直接抛异常，说明是违法流转

***\*数据结构\****

首先状态机的核心是一张嵌套的Map<DemandStatusEnum, Map<ApprovalEvent, List< StateTransition > > 

读法是当前状态-->收到什么事件-->按顺序尝试哪些规则

然后是这里StateTransition对象，是一条规则，里面有Condition即满足什么条件用于匹配，如果为null表示永远匹配，还有targetState，即要转到哪个状态，如果为null表示这条规则状态不变，还有action字段，表示要做哪些行为，例如发通知等等，这个Action和Condition我们用的函数式接口实现，前者返回void后者返回boolean

然后有match方法

这里还有一个数据结构即：审批上下文，这里存的就是需求的一些元信息、当前审批节点元信息、基本都是final的，还有一个nextApprovers非final属性，因为在guard阶段要判断下一节点有没有审批流，这里正好action节点需要用，防止重复计算

状态机的fire方法逻辑:

\```

​    @SneakyThrows

​    public DemandStatusEnum fire(DemandStatusEnum current, ApprovalEvent event, ApprovalContext ctx) {

​        List<StateTransition> candidates = Optional.ofNullable(table.get(current))

​                .map(m -> m.get(event))

​                .orElse(Collections.emptyList());

​        if (candidates.isEmpty()) {

​            throw new BadRequestException(

​                    String.format("非法操作：当前状态 [%s] 不支持事件 [%s]", current, event));

​        }

​        for (StateTransition t : candidates) {

​            if (t.matches(ctx)) {

​                DemandStatusEnum next = t.fire(ctx, current);

​                if (next != current) {

​                    ctx.getDemand().setStatus(next.name());

​                    demandDao.update(BaseUtil.getHints(), ctx.getDemand());

​                    log.info(String.format("demandId=%s 状态流转: %s → %s", ctx.getDemand().getId(), current, next));

​                }

​                return next;

​            }

​        }

​        // 理论上不会走到这里：NODE_PASSED 链最后有 null-guard 的 fallthrough

​        throw new IllegalStateException("无匹配规则，状态=" + current + " 事件=" + event);

​    }

***\*有限状态机FSM\****

有限状态机是计算理论最基础的建模工具之一，用来描述“一个系统在任意时刻只能处于有限个状态之一，并只能通过预先定义好的方式在状态之间跳转”，它由三个核心要素组成：

\- 状态集，系统所有可能停留的位置

\- 事件集，驱动状态发送跳转的输入

\- 转换函数-即给定现在在哪个状态、收到了什么事件、确定接下来跳到哪个状态

但我们用的是带守卫条件的扩展版FSM，我们某个需求的审批状态 可能包含多个节点  这是因为同一个状态同一个事件，但根据具体数据条件走向不同分支这种需求在业务流程里非常常见

在业界这通常叫做“带守卫条件的转换”或者“扩展状态机”

首先我们需要把审批节点状态的流转和mq消息的发送绑在一个事务里，但改数据库和发消息是两个独立的物理操作，没法用一个原子操作同时搞定，二者间必然有一个间隙，这个间隙里发送任何意外-进程崩了，网络抖了，MQ broker不可用了，都会导致审批节点改了但消息没发出去，或者消息发出去了，事务却回滚了

因此不同于Kafka的分布式事务，qmq做的是本地事务，即把发消息这个动作降级成往本地一张表里插一条记录，这个insert和业务update用的是同一数据库连接、同一个事务，这样利用数据库原生事务保证，至于消息有没有真正送到MQ broker，这件事被推迟到事务提交之后，交给一个独立的、不再这次HTTP请求里的东西去做，这就是补偿Job的职责

另外要注意消费语义：一般有至少一次，至多一次和精确一次

QMQ默认提供的是至少一次的语义，这是所以可靠消息队列的通用语义，意味着在某些场景在可能会导致重复消费，即在补偿任务里mq的send成功但改消息表状态的时候有问题，因此可能下一轮轮询又会把它捞出来重复发送一次

***\*mq消费失败\****

qmq是拉模式的消费，即consumer主动去broker拉消息，不是broker推送，一般一条消息处理失败（消费方法抛异常、或者没有在超时窗口内ack）qmq的典型行为是延迟重投，间隔逐步拉长，超过配置的最大重试次数后，转入死信队列，等人工介入或走补偿工具重新投递

QMQ 是拉模式的消费(consumer 主动去 broker 拉消息,不是 broker 推给你),这个模式下,一条消息处理失败(消费方法抛异常、或者没有在超时窗口内 ack)之后,QMQ 的典型行为是:

1. 这条消息不会被当场丢弃,也不会被标记为"消费完成"
2. 但也不会立刻重投给同一个消费者反复死磕——否则一条坏消息会把整条队列堵死,后面排队的消息全部卡住
3. 实际做法是延迟重投,间隔逐步拉长(典型模式是退避式的:比如第一次失败后隔几十秒重投,再失败隔几分钟,再失败隔更久),这期间消费者会继续正常处理队列里其他的消息,不受影响
4. 超过配置的最大重试次数之后,这条消息才会被转入死信队列(DLQ),自动重试在这里

qmq有消费重试机制，默认次数为32次，如果消费逻辑抛了异常会触发消息重发，如果次数用尽，消息会进入死信队列，所以我们redis key的TTL配置一个能覆盖重试的时间即可，默认1h

然后会返回一个uploadId 

第二步，我们去循环上传分片

每片固定，然后带上分片序号+uploadId 调用uploadpart接口，nephele按uploadId+partNum存起来

第三步：通知合并

所有分片传完后，调complete接口告诉nephele分片都齐了，顺序拼成完整文件，会返回一个最终文件的访问URL

***\*为什么要分片 不直接传整个文件\****

如果一次HTTP请求把几百MB的字节流塞进请求体

\- 网关/代理对单次请求体大小、超时时间有限制，大文件很容易触发

\- 一个大请求失败，就要从头重传整个文件，代价很高

\- 服务器要一次性在内存里接住整个文件体，内存压力大

切成固定大小的小块后，每片都是一次独立、轻量的http请求，单片失败只是重传这一片

***\*CRC\****

我们没有对整个文件内容做完整性校验，文件超过10mb时只用头5MB+尾5MB算MD5，只是一种抽样指纹，不是严格的完整性校验，这个指纹算出来后放进Crc请求头，每片上传时带同一个值传给Nephele，来做秒传/去重识别，如果同一个文件内容，头尾文件一样，服务器可以直接复用已存储的内容，不用重新接收

***\*问题\****

1、分片上传失败没有任何处理 

2、分片是顺序上传，没有利用并发

分片协议本来一个很大的优势就是各片之间互相独立，理论上可以并发上传，大幅缩短大文件的耗时

3、CRC指纹没有完整，做了性能换精度的合理妥协

***\*前端直传 vs 后端中转\****

很多系统实际做法是两种方式缝合：

1. 前端先调后端一个申请上传接口 后端做类型校验、状态校验、权限校验，校验通过后生成一个预签名URL
2. 前端拿着URL直接文件字节传给Nephele
3. 上传完成后，拿到返回的文件URL，再调后端的确认上传完成接口

这样业务校验和元数据落库没问题，并且占内存、占网络带宽的大文件传输完全绕开后端

不然其实整个文件一次性读进JVM堆内存，如果同一时刻几个用户都传大文件，很容易把JVM堆打爆，触发Full GC甚至OOM

### **### 4、系统架构升级**

***\*Shared-nothing架构\****

核心思想：每个节点都是完全独立的，有自己的CPU、内存、磁盘，节点之间不共享任何物理资源，只通过网络通信。

数据分布规则：按照哈希等规则切片到各节点，每个节点只拥有自己那部分数据的物理文件，查询某条数据时必须先知道它在哪个节点，再去那个节点上找，

CK里有分布式表Distributed Table，按分片键路由

优点：没有共享资源的锁竞争平均，MPP并行计算效率高，但存储与计算绑定，想加计算能力就得加存储，且扩缩容麻烦，数据要rebalance，期间存在大量网络IO，且为了容灾每份数据存多份完整副本

而且Shared-Nothing可能由于数据倾斜带来热点分片问题，可能某个热点分片导致单节点的CPU/磁盘IO被打满，其他节点帮不上忙

***\*Shared-Disk架构\****

计算节点和存储节点彼此独立，所以计算节点共享访问同一份远端存储，计算节点本身不持久化数据，是无状态的

数据分布：数据统一存在共享存储HDFS/S3，不属于任何一个计算节点

代表：StarRocks External Catalog + Iceberg

优点：计算和存储独立扩缩，存储不够就加磁盘，算力不够就加计算节点，秒级扩容，且计算节点无状态可以随时快速弹性扩缩，但缺点是计算节点每次需要跨网络读存储层，有网络IO开销（SR默认开了Data Cache）存储层如果扛不住高并发元数据请求，容易变成瓶颈



**迁移方案思路**

这个问题要分两层回答：一层是"迁移策略怎么做"（这是通用的工程方法论，跟具体代码无关，可以放心讲），另一层是"这次迁移具体验证了什么"（这部分要结合你们系统的真实约束，但不用深挖代码细节）。下面给你一个完整的面试回答脚本。

---

开场：先定调——这不是一次性切换，是渐进式双跑

▎ 这种体量的架构迁移（6000+ 埋点、日增百亿级数据），不可能做"大爆炸式"的一次性切换——风险太大，一旦出问题影响的是全集团的分析师和下游报表。我们采用的是渐进式双写双跑策略，核心思路是：新架构先建起来、新老并行跑一段时间互相校验、确认结果一致后再逐步把流量切过去、最后老架构退役。整个过程分四个阶段。

---

阶段一：新链路建设，但不承担线上流量

▎ 第一步是把 Iceberg + StarRocks/Trino 这条新链路从零搭起来，但完全不影响老的 Hive+ClickHouse 链路对外提供服务。这个阶段要解决的核心问题是：怎么让新埋点的注册流程既能喂给老架构（继续写 ClickHouse），又能同时喂给新架构（写 Iceberg），这意味着埋点注册/上线这一侧的元数据生成逻辑要做成"双发"的，一份配置信息同时驱动两条下游管道建表。
▎
▎ 这个阶段最重要的是先选一批低风险的埋点做新架构的试点，不是上来就全量切。试点对象通常是新建的埋点（没有历史数据负担，天然就该走新架构）或者流量很小、出问题影响面可控的埋点，不会一开始就拿核心业务埋点练手。

---

阶段二：双跑校验——这是整个迁移里最关键、最容易被低估的环节

▎ 新链路跑起来之后，不能直接信任它的结果，必须拿同一批数据、同一个时间窗口，新老两套链路各算一遍，比对结果是否一致。比对的维度至少包括：
▎
▎ - PV/UV 等基础聚合指标是否一致——这是最基本的正确性校验，如果连简单聚合都对不上，说明解析逻辑或者过滤条件哪里出了偏差
▎ - 数据量级是否一致——老架构是 T+1 批量写入，新架构是近实时写入，统计同一天的总条数，理论上应该收敛到同一个数字（允许极小的边界误差，比如跨天写入的边界数据）
▎ - 字段级的数据分布是否一致——不只看总量，还要抽查具体参数的空值率、枚举值分布，防止新链路的解析逻辑在某些边界字段上出了细节偏差（比如布尔类型、嵌套字段这类复杂结构，最容易在两套解析逻辑里出现不一致）
▎
▎ 这个阶段要跑足够长的时间（建议至少跑过一个完整的业务周期，比如覆盖到周末和工作日的流量模式差异），而不是跑一两天看着数字差不多就结束。迁移里出的问题，往往不是在第一天暴露的，而是在某个特殊的边界场景（大促、版本发布、某个异常数据）才会暴露，双跑时间不够长，很多隐患会被带到正式切流之后才爆发。

---

阶段三：灰度切流——分批次、可回滚

▎ 校验通过之后，开始把查询流量从老架构切到新架构，但不是一次性切完，要分批次灰度：
▎
▎ - 按 BU/按业务线分批，而不是按时间一刀切全量用户——这样如果某个 BU 的数据结构有特殊性没被覆盖到，影响范围只限于这一个 BU，排查和回滚都更容易定位
▎ - 保留快速回滚开关——查询路由层要做成可配置的，一旦发现新架构某个场景有问题，能迅速把这批流量切回老架构，而不需要代码发布
▎ - 灰度期间保持双写，不能新架构切完就立刻把老架构的写入链路关掉，因为万一需要回滚，老架构的数据不能是断档的

---

阶段四：历史数据回填 + 老架构退役

▎ 新架构稳定承接增量流量之后，还有一个经常被忽略的问题：历史数据怎么办。分析师经常需要看"去年同期对比"这类长周期数据，如果新 Iceberg 表只有切流之后的数据，没有历史数据，这类分析直接做不了。所以需要有一个历史数据回填的工作，把 Hive 里存量的历史数据按新架构的表结构重新转一遍灌进 Iceberg，这个工作量不小，因为老数据的 schema 和新 schema 不一定完全对得上（尤其是经历过多次参数变更的埋点，历史数据可能对应着好几个版本的 schema）。
▎
▎ 等历史数据回填完成、新架构稳定运行一段时间（建议是能观察到至少一次月度大促或版本发布高峰、确认没有隐藏问题）之后，才真正可以着手下线老架构——包括停掉每天的 Hive→ClickHouse 同步任务，退役 ClickHouse 集群。

---

需要特别注意的几个点（面试官追问大概率会问这些）

1. 查询引擎的 SQL 方言差异，是最容易被低估的坑

ClickHouse、Trino、StarRocks 三者 SQL 方言不完全兼容——函数名不同（比如正则匹配、数组操作的内置函数名）、字符串类型处理不同（Trino 没有传统意义的 string 类型别名，用 varchar）、标识符引号风格不同（反引号 vs 双引号）。迁移时所有动态生成 SQL 的逻辑都要过一遍方言适配，这是纯体力活但极易漏掉边界情况，建议专门写一层方言转换，而不是在每个业务方法里散落着写 if-else 判断引擎类型。

2. JDBC 驱动行为差异比 SQL 方言差异更隐蔽

即使 SQL 语句本身写对了，不同引擎的 JDBC 驱动对同一个 ResultSet 方法的实现行为可能不一致（比如某个驱动对特殊数值 NaN/Infinity 的处理方式）。这类问题往往只在生产环境遇到边界数据才会暴露，建议迁移时专门针对"异常值/边界值"场景做一轮有针对性的测试，而不是只测正常数据。

3. 元数据驱动的 Schema 变更链路要同时兼容新老两套下游

迁移期间，埋点参数变更（新增字段）这个动作，要同时驱动老架构的 ClickHouse 建表变更和新架构的 Iceberg 建表变更，这两条链路的字段类型映射规则不完全一样（比如同一个布尔类型字段，老架构可能映射成数值类型，新架构可能出于兼容性考虑映射成字符串），这个阶段必须保证两条链路都不出错，任何一条断了都会导致数据丢失或者分析报错。

4. 消费端（下游调用方）必须做到无感知

查询路由这一层要对上层完全透明——不管是双跑阶段的内部比对，还是灰度切流阶段的逐步切换，所有的"该走哪个引擎、该查哪个数据源"的决策都应该收敛在一个统一的路由层，业务代码不应该感知到底层是老架构还是新架构。这不仅是为了代码整洁，更是为了灰度切流和快速回滚的能力能真正落地——如果路由逻辑散落在各处，想做灰度/回滚会变得极其困难。

5. 双跑阶段的基础设施成本要提前规划

新老两套集群同时跑，意味着这段时间的基础设施成本是翻倍的——不只是存储翻倍（这是显而易见的），计算资源、运维人力也是双倍投入。这个阶段的时间窗口不能无限拖长，需要提前定好"双跑多久、校验到什么标准就可以切流"的量化标准，否则容易出现"一直在双跑、迟迟不敢切"的拖延状态，反而让迁移成本持续失控。

---

一句话收尾

▎ 整个迁移的核心原则是：新链路先在无风险的边界试点，用双跑互相校验建立信任，再分批灰度切流并保留回滚能力，最后处理历史数据和退役老系统——每一步都是可验证、可回滚的，而不是一次性"赌一把"式的切换。真正的风险不在于技术选型对不对，而在于迁移过程中有没有给自己留足"发现问题就能退回去"的安全网。

---

补充说明：这个回答的框架是基于通用的大型存储迁移方法论（渐进式双写、分阶段灰度、可回滚设计），结合你们系统已经确认的架构事实（新老并存期、元数据驱动建表、双引擎路由抽象）组织起来的，不是对代码里具体迁移脚本的逐行复述——你说得对，这类"迁移怎么做"的问题，答的是工程方法论和风险意识，不是代码细节

***\*虚拟线程池\****

这是一个非常经典的纯IO密集型场景，虚拟线程可以让线程池参数问题直接消失

直接Exectors.newVirtualThreadPerTaskExecutor

这样阻塞不再消耗载体线程，等待Dass接口返回时JVM会把虚拟线程从载体线程上卸载

并发的上限从线程池大小变为内存，虚拟线程的开销很小

并且不再需要拒绝策略

虚拟线程对Synchronized块有问题，虚拟线程在同步块内无法卸载，JDK25修复

这不会使得单次请求响应时间变块，收益体现在资源消耗和并发容量上，

有效降低内存占用，提升吞吐

***\*爬虫过滤的SQL陷阱\****

问题：上线爬虫剔除功能后，某些分析场景返回空结果，但相同条件不剔除爬虫时有数据

排查过程

原始写法用了 NOT IN：

WHERE uid_value NOT IN (

​    SELECT division_id FROM hive.ctripdi_prodb.dwd_ab_crawler WHERE d = '...'

)

SQL 是三值逻辑（true / false / unknown），WHERE 只保留 true 的行。当子查询里 division_id 存在哪怕一条 NULL，x NOT IN (..., NULL) 的结果是 UNKNOWN，整个 WHERE 返回空集。爬虫表有 7700 万行，脏数据概率不低。

解决方案

改用 Anti-Join 模式（LEFT JOIN + IS NULL），不受 NULL 影响：

LEFT JOIN hive.ctripdi_prodb.dwd_ab_crawler t_crawler

​    ON t1.uid_value = t_crawler.division_id AND t_crawler.d = '...'

WHERE t_crawler.division_id IS NULL  -- 只保留不在爬虫表里的

同时性能也更好：OLAP 引擎对 LEFT JOIN 有专门的 Hash Join 优化，小表（爬虫表）建 Hash Table，大表 probe，比 NOT IN 子查询快。

***\*Anti-Join\****

反连接语义：返回左表中右表里没有匹配行的记录，和Inner Join正好相反

项目场景：从埋点数据里剔除爬虫用户

NOT IN的NULL陷阱：SQL用的是三值逻辑：true/false/unknown，而不是普通的布尔值，where子句只保留结果为true的行，而任何值与NULL比较，结果都是UNKNOWN

not in 展开后 是一串<>的AND，因此只要爬虫表里有一条division_id=NULL的脏数据，not in都会是空集，没有任何数据

LEFT JOIN + IS NULL：先做连接，匹配不上的行右侧全填NULL，再用where b.key is null 删除没有匹配的行，NULL只是连接失败的标记

LEFT JOIN的写法 SR有向量化的Hash Anti-Join实现 性能可预期
