# Java相关



































String：

怎么理解String中的对象是不可变的呢？



**stringbuffer和stringbuilder**

只是用于构建可变字符序列的工具类，而非string的可变版本，最终若要得到string对象，仍需调用tostring创建新的不可变string对象，Stringbuffer是线程安全的，方法加了synchronized，性能较低





其不可变指的是一个string对象一旦被创建，它底层字符序列（内容）就永远无法被修改，任何看似修改String的操作本质都是创建了一个全新的string对象，这是JDK源码层面的设计：

1、底层用字符数组实现，被private+final修饰

private:外部类无法直接访问value数组，只能通过string的方法操作

final：value数组的引用地址不可变，且String类没有提供任何修改value的内部方法

2、String类被final修饰

类被final修饰意味着无法继承，子类无法重写string方法来实现修改原字符串的逻辑

3、所有看似修改string的方法，例如subString、replace、concat都是返回新的string对象，原对象内容完全不变



那么为什么string要这样设计呢？

1、性能优化：字符串常量池

Java为String设计了字符串常量池，目的是复用相同内容的字符串减少内存占用

当创建`String s1 = "hello"`时，常量池会先检查是否有`"hello"`，没有则创建，s1 指向常量池中的对象；

当创建`String s2 = "hello"`时，直接复用常量池中的对象，s2 和 s1 指向同一个地址；

若 String 是可变的：修改 s1 的内容会导致 s2 的内容也被修改，常量池的复用逻辑会完全失效。



2、安全保障

String大量用于敏感场景，不可变保证这些数据在生命周期内不会被篡改，例如数据库连接串、hashmap的key



3、并发安全 不可变对象天然是线程安全的，因为其不可变



**如何理解字符串常量池的数据结构**

首先字符串常量池是JVM为了复用字符串对象、减少内存开销设计的缓存区域，核心是：存储唯一的字符串字面量对应的对象引用/对象本身，保证相同字面量只存一份：

JDK7之后：常量池被移到了堆内存，存储的是指向堆中string对象的引用（而非对象本身），因为堆空间更大更适合存储大量字符串，理解内存分布：



**误区：**

1、常量池里存储的不是字符串字面量这种单纯的字符序列，而是对象引用

2、new string（“hello”）极端情况下会创建两个对象，双引号触发的常量池对象&new触发的堆对象

3、==在java中永远比较的是对象的引用地址，只有equals才比较字符串内容





字符串常量池在JVM中官方名称是String Table，其底层实现是一个固定大小的哈希表Hash Table，其核心设计如下：

| 结构维度   | 具体实现                                                     |      |
| ---------- | ------------------------------------------------------------ | ---- |
| 哈希表的桶 | 数组结构，每个桶对应一个哈希值区间，存储指向字符串引用的链表 |      |
| 哈希值计算 | 基于字符串字面量的字符序列计算哈希值                         |      |
| 查找逻辑   | 计算字面量哈希值定位到桶--遍历桶中的链表对比字面量是否完全一致--找到则返回引用否则创建新对象进入桶 |      |



**HashMap与ConcurrentHashMap**

其实HashMap仍然是开发主力，因为绝大多数业务逻辑是单线程执行，没必要为了线程安全付出性能代价

在多线程仅读的情况下也只需HashMap即可，有写操作才上ConcurrentHashMap

用户线程：由用户空间程序管理和调度的线程，运行在用户空间

内核线程：由操作系统内核管理和调度的线程，运行在内核空间



需要搞懂：

1、Java线程

2、内核线程

3、CPU核心

4、操作系统调度



java启动线程：

例如new Thread().start()，本质JVM调用OS函数，是系统调用，然后OS内核去创建一条内核线程，让JAVA线程和内核线程绑定，由OS统一调度

内核线程是OS能调度的最小单位，真正跑在CPU上，每个线程有自己的上下文（寄存器、栈），os负责创建、销毁、挂起、恢复、分配CPU时间片

一个4核的CPU同一时刻最多跑4个线程 如果线程多就需要OS不停切换让线程轮流上CPU，即线程切换，线程切换需要保存当前线程运行状态、恢复下一个线程、从用户态切内核态切用户态，一次切换几us-几十us，线程越多切换越频繁使得CPU真正用来执行业务的时间越少，系统负载越高接口越慢

为什么要用线程池？创建/销毁内核线程是重量级操作，要进内核分配资源注册os很慢，即创建销毁线程很贵 切换也比较贵 但复用线程很便宜

这也是为什么线程池不能无限大，IO密集型可以设大线程池因为大部分时间在等待不占用CPU，而CPU密集型建议线程数=核心数避免切换让CPU全力计算



虚拟线程：JVM层面的轻量级用户线程，它跑在少量内核线程上，传统内核线程JDK21之前叫Platform Thread，平台线程和内核线程是1：1绑定的，创建/销毁内核线程要走系统调用，每个线程占用1-2mb栈内存，单机最多创建几千个就OOM了，走OS调度，OS调度会需要内核态切换



虚拟线程关键在于智能阻塞，比如执行到阻塞操作，如Thread.sleep、JDBC查询、IO读写时JVM会自动把这个虚拟线程从绑定的内核线程上摘下来，即卸载，让内核线程去跑其他虚拟线程，等阻塞结束再把虚拟线程挂载到任意空闲的内核线程继续执行，由于这个过程完全在JVM用户态完成，没有OS内核态切换，开销很小



虚拟线程的栈内存初始几KB，按需扩容



**虚拟线程 vs 协程**

例如Go里面的协程 也是用户级线程，需要使用异步语法，改造成本高，但Java是同步代码直接跑，JVM自动调度



为什么虚拟线程能这么丝滑地切换呢？

本质是JVM把线程上下文从内核态搬到了用户态管理，切换时只操作JVM内部的内存数据，



注意切换的本质都是保存当前线程上下文-恢复下一个线程的上下文



传统内核线程的上下文存在OS内核的内存空间，包含CPU寄存器的值，内核栈，线程状态

理解线程的状态

2. RUNNABLE
3. WAITING/TIMED_WAITING

其他状态其实很好理解，如何理解BLOCKED和WAITING呢

虽然都表现为线程不执行，但触发原因、等待的资源、唤醒条件完全不同

- BLOCKED：线程抢不到锁，被动等待锁释放（锁资源竞争）
- WAITING：线程主动等通知，主动放弃CPU/锁，等别人叫醒它（线程协作）



线程间协作的api不好记，wait/notify/join这些价值是在实现线程间的协作，关键两个原则：

1. wait/notify/notifyAll 必须在synchronized方法里调用，否则会抛illegalMonitorStateException
2. 调用wait，线程会自动释放持有的锁，被唤醒后需要重新抢锁才能继续执行

**死锁**

多个线程同时被阻塞，程序无法正常终止，因为在等待相互的资源释放

产生死锁的四个必要条件：

1. 互斥
2. 请求与保持 线程因请求资源而阻塞时对已获得的资源保持不放
3. 不剥夺 线程对已获得的资源在未使用完之前不能被其他线程强行剥夺，只有自己使用完毕后才释放资源
4. 循环等待 若干线程之间形成一种头尾相连的循环等待资源关系



通过jstack去检测死锁，比如jstack中通常有：Found one Java-level deadlock

或者有JConsole工具



如何预防死锁？破坏死锁产生的必要条件即可

1、占用部分资源的线程进一步申请其他资源时，如果申请不到就主动释放它占用的资源，破坏不剥夺条件

2、按照某一固定顺序来申请资源，破坏循环等待条件



如何检测死锁？

首选jstack JDK的线程栈分析工具

先jps 找到进程号

然后jstack 会很明确告诉你发现死锁的信息Found one Java-level deadlock



或是JConsole 链接到进程 切换到线程标签页 点击检测死锁即可



**使用多线程的价值&意义**

1、从技术层面

现代计算机的核心特征是多核CPU+IO设备慢，单线程会让大部分硬件资源闲置

- 单线程只能利用1个CPU核心，多线程能让多个核心并行（大数据计算Spark/MapReduce）
- 程序中90%的时候可能都在等IO（等数据库、调接口、读写文件），单线程可能会卡在等待步骤，CPU空转，多线程让等待IO的线程让出CPU，去执行其他有活干的线程（Tomcat处理请求 消息队列消费）

2、从业务层面

技术最终要服务业务，多线程对业务的价值体现在两个核心指标

- 降低响应时间，例如抖音首页加载（多线程同时拉取视频列表、用户信息、关注动态，比单线程依次拉取快
- 提升吞吐，系统能处理更多业务，吞吐量=单位时间处理的请求数/任务数，例如多线程处理订单创建、库存扣减、支付回调，单机支持万级QPS

3、从架构层面

多线程天然适合多任务并行的业务场景，例如微服务的异步线程池（订单创建后主线程返回成功，异步线程处理物流通知、积分发放）



两面性：

技术是没有银弹的

1、多线程开发成本高，要处理线程安全、线程通信

2、线程太多会导致CPU频繁切换，反而让真正的业务执行时间减少，反而会降吞吐

3、多线程的BUG难以复现难以调试



线程数也不是越多越好，IO密集型一般CPU核心数*2-4 CPU密集型一般等于CPU核心数

优先用线程池避免频繁创建/销毁线程，也方便控制线程总数

核心流程用同步、非核心流程用异步，例如订单支付必须同步，短信通知用异步线程



不懂多线程 很难设计高并发高性能的系统



**并发编程的特性**

这是保证多线程程序正确运行的基础

1、原子性 操作不可分割 

2、可见性 即一个线程修改了共享变量的值，其他线程能立刻看到修改后的值

3、有序性 程序执行顺序按照代码先后顺序执行（编译器/CPU可能重排序 需约束）



JMM通过happens-before规则隐式保证有序性：

1. 单线程内前面的指令happensbefore后面的
2. 解锁happens后续加锁
3. 写volatilehappens before读

    public static Singleton getInstance() {
        if(instance==null){
            synchronized (Singleton.class) {

**JMM**

多线程环境下，cpu、缓存、内存的交互存在问题，JMM规范内存访问行为，是java并发编程的底层规范

现在CPU有多级缓存，一般是L1-L3，线程执行时先从主存加载数据到缓存，修改后刷回主存：



JMM抽象的主存基本等于计算机物理内存

而线程的工作内存可以理解为CPUL1 L2缓存+线程私有寄存器

现代CPU架构每个核心私有L1 L2缓存 所有核心共享L3缓存 

主存是所有线程共享的

工作内存是线程私有的，别的线程看不见，JAVA要跨平台，不能直接暴露硬件细节



线程对共享变量的所有操作，必须在工作内存中进行，不能直接操作主存，且不同线程之间无法访问对方的工作内存，变量值的传递必须通过主存，JMM通过内存屏障控制工作内存和主存的交互，保证可见性和有序性

| 问题   | 含义                                                 | JMM 的解决方案                              |
| ------ | ---------------------------------------------------- | ------------------------------------------- |
| 原子性 | 操作要么全部执行，要么全部不执行（不能被中断）       | synchronized、Lock（粗粒度）、CAS（细粒度） |
| 可见性 | 一个线程修改了共享变量，其他线程能立即看到修改后的值 | volatile、synchronized、Lock                |
| 有序性 | 程序执行的顺序与代码顺序一致（禁止指令重排序）       | volatile（禁止特定重排序）、synchronized    |

JMM 的 happens before规则 定义了操作之间的可见性顺序：

1. 同线程内，代码按书写顺序执行
2. 对volatile变量的写 bappens-brefore 读
3. 解锁操作 happens-before 后续对同一锁的加锁操作



能用volatile解决的不用synchronized，原子操作有限用Atomic包（CAS比monitor性能高）

**AtomicInteger**

其原子性核心是基于Unsafe类调用CPU的CAS指令Compare And Swap，通过do-while循环自旋重试的方式，在无锁的情况下保证“读取-修改-写入”操作的原子性，避免synchronized锁开销



其所有原子操作最终都调用Unsafe的compareAndSwapInt方法

```
public final native boolean compareAndSwapInt(Object obj, long offset, int expect, int update);

obj要操作的对象 offset字段在对象中的内存偏移量 expect预期值 update更新值
CAS是CPU的原子指令，核心是比较内存地址obj+offset上的值是不是为expect，如果相等就将该地址的值改为update
返回true否则返回false


    public final int getAndAddInt(Object o, long offset, int delta) {
        int v;

            v = getIntVolatile(o, offset);

    }
do-while自旋重试，直到CAS成功为止
自旋逻辑：
1、读取当前内存中的实际值（volatile保证可见性 每次读取最新的
2、尝试CAS修改，如果失败就一直循环重试，成功则退出循环，且返回修改前的值

```



**Unsafe类**

该类的设计初衷是给JDK内部类使用，是很具安全风险的工具类，是Java访问底层硬件指令，如CAS、内存操作的后门，里面的CAS方法最终通过native调用映射到CPU的CAS指令

Java的CAS核心实现封装在Unsafe中，其CAS方法通过native调用映射到CPU指令



AtomicInteger底层原理就是Unsafe的CAS



**自旋：**

CAS假设大多数情况下能修改成功，如果多个线程同时修改会出现预期值不匹配的情况，此时需要重试，即自旋

它是无锁自旋，传统锁线程抢不到就Blocked等待唤醒，而自旋是CPU空转一直Runnable态的直到成功

一个有上下文切换开销有一个是更多占用CPU资源，因此看并发的场景如果写入多失败场景多用传统锁



但这个只能保证单个变量的原子性，如果需要修改多个变量要用synchronized/Lock

此外存在ABA问题，没有检查值的修改次数，这种情况可以用AtomicStampedReference加版本号字段



do-while的语义 就是至少执行一次 这很贴近该业务场景



synchronized的使用：

1. 修饰实例方法 当前对象实例锁
2. 修饰静态方法 当前class对象锁
3. 修饰代码块 锁指定对象/类

尽量不要使用用字符串，因为字符串常量池有缓存功能



构造方法天然线程安全，但如果里面涉及到共享资源的操作，其内部是可以用synchronized代码块的



底层原理：

可以通过javap去分析字节码，实现底层是monitorenter和monitorexit指令，分别是同步代码块的起止位置

monitorenter质量线程试图获取锁即对象监视器monitor的持有权，每个对象都内置了一个objectmonitor对象

而修饰方法会有一个ACC_SYNCHRONIZED标识，指明该是一个同步方法，JVM回去看是否有static修饰去获取不同的锁，本质都是对象监视器



**对象监视器**

不属于对象内部的实体，而是JVM为每个java对象分配的一块内存结构，在堆里，用于实现锁机制，物理上采用懒加载策略，只有当对象被用作锁时才会真正分配监视器的核心数据结构



```
struct ObjectMonitor{
	Thread* _owner;//当前持有锁的线程
	QueueList _EntryList;//等待锁的线程队列，线程block在此
	QueueList _WaitList;//线程调用wait后进入此队列 线程进入waiting状态，等待被notify唤醒
	int _recursions;锁的重入次数
	int _count; 等待锁的线程计数器
}
```

对象监视器的工作流程：

1. 线程调用synchronized(obj)  去检查obj的Mark Word
2. B如果无锁 即创建ObjectMonitor，Mark Word指向该监视器 若B已有监视器则检查_owner是否为当前线程
3. 如果不为当前线程，则让线程进入entryList队列 进入Block，如果为当前线程可重入，让recursion继续执行

要注意如果有调用wait，会释放锁，让线程进入waitset队列，然后当其他线程调用notify后，才移动到entryList里等待抢锁

因此对象监视器是JVM层面的ObjectMonitor结构体，不是Java对象的成员变量，通过MarkWord指针关联

它是C++实现的结构体，属于JVM内部数据结构，存储在JVM分配的本地内存（OS层面的内存，非Java堆）

Java对象头的Mark Work是连接Java对象和ObjectMonitor的核心，



只有升级为重量级锁时，JVM才会创建ObjectMonitor，轻量级锁仅存储锁记录指针







**锁的一些概念**

1、可重入锁与不可重入

可重入锁也叫递归锁，指线程可以再次获取自己的内部锁，如果是不可重入锁的话重复获取会导致死锁

synchronized和Lock都是可重入的

2、公平锁vs非公平锁

默认非公平锁，抢锁时先CAS直接抢，失败再排队

公平锁：必须排队，按顺序抢锁不允许插队

非公平锁减少了线程切换和队列唤醒的开销，高并发下吞吐更大

3、可中断锁与不可中断锁

线程在等待锁的过程中如果收到中断信号，会不会立即停止等待并抛出InterruptedException



**ReentrantLock**

基于AQS抽象队列同步器实现的可重入互斥锁，AQS是java代码实现，



| 特性       | ReentrantLock                      | synchronized                          |
| ---------- | ---------------------------------- | ------------------------------------- |
| 可重入性   | ✅ 支持（和 synchronized 一致）     | ✅ 支持                                |
| 锁类型     | ✅ 公平锁 / 非公平锁（可配置）      | ❌ 仅非公平锁                          |
| 可中断性   | ✅ 支持（lockInterruptibly）        | ❌ 不支持                              |
| 超时获取锁 | ✅ 支持（tryLock (long, TimeUnit)） | ❌ 不支持                              |
| 条件变量   | ✅ 支持多个（newCondition ()）      | ❌ 仅支持一个（wait/notify）           |
| 手动释放锁 | ✅ 必须手动 unlock（易漏）          | ❌ 自动释放（JVM 层面）                |
| 底层实现   | AQS（Java 代码实现）               | 对象监视器（ObjectMonitor，JVM 底层） |

特别注意ReentrantLock的unlock必须手动调用且必须放在finally中，如果临界区代码出异常，未释放的锁会导致其他线程永久阻塞



简单场景用synchronized，复杂场景用ReentrantLock，高并发优先用非公平锁



使用模版:

```
ReentrantLock lock = new ReentrantLock();
lock.lock();
try{
	dowork();
} finally{
	lock.unlock();
}
```

相比于synchronized，有一些功能上的升级：

1. lock.lockInterruptibly() 可中断等待 而synchronized一旦开始等锁就无法中断
2. lock.tryLock(1,TimeUnit.SECONDS) 超时等待 放弃
3. new ReentrantLock(true) 公平锁 默认是非公平锁 吞吐更高 
4. lock本身提供了很多api来查看当前锁信息























**AQS**

是JUC的基础骨架，封装了同步状态管理+阻塞队列管理+线程唤醒的核心逻辑

ReentrantLock底层通过Sync子类实现AQS的抽象方法



核心变量：

state：同步状态，表示锁的重入次数，state为0表示锁未被任何线程持有 state为n表示锁被当前线程持有且重入了N次（释放时需unlock N次）

exclusiveOwnerThread：指向当前持有锁的线程

阻塞队列：AQS的CLH队列（双向链表）存储等待锁的线程



**ThreadLocal**

底层用ThreadLocalMap，Map是Entry[],是一个threadLocal的弱引用，弱引用只如果没有强应用下次gc会回收某个实例，导致key被回收



理解内存泄漏：

某个对象不再被使用，但仍有可达的引用链，导致GC无法回收，最终占用堆内存



正常场景：

即当ThreadLocal实例不再被使用，比如方法执行完毕栈中的ThreadLocal引用被销毁，且线程也执行完毕，即Thread对象被GC回收：

Thread对象被回收-->ThreadLocalMap被回收-->Entry[]被回收-->Entry对象被回收 无泄漏



但有可能线程长期存活，比如线程池中的核心线程，且ThreadLocal实例无强引用

Entry数组存活，导致value无法GC回收，但是Entry的key因为是弱引用，因此会被GC回收掉



这也是为什么Entry的key被设计为弱引用，可以降低内存泄漏风险，可以把ThreadLocal对象回收掉

但仍存在value泄漏的风险，比如线程长期存活，为线程池的核心线程，且ThreadLocal实例无强引用，后续也没有调用该ThreadLocal的get/set方法



每次用完后显式remove



**线程池**

池化技术在线程管理上的体现，核心还有：数据库连接池、http连接池，核心都是减少每次获取资源的消耗，同时提高对资源的利用率，并提升可管理性

线程资源必须通过线程池提供，不允许在应用中显示创建线程，且不要用Executors去构建，而是通过TheadPoolExecutor的构造函数，



**如何设计一个动态线程池**

普通线程池的参数在创建时固定，运行中无法调整，动态线程池的诉求是在不重启服务的情况下，根据业务负载实时调整线程池参数。

JDK本身支持运行时修改采纳数，除了队列容量



因此本质就是监听配置中心Qconfig+实现一个支持动态扩容的队列（可以用反射的方式实现）

注意顺序：扩大先扩max再扩core，缩小先锁core再缩max

然后采集线程池指标做监控



动态线程池的灵魂在于先有监控，才知道何时该调整，例如定时上报指标，例如队列使用率超多少了 拒绝策略多少次

**中断**

Java不允许强制终止一个线程，只能请求线程停止，让线程自己决定何时响应

每个线程内部有一个中断标志位，初始为false

```
t.interrupt(); //其他线程向t发出中断请求
```

但线程被阻塞时，例如sleep、wait、take 根本没机会检查中断标志位

因此JDK的设计是：当线程处于阻塞状态时，如果收到中断请求，立即抛出InterruptedException来唤醒线程，让它有机会处理中断

但是会让线程进入waiting状态的方法 都会抛该异常

抛出异常后，JVM会自动清除中断标志位，如果不重置会导致中断信号丢失

正确响应时传递或恢复中断标志位























**异步编排框架**

早期java多线程只有Runnable（无返回值、无法抛异常），为了支持异步任务有返回值，引入callable+Future

JDK8+引入CompetableFuture，是高并发场景首选，实现了Future+CompletionStage接口

CompletableFuture的默认线程池ForkJoinPool.commonPool是全局共享的，建议自定义线程池

核心在异步任务的编排，例如需要一个任务依赖其他某两个任务执行完这种场景，就非常适合用CompletableFuture

且进行避免阻塞调用



**AQS**

Java早期的同步机制synchronized是JVM层面的，而JUC包需要用户态可自定义的同步逻辑（如可重入锁、倒计时器、信号量）如果每种同步器都从零去实现“等待队列/线程唤醒阻塞/状态管理”会大量重复造轮子

AQS封装了这些通用逻辑，开发者只需继承AQS重写少量方法就能快速实现自定义同步器



AQS支持的核心JUC组件：

- ReentrantLock 可重入独占锁
- CountDownLatch 共享锁（等待多个线程完成）
- Semaphore 共享锁（控制并发量）



AQS内的核心要素：

1、同步状态

AQS用一个volatile int state存储同步状态

不同同步器对state语义定义不同

2、CLH等待队列（双向链表）

当线程获取同步状态失败时 AQS将该线程封装成节点 加入CLH双向链表 然后阻塞线程 同步状态释放时唤醒队列头节点线程

3、条件队列Condition

用于实现线程等待/唤醒，每个Condition对应一个单向条件队列

线程调用 `condition.await()` → 释放同步状态 → 进入条件队列等待；

线程调用 `condition.signal()` → 唤醒条件队列的头节点 → 移到 CLH 等待队列，重新竞争同步状态。

典型应用：`ReentrantLock.newCondition()` 实现 “生产者 - 消费者” 模型。



CLH队列里的线程状态：

入队前是Runnable状态，线程竞争同步状态失败后不会立即阻塞，而是先进入自旋（忙等）状态，自旋的目的是减少线程阻塞/唤醒的开销（若锁很快被释放，自旋就能获取无需阻塞）

自旋一定次数后仍未获取锁，线程会封装为Node节点加入CLH队列，然后调用LockSupport.park(this)挂起当前线程，此时线程状态：WAITING 直到持有锁的线程释放后会唤醒CLH队列的头结点的后继节点



**基于AQS实现的几个同步器：**

1、Semaphore

2、CountDownLatch

3、CyclicBarrier

4、ReentrantLock

其实AQS用一个volatile int state + 一个CLH等待队列，配合CAS，把线程排队等待资源这套逻辑抽象出来，子类只需定义state的含义和修改规则，其余全部复用即可

**虚拟线程**

提升的主要是吞吐量和并发能力，并不能让单个请求执行速度变快

JDK在平台线程之上又加了一层调度：

- 虚拟线程是任务的承载者
- 平台线程是虚拟线程的载体，负责真正执行虚拟线程里的Java代码
- 操作系统仍然只调度平台线程，不知道虚拟线程的存在

一个虚拟线程开始执行会被JDK调度器挂载到某个平台线程上，执行到阻塞IO等支持挂起的阻塞点时，虚拟线程可以卸载，平台线程被释放出来继续执行其他虚拟线程



**不要池化虚拟线程**

线程池的目标是复用昂贵的平台线程，同时限制并发，虚拟线程不是稀缺资源

如果目标是为了限制某个资源的并发量，应该限制资源而不是虚拟现场数量，比如某个接口并发最大20，完全可以用Semaphore限制，如果瓶颈是数据库连接，那就调整连接池大小

把虚拟线程看做可以创建很多、阻塞成本更低的线程，通常能提升IO密集型服务的吞吐，但不会降低一次http调用或db查询的耗时



虚拟线程的pinning问题：虚拟线程暂时没法从载体线程上卸载，即被固定在某个platform thread了，在JDK21经典场景是在synchronized代码块里执行阻塞IO，可以改用ReentrantLock



切换后小心ThreadLocal缓存大对象，因为每个任务一个虚拟线程会导致内存压力很大

很多服务迁移虚拟线程后，第一个瓶颈不再是业务线程池，而是数据库连接池、HTTP连接池、Redis连接数或下游限流

虚拟线程更适合同步阻塞代码，已经用Netty写成全链路异步系统不一定会获得明显收益

**内存区域**

1、方法区

是JVM规范里的逻辑概念，用于存储【类的元数据、常量、静态变量、即时编译后的代码】

JDK7及之前 HotSpot用永久代实现 JDK8及之后用元空间替代 核心区别是元空间不再占用JVM堆内存而是使用OS的本地内存

特征：

- 所有线程均可访问方法区中类元数据
- 其回收目标主要是无用类的卸载和常量池回收，回收条件苛刻
- 易OOM，类加载过多（动态代理）



此外元空间达到阈值会触发Full GC并扩容元空间，JVM会卸载无用类，释放元空间内存



2、字符串常量池

这里补充一个字符串常量池，JDK8+仍在堆中，元空间仅存储类元数据不包含常量池，防止因字符串过多导致OOM，（这里提个点 JDK1.7把字符串常量池移到了堆里，因为方法区的GC回收效率很低，只有Full GC时会被执行GC，而Java程序通常有大量字符串等待被回收 于是移动到了堆里）



HotSpot里字符串常量池的实现是StringTable，可以理解为HashTable，保存的是字符串“key”和字符串对象引用的映射关系，其引用指向堆中的字符串对象



3、直接内存

它是JVM直接向操作系统申请的本地内存，是实现高性能IO的核心，这块内存不受JVM GC管控由OS管理，核心价值是减少数据拷贝，提升IO性能，读写速度远高于堆内存（减少了JVM堆-->OS内核缓冲区的拷贝）需手动调用Unsafe.freeMemory



与传统IO（BIO）对比：

数据从磁盘-->OS内核缓冲区-->JVM堆内存 经历两次拷贝

而NIO直接内存，数据从磁盘-->直接内存 仅一次拷贝，JVM可直接访问此内存无需拷贝到堆



应用场景：

- java.nio.DirectByteBuffer 网络/文件IO时减少数据拷贝 提升吞吐
- Netty/ElasticSearch 核心IO模块全部使用DirectByteBuffer 
- 大文件处理



必须注意，这块内存不受JVM GC管理，若释放不及时会导致OS内存耗尽，进程被kill

直接内存泄漏时生产环境高频问题，排查核心是【跨JVM+操作系统】分析：

**堆**

是JVM内存区域最大、核心、复杂的部分，几乎所有对象实例、数组都在堆中分配，建议-Xms和-Xmx值相同避免动态扩容卡顿，新生代频繁触发YGC，老年代低频FGC，按对象声明周期分为新生代、老年代，新生代分为Eden区、Survivor 0区、Survivor 1区，默认新生代：老年代是1：2 eden：s0：s1:=8:1:1

2、缓存对象多（存活时间长），老年代增长快（频繁Full GC）--增大老年代比例

**如何创建一个对象**

new指令触发-->类加载检查（常量池是否有类符号引用、类是否加载/解析/初始化）-->分配内存-->初始化零值--->设置对象头--->执行init方法



分配内存这一步，对象所需大小其实在类加载后是能确定的，等于是在堆里划分一块确定大小的内存，分配方式有指针碰撞和空闲列表两种（取决于堆是否规整，即垃圾收集器是否自带压缩整理功能）

- 指针碰撞 堆规整，用过的内存整合到一边，没用过的放一边，中间一个分界指针
- 空闲列表 虚拟机维护哪些内存块可用

且分配内存时创建对象是很频繁的，需要保证线程安全，CAS失败重试



一个对象在内存布局可以分为3块区域：对象头、实例数据和对齐填充，对象头包含：标记字段&类型指针

MarkWord标记字段：存储自身运行时数据，如哈希码、GC分代年龄、锁状态标志

类型指针：指向其类元数据的指针，通过这个JVM判断它是哪个对象的实例



访问定位：

我们知道java通过栈上的refence数据来操作堆上的具体对象，主流的访问方式有句柄、直接指针

1. 句柄：在Java堆里划分一块内存作为句柄池，引用指向对象的句柄地址，然后再句柄里包含了对象实例数据和类型数据各自的地址信息，句柄好吃是比较稳定，对象实例移动时不需要变refence，只用动句柄池即可
2. 直接指针，即refence直接存对象在堆内的地址，这种方式更快，减少一次指针定位的时间开销





**栈**

核心用于支撑方法的执行，每个线程启动时会分配独立栈空间，核心是存储方法执行的上下文，方法的调用和返回其实对应栈帧的入栈和出栈，其生命周期跟着线程走的，概念上分虚拟机栈和本地方法栈

最小的核心数据结构是栈帧：

- 局部变量表 方法参数、局部变量
- 操作数栈 
- 动态链接 指向运行时常量池的方法应用
- 方法返回地址 



栈溢出：栈深度超限制，例如无限递归、调用链过深、单线程栈配置过小例如-Xss很小

JVM进程的内存上线固定，若-Xss设为4m，创建4000个线程需要16GB栈内存，超过限制

## Java集合





关于fail-fast和fail-safe哲学，是Java集合框架在处理并发修改问题时的不同设计哲学

这其实是集合在被迭代遍历时，如果另一个线程（或同一线程）修改了集合结构，会发生什么？



fail-fast：快速失败，发现并发修改立即抛异常，不允许在不安全状态下继续运行

实现原理是modCount，迭代器创建时记录当前modCount，每次next()都检查值是否变化，如果有就抛出

ConcurrentModificationException

正确做法是用迭代器自己的remove，会同步更新expectedModCount



针对可能发生的异常进行提前表明故障并停止运行，通过尽早发现和停止错误降低故障系统级联的风险

fail-safe：安全失败，即使面对意外情况也能恢复并继续运行，适用不稳定的情况

而fail-safe的思想常用于并发容器，最经典的实现就是CopyOnWriteArrayList，通过写时复制Copy On Write的思想保证在进行修改操作时复制一份快照，基于这份快照完成添加或者删除操作后将底层的数组引用指向新的数组空间，由此避免迭代时被并发修改所干扰导致并发操作安全问题



```
public boolean add(E e) {
        final ReentrantLock lock = this.lock;
        lock.lock();
        try {
        	//获取原有数组
            Object[] elements = getArray();
            int len = elements.length;
            //基于原有数组复制出一份内存快照
            Object[] newElements = Arrays.copyOf(elements, len + 1);
            //进行添加操作
            newElements[len] = e;
            //array指向新的数组
            setArray(newElements);
            return true;
        } finally {
            lock.unlock();
        }
    }
```

**堆**

TOP-K问题：从N个数据中找出最大/最小的K个，是面试和工程里的高频场景：

暴力解法是全量排序 O（nlogn）但用堆可以做到O（Nlogk）

实际用得更多的还是对象：

```
public List<Order> topKOrders(List<Order> orders, int k) {
    PriorityQueue<Order> minHeap = new PriorityQueue<>(
            Comparator.comparingDouble(Order::getAmount)  // 按金额升序，堆顶最小
    );
    for (Order o : orders) {
        if (minHeap.size() < k) {
            minHeap.offer(o);
        } else if (o.getAmount() > minHeap.peek().getAmount()) {
            minHeap.poll();
            minHeap.offer(o);
        }
    }
    return new ArrayList<>(minHeap);
}                                                                                                                                                               
               
```

优势在于，外层遍历N次 每次堆操作O（logk），空间只需要O（k）不需要把全量数据加载进内存，天然支持流式数据，简单理解为用一个K大小的窗口，始终保留见过的最好的K个

**hashmap**

一、HashMap 的整体设计

HashMap 是 key-value 键值对的存储结构，核心目标是在平均 O(1) 的时间内完成增删查改。

它的底层结构（JDK 8+）：

数组 + 链表 + 红黑树

      table[]
   ┌──────────┐
 0 │   null   │
   ├──────────┤
 1 │  Node ───┼──> Node ──> Node (链表，元素少时)
   ├──────────┤
 2 │   null   │
   ├──────────┤
 3 │  Node ───┼──> 红黑树 (元素多时)
   ├──────────┤
 4 │   null   │
   └──────────┘

table 是一个 Node[] 数组，每个位置叫桶（bucket）。哈希冲突的元素挂在同一个桶后面，先用链表，链表长了转红黑树。

二、核心字段和常量

public class HashMap<K,V> {
    // 默认初始容量 16，必须是 2 的幂
    static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;

    // 默认负载因子 0.75
    static final float DEFAULT_LOAD_FACTOR = 0.75f;
    
    // 链表长度 >= 8 时，尝试转红黑树
    static final int TREEIFY_THRESHOLD = 8;
    
    // 红黑树节点 <= 6 时，退化回链表
    static final int UNTREEIFY_THRESHOLD = 6;
    
    // 只有数组长度 >= 64 时才会转红黑树，否则先扩容
    static final int MIN_TREEIFY_CAPACITY = 64;
    
    // 存储数据的桶数组
    transient Node<K,V>[] table;
    
    // 当前元素数量
    transient int size;
    
    // 扩容阈值 = capacity * loadFactor
    int threshold;
    
    // 结构修改次数（fail-fast 机制用）
    transient int modCount;
}

Node 结构（链表节点）：

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;      // key 的哈希值缓存
    final K key;
    V value;
    Node<K,V> next;      // 链表指针
}

三、hash 函数：扰动计算

这是 HashMap 精妙的地方，直接看源码：

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

为什么要 h ^ (h >>> 16)（高低16位异或）？

因为定位桶用的是 (n - 1) & hash，n 是数组长度（默认16）。这个运算只用到 hash 的低几位。如果 hashCode 高位分布好、低位差、直接取低位会导致大量冲突。

高低位异或让 hash 的高16位参与到低位的计算，使桶分布更均匀。

原始hashCode：11010010 11100101 10101001 01110110
高16位右移：  00000000 00000000 11010010 11100101
异或结果：    11010010 11100101 01111011 10010011
                                  ↑ 低位融合了高位信息

---
四、定位桶：位运算代替取模

// 桶索引 = (数组长度 - 1) & hash
int index = (n - 1) & hash;

为什么用 & 而不是 %？

因为 % 是除法，慢；& 是位运算，快。

但前提是数组长度必须是 2 的幂：

n = 16 → n - 1 = 15 = 00001111（二进制）
hash = 27         = 00011011
(n-1) & hash      = 00001011 = 11

等价于 27 % 16 = 11

当 n 是 2 的幂时，(n-1) 二进制是全 1，& hash 效果等同于取余，但快得多。

这就是为什么 HashMap 容量强制为 2 的幂，即使你传 new HashMap<>(10)，实际容量也会被调整为 16。

五、put 操作全流程

public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}

final V putVal(int hash, K key, V value, ...) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;

    // 1. 表为空，先初始化
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;
    
    // 2. 定位桶，桶为空直接放
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);
    
    else {
        // 3. 桶不为空，处理冲突
        Node<K,V> e; K k;
    
        // 3a. 桶首节点 key 相同，直接替换
        if (p.hash == hash && (p.key == key || (key != null && key.equals(p.key))))
            e = p;
    
        // 3b. 桶首是红黑树节点，走树的 put
        else if (p instanceof TreeNode)
            e = ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);
    
        // 3c. 是链表，遍历
        else {
            for (int binCount = 0; ; ++binCount) {
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);
                    // 链表长度 >= 8，尝试转红黑树
                    if (binCount >= TREEIFY_THRESHOLD - 1)
                        treeifyBin(tab, hash);
                    break;
                }
                if (e.hash == hash && (e.key == key || (key != null && key.equals(e.key))))
                    break;
                p = e;
            }
        }
    
        // 4. key 已存在，更新 value 并返回旧值
        if (e != null) {
            V oldValue = e.value;
            e.value = value;
            return oldValue;
        }
    }
    
    ++modCount;
    
    // 5. size 超过阈值，扩容
    if (++size > threshold)
        resize();
    return null;
}

流程图：

put(key, value)
    ↓

    ↓

    ↓
桶为空？──是──→ 直接放入，size++，判断扩容
    │否
    ↓
桶首 key 相同？──是──→ 替换 value，返回旧值
    │否
    ↓
是红黑树？──是──→ 树插入
    │否
    ↓

六、get 操作

public V get(Object key) {
    Node<K,V> e;
    return (e = getNode(hash(key), key)) == null ? null : e.value;
}

final Node<K,V> getNode(int hash, Object key) {
    Node<K,V>[] tab; Node<K,V> first, e; int n; K k;

    if ((tab = table) != null && (n = tab.length) > 0 &&
        (first = tab[(n - 1) & hash]) != null) {
    
        // 1. 检查桶首节点
        if (first.hash == hash && ((k = first.key) == key || (key != null && key.equals(k))))
            return first;
    
        // 2. 遍历链表或红黑树
        if ((e = first.next) != null) {
            if (first instanceof TreeNode)
                return ((TreeNode<K,V>)first).getTreeNode(hash, key);
            do {
                if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
                    return e;
            } while ((e = e.next) != null);
        }
    }
    return null;
}

注意判断相等的写法：e.hash == hash && (e.key == key || key.equals(e.key))

- 先比 hash（int 比较，快速排除）
- 再比 == （引用相等，String 常量池会命中）
- 最后比 equals（真正的业务相等判断）

这就是为什么重写 equals 必须重写 hashCode——只重写 equals 时 hash 不同，直接定位到别的桶，equals 根本没机会执行。

七、扩容 resize

触发条件：size > threshold，即 size > capacity * 0.75。

扩容规则：容量翻倍，newCap = oldCap << 1。

JDK 8 的巧妙优化：

因为容量翻倍，原来在桶 i 的元素，扩容后要么在 i，要么在 i + oldCap，只需要看 hash 的一个 bit：

oldCap = 16 = 10000
newCap = 32 = 100000

原桶索引：hash & 01111 = i
新桶索引：hash & 11111

关键看 hash 的第 5 位（对应 oldCap 的最高位）：
  第5位 = 0 → 新索引 = i         (原位置)
  第5位 = 1 → 新索引 = i + 16    (原位置 + oldCap)

代码里就是 (e.hash & oldCap) == 0 的判断：

if ((e.hash & oldCap) == 0) {
    // 留在原位置
} else {
    // 移到 i + oldCap
}

不需要重新计算 hash，也不需要取模，一次位运算搞定。

八、链表 → 红黑树的转换

为什么需要红黑树？

链表查找是 O(N)，极端情况下（大量哈希冲突）性能退化严重。红黑树查找 O(logN)，兜底极端情况。

转换条件：

1. 链表长度 >= 8（TREEIFY_THRESHOLD）
2. 同时数组长度 >= 64（MIN_TREEIFY_CAPACITY）

如果数组长度 < 64，会优先扩容而不是转红黑树，因为扩容后冲突会被打散。

退化条件：红黑树节点 <= 6（UNTREEIFY_THRESHOLD）时退回链表。

为什么阈值是 8 和 6？

理想哈希（泊松分布）下，桶里放 8 个元素的概率约 6×10⁻⁷，极小。达到 8 说明 hashCode 分布很差，才需要红黑树兜底。设 6 而不是 7 是为了防止在 7-8 边界反复转换。

九、HashMap 的核心问题

1. 线程不安全

并发 put 可能形成死循环（JDK 7 头插法的问题，JDK 8 改为尾插法已解决），但 JDK 8 仍然可能出现数据丢失、size 错误等问题。

并发场景用 ConcurrentHashMap。

2. key 的 hashCode 必须稳定

如果 key 是可变对象，put 后修改字段导致 hashCode 变化，就再也 get 不到了：

Map<StringBuilder, String> map = new HashMap<>();
StringBuilder key = new StringBuilder("abc");
map.put(key, "value");

key.append("d");           // 修改 key
map.get(key);              // 返回 null！

key 应该是不可变对象（String、Integer、包装类）或至少 hashCode 不变。

3. 允许 null key 和 null value

null key 的 hash 强制为 0，固定放在桶 0。ConcurrentHashMap 不允许 null，因为并发下无法区分 "key 不存在" 和 "key 对应 null"。

#### IO

计算机底层只有二进制字节，文件存储、网络传输的最小单位都是字节，但文本数据本质是字符，字符和字节之间需要通过编码规则如UTF-8、GBK映射

在Java里区分字节流和字符流，字符流是上层的封装，前者适合处理二进制数据：图片、视频、压缩包，后者适合处理文本数据：txt、xml、日志

如果只有字节流，当你读取一个UTF-8编码的文本文件时需要自己处理多字节字符



字符流完全基于字节流实现，只不过在此基础上加了编码&解码层封装，对外保留字符级别的接口



而IO里的缓冲区本质是在内存中开辟的一块缓存区域，用于批量读取/写入数据，减少底层系统调用的次数，因为直接操作磁盘/网络的系统调用很耗时，缓冲区通过攒批处理将多次小IO合并成一次大IO



有缓冲IO：一次系统调用批量读取批量数据到缓冲区

默认8KB适合大多数场景，如果是大文件GB级别，可以手动指定更大的缓冲区减少系统调用次数



**IO模型**

IO模型的本质是应用程序与内核交互数据的方式，核心差异在等待数据和拷贝数据两个阶段的处理方式

1. 等待数据就绪（最耗时）：内核等待网络数据到达并拷贝到内核缓冲区（如网卡-->内核内存）
2. 数据拷贝：将内核缓冲区的数据拷贝到应用程序缓冲区（内核态-->用户态）

所有IO模型的性能差异本质都是这两个阶段是否阻塞、是否占用应用线程



1、阻塞IO 

应用线程调用IO接口后，全程阻塞，直到数据拷贝完成线程才被唤醒

Java中的实现：基础Socket、FileInputStream都是BIO，线程利用率极低（一个连接占用一个线程，线程大部分时间在阻塞等待），在高并发下1000个连接需要创建1000个线程导致线程上下文频繁切换、内存耗尽



2、非阻塞IO

应用线程调用IO接口后，不阻塞等待数据就绪，若数据未就绪，应用线程可做其他事，之后轮询重试，直到数据就绪内核阻塞进行数据拷贝

线程无需一直阻塞可轮询多个连接，但数据拷贝阶段仍阻塞且轮询会消耗CPU资源



3、多路复用IO

核心是事件监听+多路复用器 如linux的select/poll/epoll

1. 应用线程将所有待监听的IO连接注册到多路复用器
2. 应用线程调用多路复用器的接口如epoll_wait,阻塞等待多路复用器返回就绪的IO事件
3. 仅当连接数据就绪时，应用线程采取调用IO接口，执行数据拷贝



Java NIO的Selector（底层封装Linux epoll/Windows IOCP）是多路复用IO的核心，线程只阻塞在多路复用器等待⌚️，线程利用率大幅提升，是高并发网络编程的基础（Netty/Tomcat8+）

- select/poll：监听的连接数有限，每次轮询需遍历所有注册连接，
- epoll：无连接数限制，基于事件通知而非轮询，高并发下性能优势明显



4、异步IO

全程不阻塞，让内核完成【等待数据就绪+数据拷贝】全流程后，主动通知应用线程，应用线程直接处理

高并发下性能未必优于多路复用IO



优先用多路复用IO



**NIO**

三大组件：

1. channel 通道 对应一个网络连接/文件 
2. ByteBuffer 数据缓冲区 分heap/direct 
3. Selector 选择器 底层封装epoll 单线程轮询监听海量channel



实际工程选择：

- 读写本地文件--->BIO足够
- 高并发网络服务器 NIO 但直接用Netty 别自己写Selector
- AIO Linux下实现不成熟，实际用得很少
- Spring WebFlux/响应式编程    底层基于NIO，用Reactor模型封装

像Dubbo、RocketMQ这些都是直接用Netty

- 基数  在数据库领域，基数是指某一列中不同值的数量，比如对于用户表的userid列来说 有100w个用户就有100w个基数 

因此基数大的列不适合做索引列，因为CK的索引是稀疏索引，它会对数据进行分组，然后记录分组的边界值，当基数特别大时，数据分布会非常分散，索引难以有效地缩小查询范围



2、CK数据写入

在CK里分布式表本身不存储数据，更像一个代理将查询路由到本地表所在的节点上

有以下几种关联方式：

rand():随机 这种可以保证均匀 能均匀分散数据负载 但无法保证数据的局部性不利于关联查询

hash：根据指定列的哈希值将数据分发到不同节点，配置分布式表时可以使用hash函数来实现 有利于关联查询

但容易产生数据倾斜

分片键：指定一个或多个列的值让CK根据分片键的值将数据分发到不同节点



我们是推荐用Local to Local的方式，就是不通过分布式表进行写入，而是直接将数据写入到各个节点的本地表

这样写入性能更好，通过分布式表写入，数据先到分布式表所在节点，然后再将数据转发到各个本地表所在节点

过程是存在网络开销和处理延迟的，直接写入本地表能充分利用各个节点的资源，不会让分布式表所在的节点成为整个集群的写入瓶颈，而且这样写入单节点是独立的



一般我们会为每个节点都创建分布式表并非在一个节点去创建，这样客户端不管连接到哪个节点都可以用该节点上的分布式表发起查询，也保证系统的负载均衡，提高容错性

### 二级索引&跳表索引

与其他DB不同的是：CK中的二级索引不指向特定的行或行范围，相反它们使数据库可以预先知道某些数据部分中的所有行都不符合查询过滤条件，并且根本不读取它们，因此它们被称为数据跳过索引（即跳表索引）

对比Mysql二级索引是直接锁定到记录的主键的，而CK是对某个数据块Granule的摘要，只能判断某个Granule是否可能包含目标值

CK常见的二级索引：

- minmax 每个Granule的min/max值
- bloom_filter 每个Granule的布隆过滤器
- tokenbf_v1 字符串分词的布隆过滤器

因此可以针对高频过滤列区创建跳数索引，而主键用于排序+稀疏索引



**Q：为什么CK不做类似Mysql的二级索引**

传统索引的行指针在列存储中没有意义，且CK以Granule为单位处理数据，跳过Granule比定位单行高效

且传统B+数索引写入会严重拖慢写入

### MergeTree家族引擎

mergeTree引擎是怎样写入&合并数据，不同mergeTree家族的写入与合并表现有何不同

以及如何自动地将数据插入多个表

mergeTree引擎被设计来每秒接收数百万行插入，并存储非常大量的数据，例如数百PB

每次插入会形成一个表部件part，即磁盘上的一个目录其中包含压缩列表文件、mark文件、主索引文件

在后台CK会不断将较小的parts合并成一个较大的parts，合并后原有部件将被删除



mergeTree家族引擎的区别在于它们如何合并数据块

- 普通MergeTree：简单合并-->排序
- replacingMergeTree：CK的数据插入和读取都是极快的，但对大量单行更新的OLTP性能不好，但你可以通过replacingMergeTree来把更新转换为行插入操作，CK很适合干这个事情，把物理更新放在MergeTree部分，具有相同排序键的行会被最新行替换
- AggregatingMergeTree：把数据聚合从查询时间移动到数据插入和合并的时间，这样我们不必在查询时一次又一次地计算聚合，而是在插入和合并时分别计算，在查询时用已经聚合好的数据，在合并时具有相同排序键的所有行替换为包含具有聚合数据类型的所有列的聚合值的单行，列的特定聚合函数数据类型告诉CK作用于哪个列以及是否需要分别存储额外的状态



**简单聚合和非简单聚合**

- 简单聚合：只应用聚合函数即可 例如max
- 非简单聚合：额外存储精确增量聚合所需的一些额外信息&状态 例如AVG



在使用mergeTree引擎的时候要注意部分的合并可能永远不会完全完成，首先CK常用于实时分析场景，其中不断提取新数据，因此不断创建新part

此外CK在合并parts时会在某个时候停止，要么是因为parts变得太大，要么是没有足够的磁盘容量进行另一次合并，而且部分的合并可能永远不会完全完成



这意味着使用replacingmergeTree去替换行也可能不完整，并且使用AggregatingMergeTree引擎聚合行数据

**因此需要在查询时完成该表引擎可能未完成的工作**，这往往只需要消耗查询的一小部分资源



我们在各个表还有未完全合并的数据块的情况下 发起查询：

1、MergeTree基础只是盲目地将所有行从各个数据部件复制到一个新的，在合并期间我们可以使用标准SQL查询从表中获取数据，此查询正在读取并列出所有活动部分的所有行

2、但如果我们用相同的查询对replacingMergeTree时会有问题，因为replacing是不完整的，会包含重复项

为此我们可以在查询的from子句中使用final修饰符，当指定final时CK会在返回结果前在内存中完全合并数据从而执行给定表引擎在常规物理合并期间发生的所有数据转换



**合并与数据分区**

特别注意的是，分区是mergetree引擎中控制part合并范围的核心机制，核心原则是：**Part合并只在同一个分区内进行**



1. 首先分区是天然的数据隔离单元，不同分区数据天然组织在不同磁盘目录中，合并时只需扫描单个分区内数据，可以减少IO和内存压力
2. TTL和删除优化 例如删除整个分区时只需删除目录，无需合并或扫描数据
3. 查询减枝 可以直接在符合范围的分区内查找即可













**场景题:**

 以replacingMergeTree引擎的表为例，我理解一次insert写入Clickhouse会创建一个表部件part，后台是不断得在进部件parts合并的，此时客户端发起了一次查询，可是我的表部件还并没有完全完成，这种时候是否可能出现有相同主键的记录存在于不同的表部件中（此时由于两者还没有完成合并所以replacingMergeTree也没法完成去重），我使用普通select会可能出现这种问题嘛？

**---**使用普通select确实存在这种问题，这是由于ReplacingMergeTree的最终一致性决定的，只要相同主键的记录分散在不同的未合并 `Part` 中（比如刚写入的小 `Part` 还没和旧 `Part` 合并），去重就没完成。

而客户端普通的select执行时，CK会扫所有的Active Part不论是否合并，并将所有Part中的数据直接返回



两种解决方案：

1、OPTIMIZE TABLE t final

手动触发合并，对IO和CPU的消耗很大，会严重影响性能

虽然不影响CK的写入，因为CK的写入是Append-Only的，新的insert会继续生成part

但由于合并操作消耗大量CPU（排序、去重、压缩）IO（读取多个part+写入新part，磁盘IO飙升）而且合并需要内存缓存，optimize final会合并所有的part，期间的写入和查询会很慢，不建议在生产环境使用

**我们进行过压测实验：**

正常状态 写入50w行/s吞吐 查询延迟 100ms CPU load30%

但是执行optimize final 吞吐5w 查询延迟300ms CPU load 95%



2、final修饰符解决

性能不好，不建议频繁查询，本质是查询时模拟后台合并的行为，会读取所有part在查询时进行内存合并

尽量避免final，有限使用argMax等聚合函数去做优化

optimize table hits final这才会真实合并 select+final是不会的

而且要注意的是final修饰符的本质的内存的逻辑合并，不会触发或完成任何后台part合并，只是在查询时的模拟

后台合并线程才是真实做合并的：

- 删除旧的part 创建新part 更新System.parts元数据

对CK来说查询和存储是分离的，查询引擎只负责读取和计算，存储引擎负责合并和优化



3、使用group by+avgmax来解决

即先正常查询后去实时查询





### CK 的类MVCC机制

Q：所有问题还是在于客户端的查询其实无法感知到后台有没有把parts合并完全，但问题是我们在使用mergeTree引擎的时候parts的合并可能永远不会完全完成，首先CK作为实时分析场景，不断有数据写入，因此不断创建新part，此外CK合并parts时在某个时候停止，因为part可能已经变得太大 以上我想说明的是：对于CK来说表部件part的合并可能永远无法完全完成，而同时CK的读写又是不冲突的（我理解没有类似mysql这种mvcc快照读机制），因此CK是怎么处理数据读写可见性的问题的呢？



核心机制：Part-Level MVCC 基于数据片段的多版本并发控制

1. 每个part一旦创建就是不可变的
2. 查询开始时获取当前所有Active part的快照
3. 查询过程中只读取这个快照中的part
4. 新写入的part不会影响正在进行的查询

其实这本质就是MVCC 只不过粒度是part级别而不是mysql的行级别，实现CK读写不冲突



part生命周期：

- Active 正常数据part
- Outdated 被合并替代的part 不可见
- Temporary 正在写入的part 不可见直到写入完成

只有新的写入完成，旧的才会被标记为outdated



理解：part合并永远不会完全完成

1、持续写入 实时场景 或是合并<写入

2、合并策略限制 CK有合并阈值 超大part不会继续合并 避免单词合并耗时过长

3、资源保护 当系统负载高时合并会暂停 因为CK优先保证写入性能和查询稳定性，而不是追求完全合并





### 物化视图与投影

物化视图实际上只对源表中新插入内容做出反应，并且物化视图中的SQL查询仅应用于所有新插入的数据块，以便在将数据插入目标表前重塑数据，CK本质上设计是为了快速且高效地提取和处理数据，如果源表存储了PB级数据，那么从非常大的源表中选择数据将无法扩展

然而对源表的所有插入操作做出反应是可行的，重塑的数据块最终提供给目标表，存储在目标表磁盘目录中

这是一种自动增量数据转换的机制

例如可以做预聚合，把计算更多放在插入和合并阶段而不是查询阶段，这可以加速CK的分析查询，在查询中只需读取几乎最终的结果



而投影无疑是实现自动增量数据转换最现代的方式，和物化视图不用的是投影的底层机制对用户是隐藏的

且用户不必明确使用状态后缀状态来查询，并且所有的查询都发送到源表，CK自动在投影的隐藏目标表查询，这根据优化器决定，但物化视图需要用户显示指定



但投影不能针对性设置DTL，物化视图可以

投影以原子方式与源表一致地更新，因为投影隐藏目标表的数据存储在源表相同part目录

### 分布式表

由于采用share nothing架构，CK的分片方式很低级，例如集群主机直接没有进行协调，并且分片之间完全独立

，因此我们需要创建分布式表，分布式表本身不存储任何数据，但提供单个表接口，来组合访问位于不同主机的远程表，我们可以在集群的一个或多个节点上创建分布式表。



当查询针对分布式表时，会把查询转发到所有主机，等待分片的查询结果，然后计算并返回整体查询结果，可能由于特定的数据分布，也可能转发到一个节点



**写分片表**

1、直接指定节点的远程表写数据，这是最灵活的解决方案，数据可以完全独立地写入不同分片

2、写分布式表，需要设定分片键参数，sharding key，然后分布式表再分发，如果在创建分布式表时没有指定分片键，那么无法通过分布式表直接写入数据，只能通过向各个节点的本地表分别写入

在每个节点都配置一下集群拓扑信息，这些是给分布式表引擎使用的

| 场景                      | 建议                             |
| ------------------------- | -------------------------------- |
| 希望数据分布均匀          | 使用rand()或高基数字段（userid） |
| 希望相同的key落在同一分片 | 使用业务字段                     |
|                           |                                  |



**写入优化**

对比写分布式表与local to local写入

| 对比项   | 分布式写                                   | local to local        |
| -------- | ------------------------------------------ | --------------------- |
| 网络跳数 | 客户端->协调节点->目标节点 两跳            | 客户端到目标节点 一跳 |
| 协调节点 | 所有写流量都经过协调节点，容易成为写入瓶颈 | 无协调节点，负载分散  |
| 写入延迟 | 更高                                       | 更低                  |
| 场景     | 小批量简单写入                             | 高吞吐、生产推荐      |

Local to Local写入核心：客户端负责分片路由，先拉取到CK集群配置，在客户端实现分片算法，然后将数据发送到对应节点的本地表，确保数据分布与分片规则完全一致，此外写入时只需写入一个副本，CK集群会在副本间同步，建议按分片分组数据，每个节点一次批量写入，避免频繁小写，建议是攒够1w条数据写一次

建议封装同一个shardRouter，避免各团队重复实现，然后自动化测试验证，监控集群数据分布，千万不要随便改分片键，扩容需要rehash的

另外如果分片键用rand，其实不能local to local写入了，因为每次rand不同，local to local必须分片要确定

bin文件是由一个个数据块组成的，数据块分为头文件和压缩数据，头文件记录压缩算法以及压缩前大小&压缩后大小，CK会把64k-1mb的数据作为一个压缩块，



了解到bin文件构造后，就可以去看每个列的mrk文件，mrk文件是为了快速定位到

这里要注意的是Granule是逻辑查询单位，但Compression Block是物理存储单位 mrk文件是二者的桥梁



**理解：为什么CK是压缩数据块而不是每个granule压缩**

压缩效率Compression block默认64-1mb（如果我们批量写 大多是1mb）相比一个granule 8192行 大约几十KB来说，压缩效率更高，

一个granule永远不会跨多个block

以 `SELECT name FROM table1 WHERE id = 657812` 为例：

步骤 1️⃣：主键索引定位 Granule

- `primary.idx` → 确定 `id=657812` 在 **Granule 100**

步骤 2️⃣：.mrk3 文件提供精确定位

- ```
  name.mrk3[100]
  ```

   包含：

  - `offset_in_compressed_file = X` → Compression Block 起始位置
  - `offset_in_decompressed_block = Y` → Granule 100 在解压数据中的偏移

步骤 3️⃣：读取并解压整个 Compression Block

- 从 `name.bin` 的位置 `X` 开始，读取**整个 Compression Block**（约 1MB）
- 解压得到连续数据：`[Granule 95, Granule 96, ..., Granule 105, ...]`

步骤 4️⃣：精确定位到目标 Granule

- 从解压数据的偏移 `Y` 开始，就是 **Granule 100 的起始位置**
- 读取 Granule 100 的 8192 行数据

步骤 5️⃣：在 Granule 内查找目标行

- 由于 Granule 内部**按主键排序**，可以用二分查找快速定位 `id=657812`
- 返回对应的 `name` 值

### 分页

limit 10000 20

对于mysql来说 分页执行其实不是直接跳到第10001条，而是优化器根据where+order by确定执行计划，从第一条数据开始扫描并依次读取索引满足条件的行，一直扫描到你要偏移的位置：10000+20 = 10020行，然后把前面10000行全部丢弃，只返回最后20条

简单来说就是 并不是跳到第几行，而是读到第几行再扔掉前面的



深度分页：limit 1000000，20 要扫描1000020 然后扔掉1000000，如果是二级索引要逐条回表，如果order by字段无索引mysql会filesort，可能用到临时磁盘表



深度分页慢的核心在于，mysql必须先读到偏移位置不能直接跳转，偏移越大扫描与回表的代价越高



解决方案：

1、主键ID连续分页

不使用偏移量，用ID定位

```
select * from user 
where id > 100254 
order by id
limit 20
```

但这种方式不能跳页，只能上一页或下一页



2、延迟关联 子查询优化

```
select * from user u
JOIN (
select id from user where age > 18 order by id limit 100000 20
) t
on u.id = t.id
```

这样子查询无需回表走索引覆盖，只回表20次



3、覆盖索引

```
-- 建立联合索引 (status, id, name, phone)
SELECT id,name,phone FROM user 
WHERE status=1 
ORDER BY id 
LIMIT 1000000,20;
```

例如app/前端限制不允许跳转到1000页之后，只提供上下页，搜索类改用ES

### **日志**

两阶段提交redo log&&binlog

其实有点分布式事务：

阶段1：prepare

1. Innodb写redo log，状态标记为prepare
2. 刷盘策略由参数决定

阶段2 写binlog

1、根据sync_binlog刷盘 

binlog一旦刷盘 事务逻辑上就已经提交

阶段3 commit

将redo log状态改为commit



如果写完redo prepare 但binlog刷盘失败 会事务回滚



如果写完binlog 但redo commit失败

会自动提交事务

本质以binlog作为事务是否提交的裁决者



要理解 redo prepare只是内存操作 不保证刷盘 由参数决定

两阶段提交保证的是磁盘上的redo和binlog一致，崩溃恢复时只看磁盘上的redo log，只有磁盘上存在prepare状态的redo，才去查binlog里有没有对应的XID来决定提交或回滚





会先写redo log 至少写到OS cache 再写binlog 最后才标记redo为commit



**页缓存机制**Page Cache

 即通过将数据缓存在内存中来提高对磁盘读操作和写操作的性能

对磁盘读：即cache 将最近读过的数据放在内存，下次若访问同样的数据可以直接读内存 

对磁盘写：即buffer缓冲 磁盘的访问粒度是磁盘块 通常4KB，而内存访问粒度是cacheline



引入page cache后，内存中的数据与磁盘中的数据往往是不同步的，内存数据更新一点，因此在数据未完全写入磁盘的情况下，如果断电则所有内存中新的数据都会丢失 

fsync的引入就是为了解决该问题，当应用程序调用fsync后，OS会将所有在page cache的数据写入磁盘并等待写入操作结束后才返回，因此应用程序在fsync返回后就能够确认之前通过write写入磁盘的数据已经落盘了，即使断电也完整保证在磁盘上了



这是在性能与数据持久性的权衡



**binlog刷盘**

其实binlog的刷盘只有两个选项：

sync_binlog：0 提交时write到OS page cache，让OS自己定时刷盘 1：提交时立即fsync

因为binlog是Mysql Server层而非存储引擎层的日志，一是很重要是主从复制的数据源，必须保证日志不丢，且没有类似redo那样的崩溃恢复能力



**两阶段提交**

流程：

1. redo prepare 并根据策略决定是否刷redo
2. 再写binlog 根据sync_binlog决定是否刷
3. redo commit 仅内存标记 很轻量





1、两阶段提交的流程结构永远不变，不受任何刷盘策略的影响，变的只是刷盘时机，落盘保证强度

2、redo log和bin log是否真正落盘，不影响事务是否提交成功 只影响宕机后是否丢数据

3、事务提交的逻辑顺序永远固定，先redo prepare 再写binlog 最后redo commit，日志刷盘是这个流程中的动作而不是改变流程本身

刷盘策略只影响

- 在 `redo prepare` 时，redo 是只写到 buffer？还是写到 page cache？还是直接 fsync 落盘？
- 在 `binlog` 写完后，是立即 fsync？还是交给 OS 刷？



binlog成功=事务最终生效 宕机后根据binlog有无来决定提交/回滚 ，即如果binlog刷盘失败 则事务会回滚

宕机重启后会去扫描redo log找到所有prepare状态的事务，去binlog查XID是否存在，如果存在则提交事务否则回滚，即让binlog作为事务是否提交的衡量标准







### Direct IO

OS提供了直接IO的机制 让应用程序自己管理文件系统的缓存

InnoDB使用O_DIRECT打开数据文件（ibd）绕过OS Page Cache直接读写磁盘，redo log依然走Page Cache + fsync

- 数据页：Innodb已经有Buffer Pool做精细化缓存（按页、按热度、LRU、预读、脏页）再走Page Cache就是双缓冲--同一份数据在内存存两份、浪费内存、增加拷贝开销
- redo log是顺序写，小IO，必须强持久



**为什么数据页默认开direct io 但是redo log不用**

因为redo log是顺序写、高频小IO，page cache可以批量合并小IO 延迟刷盘 提升吞吐量

这里引申一下操作系统的page cache

对磁盘写提供缓冲buffer，如果对一个磁盘块有多次写操作，则可以通过页缓存将其合并成一次磁盘写操作，从而进一步提升性能

对磁盘读来说是提供缓存功能即cache，将最近读过的数据放在内存中，下次若访问同样的数据则可以直接读内存

但引入页缓存，内存中的数据和磁盘是有差别的，如果突然断电可能导致pagecache里的脏数据没能刷到磁盘，导致数据丢失

因此fsync系统调用就是解决这个问题，即将pagecache里的数据都写入磁盘并等待写入操作完成后才返回，因此应用程序在调用fsync返回后就能确认之前通过write（）写入磁盘的数据已经落盘了

通过write和fsync解耦 让应用程序在性能和数据持久性上做出选择 



此外有些应用，如数据库，希望自己来管理文件系统的缓存，因为相比OS，其实Innodb更清楚数据，且mysql有自己的日志文件，这些文件对持久性的要求和其他文件不同，让数据库来管理文件缓存比OS更合适，OS提供了Direct IO机制，允许应用程序在打开文件时不使用Page Cache

**Multi-part AOF**

即把aof文件拆成了多个文件管理：

- 清单文件manifest：记录当前aof由哪些文件组成
- 基础文件base：RDB格式保存重写开始那一刻内存的全量数据
- 若干增量文件incr：AOF格式记录重写开始之后新产生的写命令



重写过程：

1. 重写开始时，主进程新开一个incr文件，之后新的写命令追加incr
2. 子进程把当前内存状态以RDB格式写入新的base文件
3. 重写完成后，Redis更新manifest文件，指向新的base和incr

这样减少父子进程对于增量命令的同步，以及重写缓冲区的维护，减少内存和cpu的压力

**脑裂**

网络分区导致集群出现两个可写的主节点，网络恢复后，旧主的数据被清空覆盖造成永久丢失

```

# 从延迟 ≤ 10 秒才算健康

```

这样只要出现网络分区，旧主节点的客户端写入应该报错

**中断**

操作系统收到硬件的中断请求，会打断正在执行的进程，然后调用内核的中断处理程序来响应请求，由于OS收到了中断请求会打断其他进程的运行，所以中断处理程序要尽可能快的执行完，这样可以减少对正常进程运行调度的影响

并且在执行中断处理程序时可能还会临时关闭中断，这意味着中断有可能会丢失

中断是一种异步的事件处理机制，可以提高系统的并发处理能力。



**软中断**

中断是一种异步的事件处理机制，可以提高系统的并发处理能力。

linux将中断分成两个阶段，上半部来快速处理中断，暂时关闭中断请求，下半部延迟处理未完成的工作

举一个网卡接收网络包的例子，网卡收到网络包后通过DMA方式将数据写入内存，然后通过硬件中断通知内核有数据就绪，此时内核会调用相应的中断处理程序，上部分先禁止网卡中断，接着内核会触发一个软中断把一些处理耗时且复杂的事情交给软中断处理程序去做，也就是中断的下半部，主要是从内存中找到网络数据再按照网络协议栈逐层解析处理网络数据，最后把数据送给应用程序



硬中断会打断CPU正在执行的任务然后立即执行中断处理程序，软中断以内核线程执行

inter-process communication IPC

- 消息系统 通过中间层（如内核）保证通信时延，仍可通过共享内存传递消息

直接通信

间接通信：topic

**如何优化文件传输**

### **事务**

spring支持声明式和编程式，一般就用声明式即@transactional注解去做，它对代码侵入少

默认只有RuntimeException和Error会回滚，检查型异常不回滚，可以通过rollbackFor来指定



事务传播行为：

1、propagation_required

使用最多的，也是默认的，即如果当前存在事务，则加入该事务，如果当前没有事务则创建一个新事务



2、propagation_new

创建一个新的事务，如果当前存在事务则挂起，开启的新事务相互独立，互不干扰

占用两个数据库连接，适合必须独立提交



3、propagation_nested

如果当前有事务 会创建一个嵌套事务 嵌套事务的回滚不影响外层  但外层失败 嵌套事务会回滚

经典使用场景：主流程不能因为子任务失败而整体失败，例如创建订单和扣减库存完之后，尝试发优惠券，不能因为优惠券失败导致订单创建有损

基于savepoint实现 回滚只回滚到savepoint 还是同一个连接



事务失效的场景：

1、必须用在public方法

2、同类内部调用（非常场景）其实相当于this 直接绕过代理 用了原始对象，解决方案：重构、自注入

3、异常被吞掉 或和rollbackFor的异常不匹配

4、bean没有被spring管理



代理类的生成时机：spring容器启动时 不在运行时

springboot2.0之后都默认用cglib动态代理





### 自动装配

传统spring需要手写大量的xml或@configuration来配置大量的bean，自动装配思想是：引入了哪个依赖，框架自动把对应的bean配置好，开箱即用

实现原理：@springbootapplication--->@EnableAutoConfiguration--->import(AutoConfigurationImportSelector)这个类负责找到并加载所有自动配置类



metai-inf下加载所以自动配置类，读取自动配置类全类名，然后将符合条件的配置类注册为BeanDefinition，然后实例化放入容器

### 循环依赖

指Bean对象循环引用，spring通过三级缓存解决：

第一层：singletonObjects 存放完整bean

第二次：earlySingletonObjects 半成品 尚未进行属性填充

第三级：原始bean对象或代理对象

本质是发生循环依赖，去第三级缓存拿objectfactory调用getobject（）来获取前期暴露对象，并将这个前期暴露对象放入二级缓存

如果没有aop其实两级就行，三级缓存可以避免一个bean有多个代理对象

### 限流

对请求的速率进行限制，避免瞬时的大量请求击垮软件系统

限流最场景的是在服务端，当然客户端也可以自觉限流为了保护下游



限流算法：

1、固定窗口计数器

将时间划分为固定大小的窗口 限流不够平滑 也存在窗口边界突刺问题 比如1分钟限制1000个，如果上一分钟最后1s和下一分钟开始1s分别涌入 会造成2s内放行2000个



2、滑动窗口计数器

在固定窗口的基础上划分更多个子窗口，子窗口划分越多限流越平滑



3、漏桶

实现上即队列保存请求，服务定期从队列里拿请求执行，和消息队列削峰的思想一

实际还是令牌桶用的多，因为令牌桶可以允许正常突发流量



4、令牌桶

桶里面装令牌，请求在被处理之前需要从桶里拿到一个令牌，如果桶里没有令牌就要等待或拒绝

我们根据限流大小，按一定速率往桶里添加令牌，如果桶满了就不再继续加



**如何理解令牌桶和漏桶的区别**

漏桶的突发流量 需要排队等待 对下游来说是稳定的

而令牌桶只要桶里有token，立即全部放行，突发时瞬间压力大，比如流量低时令牌桶里可能积累了一部分令牌



**分布式限流**

当然其实也可以用本地限流+负载均衡均匀打散

利用Redis+Lua脚本实现分布式限流：

```
-- 滑动窗口限流
-- KEYS[1]: Redis key
-- ARGV[1]: 当前时间戳(ms)
-- ARGV[2]: 窗口大小(ms)
-- ARGV[3]: 限流阈值
-- ARGV[4]: 请求唯一ID（ZSET member）

local key       = KEYS[1]
local now       = tonumber(ARGV[1])
local window    = tonumber(ARGV[2])
local limit     = tonumber(ARGV[3])
local requestId = ARGV[4]

-- 删除窗口之外的过期记录
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 统计当前窗口内的请求数
local count = redis.call('ZCARD', key)

if count < limit then
    -- 未超限，记录本次请求
    redis.call('ZADD', key, now, requestId)
    -- 设置过期时间，防止 key 泄漏（单位 ms）
    redis.call('PEXPIRE', key, window)
    return 1
end

return 0

```



```
-- 令牌桶限流
-- KEYS[1]: Redis key
-- ARGV[1]: 桶容量 capacity
-- ARGV[2]: 每秒补充令牌数 refillRate
-- ARGV[3]: 当前时间戳(ms)

local key        = KEYS[1]
local capacity   = tonumber(ARGV[1])
local refillRate = tonumber(ARGV[2])
local now        = tonumber(ARGV[3])

local info     = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens   = tonumber(info[1])
local lastTime = tonumber(info[2])

-- 首次请求：初始化满桶
if tokens == nil then
    tokens   = capacity
    lastTime = now
end

-- 按时间差计算应补充的令牌数
local elapsed  = (now - lastTime) / 1000.0
local refilled = math.floor(elapsed * refillRate)
tokens = math.min(capacity, tokens + refilled)

-- 只在实际补充了令牌时推进时间戳，避免毫秒精度丢失
if refilled > 0 then
    lastTime = now
end

-- TTL = 桶从空到满所需秒数 + 5s 缓冲
local ttl = math.ceil(capacity / refillRate) + 5

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_time', lastTime)
    redis.call('EXPIRE', key, ttl)
    return 1
end

-- 令牌不足，更新状态后拒绝
redis.call('HMSET', key, 'tokens', tokens, 'last_time', lastTime)
redis.call('EXPIRE', key, ttl)
return 0

```





### 幂等

在接口语义里 幂等主要指多次相同请求对服务端资源产生的预期效果和执行一次请求一致

接口幂等性问题通常由网络波动、用户重复操作、客户端/网关超时重试、消息重复投递等触发

涉及资金、订单、库存、优惠券这类场景都需要认真处理幂等



一般业务唯一键/幂等号负责识别重复请求，数据库唯一索引或去查表负责兜底、状态机负责防止状态回退



**常见的幂等实现方案：**

1、HTTP接口防重复提交

Token+Redis AOP 前端配合简单

 客户端先获取 token → 携带 token 发起请求 → 服务端用Redis做去重

2、数据库唯一索引

最终一致 DB兜底

例如订单号

3、支付回调/消息消费

状态机+乐观锁，天然幂等，无需额外存储

适合有状态流转的场景





### 超时&重试

当一个请求超过指定时间还没有被处理，请求会直接被取消并抛异常，例如504gateway timeout

一般超时可以简单分为：

1. 连接超时 connect timeout客户端与服务端建立TCP连接的最长等待时间
2. 读取超时 read timeout 连接已建立后 客户端等待对端返回数据的最长等待时间

总超时 即整个请求的上限

**生产环境还要看客户端是否支持更多维度的超时配置**：



如果没有超时机制 可能会导致服务端连接数爆炸 和 大量请求堆积的问题

超时值应该参考p99响应时间



超时一般搭配重试，但要清楚对哪些错误去重试，常见的例如：

1. 网络抖动、连接超时
2. 503
3. 幂等操作的5xx

且重试一般建议搭配退避策略，生成推荐指数退避+抖动，避免多个客户端同时重试

retry after:1s + rand  2s+rand 4s+rand

通常就重试2-3次 大量重试会让已经挂掉的服务雪上加霜 应配合熔断



### 降级&熔断

在微服务架构里，一个请求往往要经过好几个服务的调用链，如果链路上某个服务出了问题，比如响应变慢甚至挂掉，很容易把上游的资源也拖垮，最后演变成整条链路雪崩，降级和熔断就是应对这类问题的防线



Fallback：兜底结果，正常情况下请求调用真实业务逻辑，但如果调用失败或限流熔断了，系统不能直接把异常甩给用户，而是返回一个提前准备好的结果，别让一次失败把整个链路拖垮

例如推荐服务挂了先返回空列表、商品详情接口超时就返回缓存的旧数据



熔断思路：如果发现下游已经明显不正常，不再调用而是直接fallback，等一段时间后再放少量请求过去试探，如果下游恢复了再慢慢恢复正常调用

### CDN

content delivery network内容分发网络，通过将内容缓存到全球分布的边缘节点，让用户从最近的节点获取资源，降低延迟提升可用性



用户请求-->DNS解析-->就近边缘节点

若边缘节点命中缓存则直接返回，未命中则回源到源站，然后再缓存下来

适用：静态资源、大文件下载（安装包）

核心指标：缓存命中率/回源率



正常我们将自己域名的CNAME指向云厂商的CDN域名，这样换CDN云厂商时只需改CNAME记录即可，前端代码无需改动，CNAME是DNS的一种记录类型作用是给一个域名起别名指向另一个域名

CDN厂商边缘节点IP是动态变化的，会根据位置、节点负载实时调度，即GSLB

一般CDN服务器是搬运工，优化目标是高吞吐低CPU，对硬盘、网卡要求很高



**CDN加速动态请求**

静态资源靠缓存，动态请求靠网络路径优化

以用户在上海访问北京的API为例，正常是走公网路由到北京服务器

公网路由的问题：

- 路径不是最优
- 跨运营商劣化严重
- 节点拥堵无法干预

CDN加速原理是：CDN厂商在全球建了专线骨干网，边缘节点之间走私有链路

上海用户先从边缘CDN节点接入，走厂商专线到北京CDN节点，然后到服务器，绕开不可控公网



**价值**

基础设施的共享摊薄，是典型的规模效应，自建一套成本很昂贵

Akamai烧了20多年才有现在的规模



**盗刷**

CDN盗刷主要是两种场景：

1. 盗链 即别人的网站引用你的资源
2. 恶意刷量 即脚本大量请求消耗你的流量

Referer白名单，检查请求头里的Refer 只允许来自自身域名的请求，但Refer可以伪造

token鉴权，给每个资源URL带过期时间的签名，CDN节点验证签名，过期报错

恶意刷量：对单IP限制、地域封禁



### 负载均衡

将用户请求分摊到不同服务器处理，提高整体并发能力和可靠性，可以由硬件或软件实现，硬件更贵但性能更好

又分为服务端负载均衡和客户端负载均衡两种



硬件负载均衡太贵了例如F5 A10，开发还是软件负载均衡接触多，又根据OSI模型分四层和七层

执行七层负载均衡的设备称为反向代理服务器（常见nginx），四层的核心是IP+端口的 loadbalance，七层是http报文的loadbalance



客户端负载均衡就是在客户端维护一份服务器地址列表，根据对于负载均衡算法选择一台服务器请求



**场景算法**

1、随机



2、轮询（可加权）



3、哈希&一致性哈希

将请求的参数信息通过哈希函数换算哈希值，又哈希值决定请求被哪一台服务器处理

在服务器数量不变的情况下，相同参数的请求总是发到一台服务器处理



一致性哈希是将数据和节点都映射到一个哈希环上，根据哈希值的顺序决定哪个节点，这样当服务器增加或删除时只影响该服务的哈希，不会造成整体rehash



4、最小连接、最小活跃、最快响应

根据某些指标 挑选当前集群某个节点



**七层负载均衡怎么做**

1、DNS解析

在DNS服务器为同一个主机配置多个IP地址，用户请求域名时，DNS服务器采用轮询算法返回IP地址，也可以做IP做权重

2、反向代理

让反向代理去选择目标服务器，隐藏真实服务器IP地址



**健康检查与摘流量**

TCP检查

HTTP检查 例如定期访问/health接口

判断一个节点是否健康，能不能接入流量





## 系统设计



### 代理

正向代理：客户端通过正向代理服务器访问目标服务器，需要设置正向代理的IP+端口，例如借助VPN工具

反向代理：客户端把请求发送到反向代理服务器，让反向代理服务器去选择目标服务器，让真实服务器IP隐藏，一般在跨域时常用，还可通过反向代理实现负载均衡



Nginx除了作为静态资源服务器，通常也可作为反向代理服务器，此外还具备健康检查即服务器心跳检测，定期轮询集群内所有服务器

nginx适合用来做负载均衡：本身处于7层应用层，且自带健康检查，nginx基于C语言实现性能很好，1000个非活跃的http keep-alive连接只占2.5mb内存 单机可以撑10w以上并发
